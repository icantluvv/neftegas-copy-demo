# Master Skill: Estimates — Полный воркфлоу оценки

Ты ведёшь весь процесс оценки от начала до конца. Работаешь в двух фазах: **декомпозиция** (с вопросами) → **оценка** (с рисками и артефактами).

---

## Входные данные

- `tasks` — описание задачи или список задач
- `context` — контекст проекта (стек, ограничения, особенности)

---

## ФАЗА 1 — Декомпозиция

### 1.1 Анализ кодовой базы и уточнения

Изучи проект перед тем, как задавать вопросы:

```
Бэкенд:
  package.json                    — стек, пакеты (NestJS, TypeORM)
  src/                             — домены, структура, паттерны
  src/database/migrations/        — схема БД
  *.spec.ts, *.e2e-spec.ts        — наличие покрытия

Фронтенд:
  package.json                    — стек (React, Next.js, TypeScript)
  src/ или app/ (FE)              — компоненты, роутинг
  openapi*.yaml                   — OpenAPI-контракт, кодогенерация
```

Не спрашивай то, что можно прочитать из кода. Задавай только вопросы, от которых напрямую зависит декомпозиция. Предпочитай 0 вопросов если всё ясно.

Если вопросы есть — выведи:

```
## Уточняющие вопросы

Нашёл в коде: [summary — стек, что реализовано, на что опираемся]

1. [вопрос] — влияет на: [что именно]
...

Жду ваши ответы.
```

**Жди ответа пользователя перед декомпозицией.**

### 1.2 Декомпозиция BE + FE

После ответов (или сразу, если вопросов нет) — раздели каждую задачу на подзадачи.

Для каждой подзадачи определи: `new` / `modify` / `config` / `test`, найди компонент в `components_ref`. **RE на этом этапе не считаем** — только тип, компонент и источник (`ref` — найден в справочнике, `code` — будет оценён по факту кода на этапе оценки, `ai` — будет оценён по аналогии).

Покажи таблицу на верификацию:

```
## Декомпозиция: [название задачи]

### Backend

| Подзадача | Тип | Компонент из справочника | Источник |
|---|---|---|---|

**Легенда:** Тип — `new` новая разработка, `modify` правка существующего, `config` только настройка, `test` тест-подзадача. ⚠️ — повышенная сложность, требует отдельного внимания при оценке.

### Frontend

| Подзадача | Тип | Компонент из справочника | Источник |
|---|---|---|---|

**Легенда:** см. выше.

**Почему так декомпозировано:**
[2–4 предложения: ключевые решения, что нашлось в коде]

---
Верифицируйте декомпозицию. «ок» — продолжаю. Иначе — опишите правки.
```

**Жди подтверждения.** При правках — перестрой таблицу и снова жди.

### 1.3 Сохрани decomposition.md

После подтверждения сохрани `estimates/<slug>/decomposition.md`:

```markdown
---
задача: "..."
слаг: "..."
дата: "YYYY-MM-DD"
охват: "бэкенд, фронтенд"
---

# Декомпозиция: [название]

## Почему декомпозировано именно так
[2–5 предложений]

## Backend
| Подзадача | Тип | Компонент | Источник | Комментарий |
|---|---|---|---|---|

**Легенда:** Тип — `new` новая разработка, `modify` правка существующего, `config` только настройка, `test` тест-подзадача. ⚠️ — повышенная сложность.

## Frontend
| Подзадача | Тип | Компонент | Источник | Комментарий |
|---|---|---|---|---|

**Легенда:** см. выше.

## Находки из кодовой базы
- [находка и влияние]
```

RE появляется только на этапе оценки (ФАЗА 2): определяется по `components_ref` (источник `ref`), по факту кода (источник `code`, помечается 🔍 в таблице оценки) или по аналогии (источник `ai`, помечается ⚠️).

Сообщи: `✓ Декомпозиция сохранена: estimates/<slug>/decomposition.md`

## ФАЗА 2 — Оценка

**Ключевая логика:** RE — цена для заказчика (без AI, «по старому»). CE — внутренняя метрика планирования ресурсов, в цену клиенту не идёт. Тестирование, риски и рентабельность применяются к **RE**, не к CE.

### 2.1 Определи RE и посчитай коэффициенты AI

Для каждой подзадачи (RE в decomposition.md отсутствует):
- `Источник: ref` → найди компонент в `components_ref`, возьми его RE
- `Источник: code` → изучи кодовую базу и выведи RE на основе реального контекста; пометь 🔍
- `Источник: ai` → оцени по аналогии с ближайшим компонентом справочника; пометь ⚠️

**Формула BE (на каждую подзадачу):**
```
RE_be_hours      = estimate_min / 60
type_multiplier  = new→1.0 | modify→0.6 | config→0.2 | test→1.0
CE_subtask_be    = RE_be_hours × base_coeff × type_multiplier
RE_base_be       = Σ RE_be_hours
CE_base_be       = Σ CE_subtask_be   # информационно, для планирования ресурсов
```

**Формула FE (на каждую подзадачу):**
```
RE_fe_hours      = estimate_hours (уже в часах)
CE_subtask_fe    = RE_fe_hours × base_coeff × type_multiplier
RE_base_fe       = Σ RE_fe_hours
CE_base_fe       = Σ CE_subtask_fe   # информационно
```

`base_coeff` — берётся из `components_ref` по `component_ref` подзадачи.

### 2.2 Тестирование — применяй к RE

```
RE_autotests_be = RE_base_be × 1.10   # +10% автотесты
RE_qa_be        = RE_autotests_be × 1.15   # +15% QA

RE_autotests_fe = RE_base_fe × 1.10
RE_qa_fe        = RE_autotests_fe × 1.15
```

### 2.3 Технические риски

Прочитай код для автоматических индикаторов:

| Признак в коде | Риск |
|---|---|
| tests/ пустой / нет тестов | `legacy_code` (+20–35%) |
| Файлы >500 строк без разделения | `legacy_code` |
| Хардкод credentials | `critical_infra` (+15–25%) |
| TODO/FIXME в критичных местах | `legacy_code` |
| Нет OpenAPI на API | `unclear_requirements` (PM) |
| JS без TypeScript на фронте | `legacy_code` (FE) |
| Нет конфига нужных интеграций | `new_technology` (+15–30%) |

Добавь PM-риски из контекста задачи (`unclear_requirements`, `tight_deadline`, `scope_creep` и т.д.) — по `risk_factors_ref`.

```
risk_sum   = Σ применённых весов
risk_coeff = 1 + risk_sum

price_risks_be = RE_qa_be × risk_coeff
price_risks_fe = RE_qa_fe × risk_coeff
```

### 2.4 Рентабельность — итоговая цена для заказчика

```
price_final_be    = price_risks_be × 1.25   # +25% рентабельность
price_final_fe     = price_risks_fe × 1.25
price_final_total = price_final_be + price_final_fe
```

Округление итоговых слоёв: до 0.25 ч вверх. Округление построчных значений в таблицах: до 0.1 ч вверх.

### 2.5 Верификация оценки

Покажи послойную таблицу (порядок: коэффициенты AI → допущения 🔍/⚠️ → риски → послойный расчёт):

```
## Оценка: [название задачи]

### Коэффициенты AI — Backend

| Подзадача | Тип | RE (ч) | Коэфф. AI | CE (ч) | Компонент |
|---|---|---|---|---|---|

### Коэффициенты AI — Frontend

| Подзадача | Тип | RE (ч) | Коэфф. AI | CE (ч) | Компонент |
|---|---|---|---|---|---|

### Применённые риски

| Риск | Вес | Источник | Обоснование |
|---|---|---|---|

### Послойный расчёт

Все надбавки применяются к RE, а не к CE.

| Слой | BE (ч) | FE (ч) | Итого (ч) |
|---|---|---|---|
| RE — сырая оценка (цена без AI) | | | |
| CE — коэф. AI (план ресурсов, информационно) | | | |
| + Тестирование (+10% авт. / +15% QA) | | | |
| + Технические риски (×N.NN) | | | |
| **+ Рентабельность (+25%)** | **X.X** | **X.X** | **X.X** |

---
Верифицируйте оценку. «ок» — сохраняю артефакты.
```

**Жди подтверждения.** При правках — пересчитай и снова жди.

### 2.6 Сохрани estimate.md и report.html

После подтверждения сохрани оба файла.

**`estimates/<slug>/estimate.md`** — детальные числа с frontmatter (`задача`, `слаг`, `дата`, `re_be_hours`, `re_fe_hours`, `ce_be_hours`, `ce_fe_hours`, `risk_coeff`, `price_final_be`, `price_final_fe`, `price_final_total`) и таблицами (коэффициенты AI, риски, послойный расчёт).

**`estimates/<slug>/report.html`** — HTML-отчёт для заказчика. **Только итоговые числа и список задач с финальными оценками — без коэффициентов, рисков и внутренних расчётов.** Включает:
- Заголовок с названием задачи и датой
- Три карточки-summary: Backend / Frontend / Итого (с градиентным выделением итога)
- Таблица «Состав работ»: Область (BE/FE) | Задача | Оценка (ч) — финальная цена на подзадачу
- Footer

Финальная оценка каждой подзадачи: `ceil(RE_subtask × 1.10 × 1.15 × risk_coeff × 1.25 / 0.25) × 0.25`.

Стиль: светлый фон `#f8f9fa`, белые карточки с `border-radius: 12px`, тёмный градиентный header, цветовые badge-метки для области (BE синий / FE розовый).

После сохранения:

```
✓ Декомпозиция: estimates/<slug>/decomposition.md
✓ Оценка:       estimates/<slug>/estimate.md
✓ Отчёт:        estimates/<slug>/report.html

Откройте report.html в браузере — это версия для показа заказчику.
```
