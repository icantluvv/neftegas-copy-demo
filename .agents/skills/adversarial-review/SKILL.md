# Состязательное код-ревью с арбитражем

Цель: получить вычищенный от шума и оверкилла отчёт о ревью за счёт двух независимых параллельных ревью + явной фазы оспаривания (критик) + независимого арбитража (третий агент выносит финальный вердикт по каждому пункту).

Ключевая механика: после параллельного ревью идут два разных агента в разных ролях — критик-«адвокат дьявола» активно ищет слабости в замечаниях, а арбитр выносит финальное решение между ревьюером и критиком.

Аргумент: $ARGUMENTS

Возможные формы аргумента:
- пусто → ревью diff'а `master..HEAD` (или базовая ветка проекта, см. ниже)
- `<base-ref>` → ревью diff'а `<base-ref>..HEAD`
- `<base>..<head>` или `<base>...<head>` → явный git-range
- список путей → ревью только этих файлов
- `--base=<ref>` + список путей → ревью этих файлов относительно базы

**Важные правила (зашиты в скилл):**
- Никогда не правь код. Результат — только Markdown-отчёт.
- Ровно один раунд параллельного ревью, ровно один раунд критики, ровно один раунд арбитража. Никаких повторов.
- Шаги Agent×2 (ревью) — параллельные tool-calls в одном сообщении.
- Критик НЕ делает своё ревью — он только оспаривает существующие пункты. Не нашёл что оспорить — молчит.
- Арбитр НЕ ищет новые замечания — он только разрешает спор по существующим пунктам.
- Не дублируй работу агентов локально. Объединяй то, что они вернули.

## Фаза 0: Подготовка

1. Создай TaskList'ом 6 задач:
   - «Собрать скоуп ревью»
   - «Собрать свод правил проекта (кеш или пересборка)»
   - «Параллельно запустить 2 агента ревью»
   - «Свести черновой отчёт в файл свода»
   - «Запустить агента-критика — пишет в отдельный файл критики»
   - «Запустить агента-арбитра — читает свод+критику, пишет финальный отчёт»
2. Определи **базу сравнения**:
   - если в аргументе есть base/range — используй
   - иначе `git symbolic-ref refs/remotes/origin/HEAD` → fallback `master`/`main`
3. Определи **скоуп ревью**:
   - `git log --oneline <base>..HEAD`
   - `git diff --stat <base>..HEAD`
   - `git diff --name-only <base>..HEAD`
   - если переданы конкретные файлы — фильтруй diff по ним
   - вычисли **затронутые подпроекты**: уникальные верхнеуровневые директории из diff'а (`apps/backend`, `apps/frontend`, `services/*` и т. д.) — это нужно для следующей фазы, чтобы не тащить правила фронта в ревью бекенда и наоборот
4. Определи **место сохранения отчёта** (`<reviews-dir>`):
   - найди существующую папку с отчётами: `find . -type d -name reviews -not -path '*/node_modules/*' -not -path '*/vendor/*' 2>/dev/null`
   - если есть — клади туда
   - если нет — создай `docs/reviews/` (или `apps/<app>/docs/reviews/` для монорепо, по структуре наиболее изменённой папки)
   - кеш свода правил живёт **не** в `<reviews-dir>`, а в корне **main worktree** — `<main-worktree>/.rules-cache/` (см. Фаза 1, Шаг 1.0), чтобы переживать снос временных worktree и переиспользоваться между ними
5. Определи **имена файлов** (все три — в одной директории отчётов; пусть `<branch>` = текущая ветка из `git rev-parse --abbrev-ref HEAD`, для detached HEAD — `review-YYYY-MM-DD`):
   - **Свод (черновой отчёт после Фазы 3):** `<branch>-review-draft.md` — продукт работы главного агента, читают критик и арбитр.
   - **Критика (Фаза 4):** `<branch>-review-critique.md` — продукт работы агента-критика, читает арбитр.
   - **Финальный отчёт (Фаза 5):** `<branch>-review.md` — продукт работы агента-арбитра, единственный документ, нужный пользователю.

   **Артефакты не удаляются по умолчанию.** Все три файла остаются на диске как полный лог процесса (свод фиксирует исходное мнение ревьюеров, критика — оспаривания, финальный — арбитраж). Если пользователь явно попросил «оставь только финал» — удали `*-draft.md` и `*-critique.md` после Фазы 5.

## Фаза 1: Сборка свода правил проекта (с кешем)

**Цель.** Перед ревью собрать в одно место все артефакты, которые могут содержать архитектурные/кодовые/процессные правила, релевантные затронутым подпроектам. Это критично для качества ревью: агенты должны проверять не «общие best practices», а **то, как принято в этом конкретном репозитории**, включая частные документы вроде `apps/backend/docs/backend-architecture.md`.

**Порядок фазы.** Сначала Шаг 1.0 решает, нужна ли пересборка. Если кеш валиден (cache hit) — Шаги 1.2–1.4 пропускаются, свод берётся из кеша. Если нет (cache miss) — выполняется полная сборка 1.1→1.4 и запись кеша (Шаг 1.5). Показ пользователю (Шаг 1.6) — всегда.

### Шаг 1.0 — Проверка кеша свода правил

Сборка свода (Шаги 1.1–1.4) — самая долгая часть скилла (десятки `Read` + извлечение и формулирование правил). Чтобы не повторять её на каждом ревью, готовый свод кешируется на диске и переиспользуется, пока **источники правил не изменились** и не истёк TTL.

**Где лежит кеш.** В корне **main worktree**, в служебной папке `<main-worktree>/.rules-cache/`. Кеш намеренно НЕ кладётся в `<reviews-dir>` и не в текущий worktree: он должен переживать снос временных worktree и переиспользоваться между ними. Путь к main worktree получи командой (работает и из main, и из вторичного worktree — это та же команда, что в Фазе 6):

```bash
main_worktree=$(git worktree list --porcelain | awk '/^worktree / {print $2; exit}')
```

Если `git worktree` недоступен — fallback на корень текущего репозитория (`git rev-parse --show-toplevel`); ошибка определения main worktree не валит скилл.

Свод зависит от затронутых подпроектов (см. Шаг 1.2), поэтому кеш ключуется по **скоупу**: имя файла — `<scope-key>.md`, где `scope-key` — отсортированные затронутые подпроекты из Фазы 0 (шаг 3), слеши → `-`, разделитель между подпроектами `__`; если подпроектов нет — `root`. Примеры: `apps-backend.md`, `apps-backend__apps-frontend.md`. Один общий каталог `.rules-cache/` обслуживает все скоупы — коллизий нет, файлы разведены по `<scope-key>`.

> Кеш — служебный артефакт, его не нужно коммитить. Если в `.gitignore` main worktree ещё нет строки для кеша — добавь `/.rules-cache/`. Не валить скилл, если добавить не удалось.

**Алгоритм проверки (выполняется всегда, он дешёвый):**

1. Вычисли `scope-key`, определи `<main-worktree>` (см. выше) и путь `<cache-file> = <main-worktree>/.rules-cache/<scope-key>.md`.
2. Выполни **только поиск** источников (Шаг 1.1) — это быстро. Получи актуальный отсортированный список путей файлов-источников.
3. Посчитай **отпечаток** каждого источника по содержимому (устойчиво к `touch`, кроссплатформенно):
   ```bash
   for f in <список источников>; do printf '%s  %s\n' "$(git hash-object "$f" 2>/dev/null || echo MISSING)" "$f"; done
   ```
   `git hash-object` читает файл с диска (учитывает незакоммиченные правки) и одинаково работает на любой ОС.
4. Кеш **валиден**, если файл `<cache-file>` существует И выполнены все три условия:
   - **TTL не истёк:** `now_epoch − generated_at_epoch ≤ 7 × 86400` (7 дней — согласованный потолок). `now_epoch = $(date +%s)`.
   - **состав источников совпал:** список путей из шага 2 идентичен набору `sources[].path` в кеше (нет новых/исчезнувших файлов).
   - **содержимое источников совпало:** для каждого источника `git hash-object` из шага 3 равен сохранённому `sources[].hash`.
5. **Cache hit** (все условия выполнены): возьми готовый блок «Свод правил проекта» из тела `<cache-file>` — **пропусти Шаги 1.2–1.4**, сразу переходи к Шагу 1.6. В реплике пользователю укажи, что свод взят из кеша, и его возраст.
6. **Cache miss** (файла нет / TTL истёк / отпечаток разошёлся): выполни полную сборку — Шаги 1.2–1.4 — и запиши кеш (Шаг 1.5).

> TTL здесь — вторичная подстраховка. Основную корректность даёт отпечаток по содержимому: он ловит любую правку источника раньше TTL. 7 дней — лишь потолок «обновись хотя бы раз в неделю» на редкие edge-кейсы (например, источник правил вне git).

> Источники хешируются из **текущего** worktree (`git hash-object` читает файл с диска), а кеш хранится в main worktree. Если файлы правил в worktree и main различаются (разные ветки) — отпечаток разойдётся, кеш пересоберётся и перезапишется: общий кеш самовосстанавливается, специальной обработки не нужно.

### Шаг 1.1 — Поиск артефактов с правилами

> Выполняется **всегда** (нужен и для отпечатка кеша в Шаге 1.0, и для полной сборки).

Используй `Glob` / `find` / `Bash`. Не ограничивайся одним именем файла — типичные артефакты разнятся между проектами:

**Обязательно ищем:**
1. Все `CLAUDE.md` — корень и подпапки: `find . -name 'CLAUDE.md' -not -path '*/node_modules/*' -not -path '*/vendor/*' 2>/dev/null`
2. Все `AGENTS.md` (часто аналог CLAUDE.md): `find . -name 'AGENTS.md' -not -path '*/node_modules/*' -not -path '*/vendor/*' 2>/dev/null`
3. Все `*architecture*` документы: `find . -type f \( -iname '*architecture*' -o -iname '*архитектур*' \) -not -path '*/node_modules/*' -not -path '*/vendor/*' 2>/dev/null`
4. Все ADR'ы: `find . -type d -iname 'adr' -not -path '*/node_modules/*' 2>/dev/null` → их `*.md`
5. Конвенции и гайдлайны: `find . -type f \( -iname 'conventions*' -o -iname 'guidelines*' -o -iname 'styleguide*' -o -iname 'CONTRIBUTING*' \) -not -path '*/node_modules/*' 2>/dev/null`
6. AI-конфиги для других ассистентов (часто содержат проектные правила): `.cursorrules`, `.cursor/rules/`, `.windsurf/`, `.github/copilot-instructions.md`, `.aider.conf.yml`
7. **Документы предыдущих ревью** в выбранной папке `*/reviews/*-review.md` — формат, тон, повторяющиеся замечания (НЕ для копирования содержимого — для понимания паттерна)
8. **Архитектурные тесты** как кодифицированные правила: `find . -type d -iname 'Architecture' -not -path '*/node_modules/*' 2>/dev/null` → файлы тестов внутри
9. **OpenSpec / RFC / proposal** документы по теме изменений: `find . -type d \( -iname openspec -o -iname rfcs -o -iname proposals \) 2>/dev/null` → файлы внутри (для контекста, что задумывалось)

**Memory-правила пользователя** уже в контексте через `MEMORY.md` — выпиши явно те, что относятся к стеку текущего скоупа.

### Шаг 1.2 — Фильтрация по релевантности

> Шаги 1.2–1.4 выполняются **только при cache miss**. При cache hit свод уже готов (взят из кеша в Шаге 1.0).

Для каждого найденного файла оцени, релевантен ли он скоупу:
- если затронут только `apps/backend/**` — игнорируй фронтовые правила (`apps/frontend/CLAUDE.md`, фронтовые архитектурные документы)
- если затронут `apps/backend/**` — обязательно включи `apps/backend/CLAUDE.md`, `apps/backend/docs/*architecture*`, корневой `CLAUDE.md`, `AGENTS.md`
- общие документы (`CONTRIBUTING.md`, `STYLEGUIDE.md` корня, корневой `CLAUDE.md`) — всегда включай
- ADR'ы — фильтруй по теме коммитов (auth → ADR про auth и т. д.); если непонятно — включи все, агент сам отбросит нерелевантные

### Шаг 1.3 — Извлечение правил

Для каждого релевантного файла используй `Read`. Извлекай **компактные формулировки правил**, не копируй текст целиком:
- **Чёрные правила** («запрещено», «никогда», «не делай») → особо отметь
- **Белые правила** («предпочитай», «всегда используй») → отметь
- **Принципы архитектуры** (тонкие контроллеры; кросс-модуль через Provider; события при ≥N подписчиках; layering; transactional outbox; и т. п.)
- **Соглашения** (naming, структура папок, формат коммитов, тестовый стиль)
- **Запреты на инструменты** (моки на БД, скип хуков, `--no-verify`, `Throwable`)
- **Memory-правила пользователя** — в отдельный блок

Если документ большой и содержит много нерелевантного — извлекай только то, что соприкасается со скоупом ревью.

### Шаг 1.4 — Формат свода правил

Сформируй блок «Свод правил проекта» в виде, пригодном для подстановки в промпт агентов:

```markdown
## Свод правил проекта (для учёта при ревью)

### Источники
- `<путь/к/файлу.md>` — <одна фраза о роли документа>
- ...

### Архитектурные принципы
- **<краткая формулировка>** — источник `<файл:строка-если-полезно>`
- ...

### Запреты (чёрный список)
- **<запрет>** — источник `<файл>`
- ...

### Соглашения и стиль
- **<правило>** — источник `<файл>`
- ...

### Memory-правила пользователя
- **<правило>** — `<MEMORY.md → файл>`
- ...
```

Этот блок целиком вставляется в промпт обоих агентов ревью (Фаза 2), а также в промпт критика (Фаза 4) и арбитра (Фаза 5) — без правил проекта арбитр не сможет рассудить спор по существу.

### Шаг 1.5 — Запись кеша (только при cache miss)

После того как свод сформирован (Шаг 1.4), сохрани его в `<cache-file>` через `Write`, чтобы следующее ревью с тем же скоупом переиспользовало его. Формат — YAML-frontmatter с метаданными + тело со сводом:

```markdown
---
scope_key: apps-backend
generated_at: 2026-06-02T14:30:00Z      # человекочитаемо, для глаз
generated_at_epoch: 1779000000           # для сравнения TTL без парсинга дат
ttl_days: 7
sources:
  - path: apps/backend/CLAUDE.md
    hash: 9a3f...                          # git hash-object
  - path: apps/backend/docs/backend-architecture.md
    hash: 1c7b...
  # ... все источники из Шага 1.1
---

## Свод правил проекта (для учёта при ревью)
<... ЦЕЛИКОМ блок свода из Шага 1.4 ...>
```

- `generated_at_epoch` — из `$(date +%s)`, `generated_at` — из `$(date -u +%Y-%m-%dT%H:%M:%SZ)`.
- В `sources` перечисли **все** файлы-источники из Шага 1.1 (даже те, из которых правил не извлеклось, — их появление/изменение тоже должно инвалидировать кеш), с их `git hash-object`.
- Тело — ровно тот блок «Свод правил проекта», что уходит в промпты агентов. Кешированная и свежесобранная версии должны быть идентичны.
- Создай папку `<main-worktree>/.rules-cache/` при необходимости (`mkdir -p`). Ошибка записи кеша не валит скилл — это лишь оптимизация; при провале просто продолжай со свежесобранным сводом.

### Шаг 1.6 — Покажи свод пользователю (без вопроса)

Выведи пользователю одну короткую реплику — **информационно, не спрашивая разрешения** — и сразу переходи к Фазе 2:
- источник свода: собран заново или взят из кеша (с возрастом кеша, напр. «из кеша, 2 дня»);
- сколько артефактов учтено и какие;
- сжатый перечень ключевых правил (по 1 строке).

**Не задавай вопрос «начинать ли ревью» и не жди подтверждения.** Скоуп и свод уже определены — этого достаточно для запуска. Пользователь при необходимости прервёт сам.

## Фаза 2: Параллельный запуск двух агентов ревью

**Ключ:** оба агента запускаются одним сообщением с двумя `Agent` tool-calls, чтобы работали параллельно.

Тип агента — выбери релевантный стеку (`general-purpose`, если нет специализированного). Если по diff'у видно несколько технологий — два разных типа на свои зоны.

**Разделение фокусов** (минимизирует overlap):

### Агент A — «Архитектура и качество кода»
Фокус: доменная модель, SOLID, разделение ответственности, чистый код, TypeORM/миграции с точки зрения схемы, читаемость, дублирование, преждевременные обобщения, утечки слоёв, соответствие архитектурному документу проекта.

### Агент B — «Безопасность, контракт, тесты, производительность»
Фокус: AuthZ/AuthN, secrets, race conditions, SQL/XSS/CSRF, rate limiting, OpenAPI ↔ реализация, идемпотентность, что не покрыто тестами, N+1, observability, миграции с точки зрения safe-deploy.

### Шаблон промпта (общий для обоих, отличается только секцией «Что нужно проверить»)

```
Проведи код-ревью изменений [в ветке `<branch>` / коммитах `<base>..HEAD` / файлах <list>] с фокусом на <ФОКУС>.

# Контекст
- Корень репозитория: <abs-path>
- База: <base-ref>
- Команды: `git diff <base>..HEAD -- <path>`, `git diff --name-only <base>..HEAD`
- Стек: <узнаётся из репо: TS/Node/NestJS, TS/Next.js, ...>

Краткий бизнес-контекст фичи: <2-3 предложения по коммитам, openspec/proposal.md если есть>

# Скоуп
<вставить список файлов из git diff --name-only, сгруппированный по модулям/папкам>

# Свод правил проекта (ОБЯЗАТЕЛЬНО учитывать при ревью)
<вставить ЦЕЛИКОМ блок «Свод правил проекта» из Фазы 1, со всеми источниками и формулировками — это «закон» для данного ревью; рядом с каждым замечанием в финальном отчёте указывай правило, которое нарушено, и его источник>

## Фаза 4: Сабагент-критик оспаривает замечания (пишет в отдельный файл)

Запусти один агент-критик (`general-purpose`, если нет специализированного для стека).

**Роль критика — адвокат дьявола.** Он не делает своё ревью. Он берёт каждый пункт чернового отчёта и пытается его опровергнуть, переклассифицировать или признать переусложнением. Цель — вычистить ложноположительные срабатывания и оверкилл, оставив только реально полезные замечания.

**Артефакт.** Критик читает черновой отчёт из файла (Read), проверяет код, и сам пишет результат в отдельный файл `<dir>/<branch>-review-critique.md` через Write. Главный агент не транслирует ответ критика в свой контекст — он будет прочитан арбитром из файла. Это экономит токены и фиксирует артефакт на диске для прозрачности.

**Промпт критика (шаблон):**

```
Ты — критик-«адвокат дьявола» для отчёта о код-ревью. Твоя задача — НЕ проводить своё ревью и НЕ искать новые замечания, а ОСПОРИТЬ замечания из чернового отчёта там, где это обоснованно.

# Контекст
- Корень репозитория: <abs-path>
- Проверяемая ветка/скоуп: <branch / range>
- База: <base>
- Свод (черновой отчёт ревью) для оспаривания: `<абсолютный путь к draft.md>` — прочти его ПОЛНОСТЬЮ через Read до начала анализа.
- Файл для записи твоей критики: `<абсолютный путь к critique.md>` — сюда ты сохранишь итог через Write.

<вставить ЦЕЛИКОМ блок «Свод правил проекта» из Фазы 1>

# Стратегия оспаривания
Для каждого пункта Blocker/Major/Minor/Тесты/Миграция/«Соответствие правилам» оцени, есть ли основание для одного из вердиктов:

1. **False positive** — проблема не существует. В коде по указанному файлу:строке нет того, что описывает пункт, или есть другое поведение. Открой файл (Read, Grep, git diff) и проверь.
2. **Overclassified** — приоритет завышен. Пункт стоит как Blocker, но фактически это Major/Minor; или Major, но реально Nitpick. Обоснуй понижение со ссылкой на правила/стандарты.
3. **Overengineering** — рекомендация требует усложнения, которое не оправдано контекстом. Например: «вынести в сервис», когда логика в одном месте читается лучше; «ввести абстракцию», когда конкретики достаточно; «покрыть тестами» для приватных деталей реализации, не для контракта.
4. **Intentional / by design** — поведение намеренное, соответствует существующим паттернам в репо (приведи пример из кода), или зафиксировано в архитектурном документе/ADR.
5. **Duplicate** — пункт повторяет другой (укажи какой).
6. **Contradicts project rules** — рекомендация прямо противоречит своду правил проекта или MEMORY-правилам пользователя (приведи источник).
7. **Out of scope** — пункт касается кода, которого нет в diff (касается legacy/неизменённого).

# Что НЕ делать
- Не вноси правки в код.
- Не ищи новые замечания, не упомянутые в черновике.
- Не оспаривай ради оспаривания: если пункт обоснован — просто пропусти его, не пиши «согласен».
- Не атакуй формулировки/стиль — только содержание.
- Не повторяй сам черновик.

## Фаза 5: Сабагент-арбитр — читает свод и критику, создаёт финальный отчёт

# Как принимать решения
Для каждого пункта свода, который оспорил критик, выбери одно из:

1. **Подтверждён (uphold)** — критик неправ, оставить пункт как есть. Опровергни аргументы критика со ссылкой на файл:строку или правило.
2. **Понижен (downgrade)** — критик прав в части приоритета. Перенеси пункт в секцию более низкого приоритета (Blocker → Major / Major → Minor / Minor → удалить).
3. **Удалён (drop)** — критик прав, пункт ложный/out of scope/duplicate. Не включай в финальный отчёт.
4. **Переформулирован (rephrase)** — суть сохраняется, формулировка/предложение по фиксу меняется. Используй новую формулировку в финальном отчёте.
5. **Объединён (merge)** — пункт сливается с другим, в целевом пункте добавь кросс-референс.

По пунктам, которые критик НЕ оспаривал — оставляй как есть, перенося в финальный отчёт без изменений.

**Принципы:**
- Если критик дал слабую аргументацию (без ссылок на код или правила) — это повод подтвердить пункт.
- Если ревьюер не указал файл:строку, а критик это поднял — либо доуточни сам (открой код), либо удали пункт.
- При расхождении классификации между агентами A и B (зафиксировано в Open questions свода) — вынеси вердикт явно, со ссылкой на правило проекта.

# Проверка фактов
Для всех Blocker и для пунктов с вердиктом «удалён»/«понижен» — открой файл и проверь сам (Read/Grep/git diff). Не верь критику на слово. Если критик ошибся в фактах, но прав в принципе — переформулируй пункт сам.

## Фаза 6: Финальная сводка пользователю

После того как арбитр сообщил о сохранении файла:

1. Проверь, что файл `<branch>-review.md` создан (`ls` / `Read` первые строки).
2. **Если скилл запущен из вторичного git worktree — скопируй финальный отчёт в main worktree** по тому же относительному пути:
   - Определи, в worktree ли мы:
     ```bash
     git_dir=$(git rev-parse --absolute-git-dir)
     common_dir=$(git rev-parse --path-format=absolute --git-common-dir)
     ```
     Если `git_dir == common_dir` — мы в main worktree, **пропусти этот шаг целиком**.
   - Иначе получи путь main worktree (первая запись в `git worktree list --porcelain`):
     ```bash
     main_worktree=$(git worktree list --porcelain | awk '/^worktree / {print $2; exit}')
     ```
   - Построй целевой путь: `<main_worktree>/<тот же относительный путь, что у локального финала>/<branch>-review.md`. Относительный путь — это `<dir>/<branch>-review.md` из Фазы 0 шаг 4.
   - Создай целевую папку при необходимости (`mkdir -p`) и скопируй через `cp` (перезапись, если файл уже есть, — нормально).
   - **Копируется только финальный `<branch>-review.md`.** Промежуточные `<branch>-review-draft.md` и `<branch>-review-critique.md` остаются только в worktree.
   - Если копирование упало (нет прав на запись, отсутствует `git worktree list` и т. п.) — **не валить скилл**: сообщи об ошибке отдельной строкой и продолжай шаг 4. Локальный финал в worktree остаётся главным результатом.
3. Если пользователь явно попросил «оставь только финал» — удали `<branch>-review-draft.md` и `<branch>-review-critique.md`. Иначе — оставь как лог процесса.
4. Выведи пользователю одной-двумя репликами:
   - путь к финальному отчёту в текущем worktree
   - если копирование в main worktree сработало — отдельной строкой путь и там
   - сколько Blocker/Major/Minor в финале
   - сколько пунктов оспорено критиком и сколько подтверждено / понижено / удалено арбитром (метрики читаются из шапки критики и сравнения свода с финалом)
   - пути к промежуточным артефактам (`*-draft.md`, `*-critique.md`), если они оставлены

Если пользователь не просил коммитить — НЕ коммить. Если попросил — обычный flow создания коммита.

## Правила скилла

- **Параллельность.** Шаг Agent×2 (ревью) — всегда одним сообщением с двумя tool-calls. Критик и арбитр — последовательно (арбитру нужен файл критики).
- **Никаких правок в код.** Любая попытка править исходники любым из агентов — ошибка скилла.
- **Строго одноразовый пайплайн.** Один раунд ревью → один раунд критики → один раунд арбитража. Никаких повторных раундов и итераций.
- **Файлы — единственный канал передачи между фазами.** Главный агент готовит пути, сабагенты пишут/читают файлы. Главный агент НЕ копирует содержимое свода или критики в промпт арбитра — арбитр читает файлы сам. Это защищает контекст главного агента и фиксирует артефакты.
- **Структура финального отчёта — фиксированная (по шаблону Фазы 5).** Без таблицы решений, без пометок «бывший B3», без раздела «Решения арбитража». Трассировка остаётся в сохранённых файлах свода и критики.
- **Дедупликация.** Свод (Фаза 3) — это не объединение текста двух ревью, а слияние смыслов.
- **Сквозные ID** обязательны в своде — без них критик не может адресно оспаривать, а арбитр не может сопоставить позиции. В финальном отчёте — своя сквозная нумерация (не наследуется из свода).
- **Свод правил проекта** прокидывается в четыре промпта: оба ревьюера, критик, арбитр. Без этого арбитр не разрешит «overengineering vs design choice» и «contradicts rule».
- **Кеш свода правил.** Свод кешируется в корне main worktree — `<main-worktree>/.rules-cache/<scope-key>.md` (НЕ в `<reviews-dir>` и НЕ в текущем worktree, чтобы переживать снос временных worktree и переиспользоваться между ними) — и переиспользуется, пока совпадают TTL (потолок 7 дней) и **отпечаток источников** (`git hash-object` каждого файла правил + состав списка). Отпечаток — основной механизм инвалидации (ловит правки раньше TTL), TTL — лишь потолок. Кеш ключуется по затронутым подпроектам (свод backend ≠ свод frontend). Поиск источников (Шаг 1.1) выполняется всегда; пропускаются при cache hit только дорогие Шаги 1.2–1.4. Ошибка чтения/записи кеша не валит скилл — это оптимизация, а не зависимость.
- **Никаких вопросов перед ревью.** После сбора скоупа и свода скилл показывает свод информационно (Шаг 1.6) и сразу запускает Фазу 2 — без подтверждающего вопроса.
- **Memory-правила пользователя** прокидывай в промпты всех агентов (особенно правила про события, кросс-модульные взаимодействия, стиль документов, баланс «фикс грязи vs оверкилл»).
- **Стиль финального отчёта** — соответствуй уже существующим в репо (если в `docs/reviews/` лежат файлы — посмотри их шапку и используй похожий формат, но в пределах структуры, заданной выше).
- **Критик не делает ревью.** Если критик в файле критики добавил «нашёл ещё одну проблему» — арбитр игнорирует этот пункт. Это указано в обоих промптах.
- **Арбитр не делает ревью.** Может добавить пункт только при фактчеке, если упустить нельзя — высокий порог.
- **При detached HEAD / отсутствии git** — сообщи пользователю и не запускай.
- **Worktree-aware финал.** Если скилл запущен из вторичного git worktree — финальный отчёт (`<branch>-review.md`) дополнительно копируется в main worktree по тому же относительному пути (см. Фаза 6, шаг 2). Промежуточные `*-draft.md` и `*-critique.md` остаются только в текущем worktree. Ошибка копирования не валит скилл — главное, чтобы локальный финал существовал.
- **Когда применять этот скилл:** когда ожидается много спорных/субъективных замечаний (рефакторинги, новый функционал в чувствительной зоне, ревью по большому diff) и важно отсеять оверкилл за счёт явной фазы оспаривания (критик) и арбитража. Если не уверен, какой тир состязательного ревью подходит под конкретный дифф, — запусти `adversarial-review-auto`, он подберёт и запустит подходящий тир автоматически.
