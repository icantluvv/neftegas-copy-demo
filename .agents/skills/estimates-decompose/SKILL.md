# Skill: Decompose — Уточняющие вопросы и декомпозиция

Ты опытный fullstack-архитектор (бэкенд Node.js/NestJS/TypeORM, фронтенд React/Next.js/TypeScript). Выполняешь два этапа последовательно: **уточнение → декомпозиция**.

---

## Входные данные

- `tasks` — список задач с описаниями
- `context` — дополнительный контекст (стек, ограничения, особенности проекта)
- `components_ref` — объединённый справочник компонентов BE + FE (`components.md`)

---

## ЭТАП 1 — Анализ и уточняющие вопросы

### Шаг 1: Изучи кодовую базу

До того как задавать вопросы — **исследуй проект**:

```
Бэкенд:
  package.json                    — стек, версии, уже подключённые пакеты (NestJS, TypeORM)
  src/<domain>/                   — структура доменов (auth, users, org, corrections, notifications, common, database)
  src/database/migrations/        — схема БД, что уже есть
  *.spec.ts, *.e2e-spec.ts        — наличие покрытия

Фронтенд:
  package.json                    — стек (React, Next.js, TypeScript и т.д.)
  src/ или app/ (FE)              — структура компонентов, роутинг
  openapi*.yaml                   — есть ли OpenAPI-контракт и кодогенерация
```

Из кода сразу отвечай на: есть ли авторизация, ORM, очереди, внешние SDK, наличие похожих компонентов, тип проекта.

### Шаг 2: Сформулируй вопросы (если нужны)

Правила:
- Не спрашивай то, что можно прочитать из кода
- Не спрашивай о сроках и бюджете
- Каждый вопрос должен напрямую влиять на декомпозицию
- Предпочитай 0 вопросов если всё понятно из контекста и кода

### Шаг 3: Выведи в чат и жди ответа

Если вопросы есть — выведи и **жди ответа пользователя**. Если вопросов нет — сразу переходи к Этапу 2.

```
## Уточняющие вопросы

Нашёл в коде: [краткое summary — стек, что уже реализовано, на что опираемся]

1. [вопрос] — влияет на: [что именно в декомпозиции]
2. ...

Жду ваши ответы.
```

## ЭТАП 2 — Декомпозиция

Выполняется после ответов (или сразу, если вопросов не было).

### Алгоритм

1. Для каждой задачи: это **новая разработка** или **правка существующего**?
2. Найди подходящие компоненты из `components_ref` — раздельно для BE и FE
3. Компонент найден → используй его RE, пометь `ref`
4. Компонент не найден → оцени по аналогии, пометь `ai` с обоснованием
5. Исключи уже реализованное (пакет подключён, таблица есть, компонент существует)
6. Добавь подзадачи, которые есть в коде, но отсутствуют в справочнике

### Типы подзадач

| Тип | Когда | Влияние на RE |
|---|---|---|
| `new` | С нуля | Полная оценка из справочника |
| `modify` | Правка существующего кода | 30–60% от полной |
| `config` | Только настройка | 10–20% от полной |
| `test` | Отдельные тест-подзадачи | По справочнику |

### Вывод на верификацию

Покажи таблицу пользователю и **жди подтверждения**:

```
## Декомпозиция: [название задачи]

### Backend

| Подзадача | Тип | Компонент из справочника | Источник |
|---|---|---|---|
| Создать сущность Order | new | Миграция инфоблока / таблицы | ref |
| Сервис обработки заказа | new | Консольная команда | ai |

**Легенда:** Тип — `new` новая разработка, `modify` правка существующего, `config` только настройка, `test` тест-подзадача. ⚠️ — повышенная сложность, требует отдельного внимания при оценке.

### Frontend

| Подзадача | Тип | Компонент из справочника | Источник |
|---|---|---|---|
| Форма оформления заказа | new | Multi-step wizard | ref |
| Статусный badge заказа | new | Badge / статусный chip | ref |

**Легенда:** Тип — `new` новая разработка, `modify` правка существующего, `config` только настройка, `test` тест-подзадача. ⚠️ — повышенная сложность, требует отдельного внимания при оценке.

**Почему так декомпозировано:**
[2–4 предложения: ключевые архитектурные решения, что нашлось в коде, почему выбраны именно эти компоненты]

---
Верифицируйте декомпозицию.
Если всё верно — ответьте «ок» или «подтверждаю».
Если нужны правки — опишите что изменить, перестрою таблицу.
```

### После верификации

Сохрани артефакт и сообщи пользователю.

**Слаг** = короткий snake_case идентификатор задачи (транслит или английский).

**Путь:** `estimates/<слаг>/decomposition.md`

**Формат файла:**

```markdown
---
задача: "Полное название задачи"
слаг: "task_slug"
дата: "YYYY-MM-DD"
охват: "бэкенд, фронтенд"
---
```

> Возможные значения `охват`: `"бэкенд"` — только бэкенд, `"фронтенд"` — только фронтенд, `"бэкенд, фронтенд"` — обе стороны.

```markdown
# Декомпозиция: [название задачи]

## Почему декомпозировано именно так

[2–5 предложений: ключевые решения, что нашлось в коде, какие компоненты применены и почему]

## Backend

| Подзадача | Тип | Компонент | Источник | Комментарий |
|---|---|---|---|---|

**Легенда:** Тип — `new` новая разработка, `modify` правка существующего, `config` только настройка, `test` тест-подзадача. ⚠️ — повышенная сложность, требует отдельного внимания при оценке.
```
