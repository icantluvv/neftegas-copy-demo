# Backend Arch Check для Codex

Цель: проверить NestJS/TypeScript backend-изменения только на соответствие явным архитектурным правилам backend-документов. Это не общее ревью и не запуск тестов.

## Жесткие правила

- Не меняй код. По умолчанию результат - отчет в ответе; файл создавай только если пользователь явно попросил сохранить отчет.
- Проверяй только `apps/backend/**`.
- Источник правил - только документы, прочитанные при текущем запуске:
  - `apps/backend/AGENTS.md`;
  - `AGENTS.md` (корневой, кросс-контурные правила и бизнес-правила согласования);
  - документы, на которые прямо ссылается `apps/backend/AGENTS.md`, только если они нужны для конкретного правила.
- Не флагай "best practices", если нет точной цитаты правила из источника.
- Если не можешь привести буквальную цитату правила, нарушения нет.
- Не запускай `npm test`, `npm run lint`, `npm run test:e2e` и другие проверки, если пользователь отдельно не попросил.
- Не используй субагентов: это точечная read-only проверка.

## Инструменты Codex

- План: `update_plan`, если проверка больше одного-двух файлов.
- Поиск файлов: `rg --files`, `rg`, при необходимости `find`.
- Чтение: `sed -n`, `git diff`, `git show`.
- Отчет в файл, если явно нужен: `apply_patch`.
- Не используй Python для простого чтения/записи.

## Когда применять

Применяй skill, если пользователь просит:

- "проверь архитектуру";
- "арх-чек";
- "`backend-arch-check`";
- проверить PR/ветку/коммит/файлы на соответствие backend-архитектуре;
- проверить TypeScript-файлы под `apps/backend/src/<domain>/` (`auth`, `users`, `org`, `corrections`, `notifications`, `common`, `database`).

Если аргументов нет, спроси, что проверять. Не запускай проверку по всему backend по умолчанию.

## Режимы scope

- `files <path...>` - проверить указанные файлы или папки рекурсивно.
- `commit <ref-or-range>` - проверить измененные backend-файлы из ref/range.
- `branch` - проверить текущую ветку относительно `main...HEAD`.
- `staged` - проверить staged изменения.
- Если пользователь дал path/ref без режима, выбери режим по виду аргумента.

Команды из корня монорепо:

```bash
git diff --name-only <ref-or-range> -- 'apps/backend/src/**/*.ts'
git diff --name-only --cached -- 'apps/backend/src/**/*.ts'
git diff --name-only main...HEAD -- 'apps/backend/src/**/*.ts'
```

Для `files` разворачивай директории через `rg --files <dir>` и фильтруй.

## Фильтрация файлов

Проверяй:

- `apps/backend/src/**/*.ts` (кроме `*.spec.ts`, `*.e2e-spec.ts`).

Пропускай:

- удаленные файлы;
- файлы вне `apps/backend`;
- тесты, миграции и другие backend-файлы, если для них нет применимого правила в источниках.

Если после фильтрации файлов нет, кратко сообщи и заверши.

## Алгоритм

1. Определи scope и список файлов.
2. Прочитай источники правил целиком при каждом запуске:
   - `apps/backend/AGENTS.md`;
   - `AGENTS.md` (корневой).
3. Извлеки только проверяемые правила.
4. Прочитай каждый проверяемый файл целиком, а не только diff.
5. Сопоставь полный файл с проверяемыми правилами.
6. Для cross-file правил точечно ищи соседние файлы через `rg`/`rg --files`; не сканируй весь репозиторий без причины.
7. Сформируй отчет.

## Что считать проверяемым правилом

Правило проверяемо, если оно:

- сформулировано императивно: "должен", "обязан", "запрещено", "нельзя", "только через", "единственный способ";
- закреплено таблицей naming/структуры/событий/слоев;
- закреплено схемой файловой структуры;
- дано через пример с явной маркировкой "правильно", "неправильно", "запрещено", "required".

Игнорируй:

- рекомендации "лучше", "обычно", "по возможности";
- roadmap/future triggers;
- разделы "Что отвергнуто" и "Требует проработки";
- общие рассуждения без обязательного правила.

## Строгость

- Документы правил перечитывай при каждом запуске.
- Файлы читай целиком. Diff нужен только для scope и строк отчета.
- Цитата правила обязательна и должна быть точной.
- В каждом нарушении указывай раздел документа.
- Один файл + одно правило = одна запись, не дублируй по строкам.
- Не смешивай архитектурные нарушения с ESLint/tsc/test failures.

## Формат отчета

Если есть нарушения:

```markdown
# Backend arch check - <mode/scope>

Проверено файлов: N
Источник правил: `apps/backend/AGENTS.md`[, `AGENTS.md`]

## Нарушения

### <короткая формулировка правила>
- **Файл:** `apps/backend/src/corrections/services/correction.service.ts:42`
- **Источник правила:** `apps/backend/AGENTS.md` -> раздел "<точное название>"
- **Цитата правила:** "<буквальная цитата>"
- **Что не так:** <конкретный факт в коде>
- **Как исправить:** <одна конкретная подсказка>

## Без нарушений
- `apps/backend/src/...`
```

Если нарушений нет:

```markdown
# Backend arch check - <mode/scope>

Проверено файлов: N. Нарушений не найдено.
Источник правил: `apps/backend/AGENTS.md`[, `AGENTS.md`]

- `apps/backend/src/...`
```

## Если пользователь просит сохранить отчет

Сохраняй в `apps/backend/docs/reviews/` или ближайшую существующую папку `reviews`.
Имя файла: `backend-arch-check-YYYY-MM-DD.md` или `<branch>-backend-arch-check.md`, если проверяется ветка.
