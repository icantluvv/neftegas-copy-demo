## Why

`docs/tz/filial-cabinet.md` (раздел 0.3) держал вопрос «можно ли менять тип
корректировки в статусе «Черновик»?» открытым и явно запрещал проектировать
`/corrections/[id]/edit` до ответа заказчика. Ответ получен: менять тип
разрешено, маршрут нужен. До этого change у филиала не было способа
исправить ошибочно выбранный при создании тип корректировки иначе как
удалить черновик и создать заново (что тоже возможно, но теряет уже
загруженные в общий слот «Excel корректировка» файлы).

## What Changes

- Новый маршрут `/corrections/[humanId]/edit` — форма с единственным полем
  «Тип корректировки» (тот же список и `Select`, что на `/corrections/create`),
  доступна только автору корректировки (роль FILIAL) и только пока статус
  корректировки — `DRAFT`. При любой другой роли/статусе/чужой корректировке
  — экран «Доступ запрещён», как и при прямом вводе адреса.
- Ссылка «Изменить тип» на карточке корректировки (`correction-header.tsx`),
  видна на тех же условиях, что и доступ к странице.
- Новый backend-эндпоинт `POST /corrections/{humanId}/change-type`: роль
  FILIAL, только автор/владелец, только статус `DRAFT` (иначе `400`,
  идентично guard'у `deleteCorrection`), новый `correctionTypeId` должен
  существовать (иначе `404`).
- Слоты пакета, привязанные к прежнему типу (`requirementId != null`),
  удаляются вместе с уже загруженными в них версиями файлов (физические
  файлы — с диска, тем же способом, что в `deleteCorrection`); для нового
  типа слоты создаются заново тем же алгоритмом, что при создании
  корректировки (`create()`). Общий слот «Excel корректировка»
  (`requirementId == null`) от типа не зависит и не затрагивается — его уже
  загруженные версии сохраняются.
- Смена типа на тот же самый — не операция: эндпоинт возвращает текущую
  карточку без изменений в БД и без удаления файлов.

## Capabilities

### New Capabilities

- `correction-type-edit`: доступ к форме смены типа корректировки, её
  единственное поле и guard-условия (кто видит, когда доступно), последствия
  смены типа для слотов пакета и уже загруженных файлов.

### Modified Capabilities

(нет — существующие capability корректировок не меняют текст требований,
новое поведение полностью описывается новой capability)

## Impact

- **Frontend**: новый маршрут
  `apps/frontend/app/(private)/corrections/[humanId]/edit/page.tsx` +
  `components/edit-correction-type-form.tsx`; ссылка «Изменить тип» добавлена
  в `apps/frontend/app/(private)/corrections/[humanId]/components/correction-header.tsx`.
- **Backend**: `apps/backend/src/corrections/dto/update-correction-type.dto.ts`
  (новый), `corrections.service.ts` (`updateCorrectionType`),
  `corrections.controller.ts` (`POST :humanId/change-type`).
- **API-контракт**: новая схема `CorrectionTypeChangeInput`
  (`api/src/components/schemas/correction.yaml`), новый путь
  `POST /corrections/{humanId}/change-type`
  (`api/src/paths/corrections-human-id-change-type.yaml`), зарегистрирован в
  `api/src/openapi.yaml`. Kubb-клиент перегенерирован
  (`useChangeCorrectionType` и сопутствующие типы/моки/zod-схемы).
- **Обратная совместимость**: аддитивное изменение контракта, существующие
  эндпоинты не затронуты.

## Влияние на качество

- Уровень риска: **P1** — необратимая потеря данных (уже загруженных версий
  файлов в слотах прежнего типа) при ошибочном выборе нового типа; смягчено
  тем, что действие доступно только в `DRAFT` (до направления на проверку,
  когда потеря файлов ещё не имеет внешних последствий) и предупреждением в
  форме.
- Затронутые маршруты: `/corrections/[humanId]/edit` (новый).
- Затронутые frontend-компоненты: `EditCorrectionTypeForm` (новый),
  `CorrectionHeader` (добавлена условная ссылка).
- Затронутые backend-модули: `corrections` (новый метод сервиса и роут
  контроллера, без изменений существующих).
- Затронутые API: `POST /corrections/{humanId}/change-type` (новый).
- TDD-порядок: не соблюдён — реализация велась по коду напрямую (research
  существующего `create()`/`deleteCorrection()` как образца, затем
  реализация по аналогии), без предварительных падающих тестов; тестов на
  момент фиксации change нет — см. `test-plan.md`.
- Обязательные уровни проверки: Backend Unit/Feature (guard-условия,
  реконсиляция слотов, no-op при том же типе), Frontend Component (форма:
  disabled-состояния, guard страницы), Frontend E2E (happy path смены типа).
- Ручные проверки: подтверждены прямыми HTTP-запросами (`curl`) под демо-
  аккаунтом `filial.donbassgaz@demo.local` — смена на тот же тип (no-op,
  корректировка не изменилась), несуществующий тип (`404`), смена типа у
  корректировки не в `DRAFT` (`400`). Проверка реальной реконсиляции слотов
  между двумя РАЗНЫМИ типами не выполнена — в демо-сиде существует только
  один активный `CorrectionType` («Стандартная корректировка»); требуется
  ручная или автоматизированная проверка после появления второго типа в
  сиде/тестовых фикстурах. `tsc --noEmit` — чисто на обоих контурах,
  `redocly lint` — валиден (без новых ошибок сверх уже существовавших 44
  pre-existing warnings по всему контракту).
- План отката: новый маршрут и новый эндпоинт аддитивны, ссылка в шапке
  условна — откат равносилен revert соответствующих коммитов без обратных
  миграций БД.
