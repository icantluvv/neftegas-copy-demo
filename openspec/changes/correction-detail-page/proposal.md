## Why

Бэкенд и API-контракт корректировок (`GET /corrections/{humanId}` → `CorrectionDetail`,
загрузка версий в слоты, направление, согласование/возврат ЦФО и ДТОиР, замечания,
повторное направление, история) уже полностью реализованы в `apps/backend/src/corrections/`
и `api/src/openapi.yaml`, но фронтенд не предоставляет ни одного экрана для работы с этими
данными — карточки корректировки в UI не существует. Без неё три роли (Филиал, ЦФО, ДТОиР)
не могут выполнить ни одно действие жизненного цикла корректировки через интерфейс.

## What Changes

- Добавляется общая для всех ролей страница `/corrections/[id]` (App Router, приватный
  контур), отображающая карточку корректировки по человекочитаемому ID (`COR-000001`).
- Набор видимых блоков и доступных действий на странице определяется ролью текущего
  пользователя и полями `isFilialOwner` / `isCfoReviewer` / `isDtoe`, `myCfoStatus`,
  статусом корректировки, полученными из `CorrectionDetail`.
- Блок «Шапка корректировки»: филиал, ID, тип, статус (бейдж), этап, автор, даты.
- Блок «Комплектность пакета»: чеклист слотов с загрузкой новой версии файла в
  конкретный слот (Филиал, пока корректировка не в финальном статусе); если у слота
  есть открытое замечание — после загрузки предлагается сразу отметить его исправленным.
- Блок «Статусы ЦФО»: независимые статусы согласования по каждому направленному ЦФО,
  read-only.
- Блок «Замечания»: список замечаний с действиями «Отметить исправленным» (Филиал,
  собственные корректировки) и «Удалить» (автор замечания, только статус `OPEN`);
  оставление нового замечания выполняется как часть действия «Вернуть на доработку»
  (ЦФО/ДТОиР), отдельной формы создания замечания вне возврата не вводится.
- Блок «Повторное направление»: чекбоксы по вернувшим ЦФО (только из `returnedCfos`) и
  кнопка «Перенаправить», активная только когда отмечен хотя бы один ЦФО и все его
  замечания в статусе `FIXED_BY_FILIAL`; блок скрыт, если `returnedCfos` пуст.
- Блок «История действий»: read-only лог из `history`.
- Действия направления («Направить», «Направить в ДТОиР», «Согласовать», «Вернуть на
  доработку», финальное согласование ДТОиР) вызывают существующие эндпоинты
  `POST /corrections/{humanId}/send|resubmit|send-to-dtoe|resubmit-to-dtoe|cfo-approve|
  cfo-return|dtoe-approve|dtoe-return`.
- Изменений API-контракта не требуется — используется существующий Kubb-клиент,
  сгенерированный из действующего `api/src/openapi.yaml`.

## Capabilities

### New Capabilities

- `correction-detail-page`: ролевое поведение общей страницы карточки корректировки —
  какие блоки видны, какие действия доступны и при каких условиях (guard), в
  зависимости от роли пользователя и статуса корректировки/ЦФО/замечаний.

### Modified Capabilities

(нет — используется существующий API-контракт без изменений)

## Impact

- **Frontend**: новый маршрут `apps/frontend/app/(private)/corrections/[id]/`, новые
  компоненты блоков карточки (шапка, комплектность пакета, статусы ЦФО, замечания,
  повторное направление, история), TanStack Query-хуки поверх сгенерированного Kubb-
  клиента для `GET /corrections/{humanId}` и мутаций жизненного цикла корректировки/
  замечаний/загрузки файлов.
- **Backend**: не затрагивается — все нужные эндпоинты (`corrections.controller.ts`,
  `corrections.service.ts`) и правила уже реализованы и покрыты бизнес-логикой согласно
  «Статусной модели корректировки» в `apps/backend/AGENTS.md`.
- **API-контракт**: не затрагивается — `api/src/openapi.yaml` и `CorrectionDetail`/
  `Remark`/связанные схемы уже содержат все поля, необходимые странице (`slots`,
  `cfoStatuses`, `remarks`, `history`, `isFilialOwner`, `isCfoReviewer`, `isDtoe`,
  `myCfoStatus`, `availableCfos`, `returnedCfos`, `packageComplete`,
  `missingRequirements`).
- **Зависимости**: используется существующий `sidebar-nav` и layout приватного контура
  (`apps/frontend/app/(private)/`), появившиеся в `sidebar-nav-and-role-dashboard`.

## Влияние на качество

- Уровень риска: **P0** — экран управляет всеми переходами жизненного цикла
  корректировки для трёх ролей; ошибка в guard-условиях на фронте не ломает бэкенд
  (защита атомарна на бэкенде), но ломает основной рабочий процесс пользователей.
- Затронутые маршруты: `/corrections/[id]` (новый).
- Затронутые frontend-компоненты: новые компоненты блоков карточки корректировки,
  TanStack Query-хуки для `corrections`-домена.
- Затронутые backend-модули: нет (только потребление существующего API).
- Затронутые API: `GET /corrections/{humanId}`, `POST /corrections/{humanId}/slots/
  {slotId}/files`, `.../send`, `.../resubmit`, `.../send-to-dtoe`, `.../resubmit-to-dtoe`,
  `.../cfo-approve`, `.../cfo-return`, `.../dtoe-approve`, `.../dtoe-return`,
  `.../remarks/{remarkId}/fix`, `.../remarks/{remarkId}` (DELETE) — все существующие,
  без изменений контракта.
- TDD-порядок: failing test (component/E2E по сценарию из spec) → минимальная
  реализация блока → green → refactor.
- Обязательные уровни проверки: Frontend Unit (форматирование дат/статусов, вычисление
  видимости блоков по роли), Frontend Component (каждый блок карточки — рендер и
  guard-условия кнопок), Frontend E2E (ключевые маршруты: Филиал направляет пакет; ЦФО
  согласовывает/возвращает; ДТОиР финально согласовывает).
- Ручные проверки: визуальная сверка макета цветных бейджей статусов (скриншот
  референса) — waiver на автоматизацию визуального сравнения, см. `test-plan.md`.
- План отката: страница нового маршрута удаляется/скрывается независимо от бэкенда и
  других страниц; feature flag не требуется, так как маршрут ранее не существовал и не
  имеет входящих ссылок вне сайдбара, добавляемых этим же change.
