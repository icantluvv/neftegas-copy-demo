## Purpose

Единая для трёх ролей (Филиал, ЦФО, ДТОиР) страница карточки корректировки по адресу
`/corrections/[id]`, на которой пользователь видит состояние пакета документов и
выполняет доступные его роли и текущему статусу действия жизненного цикла
корректировки.

## ADDED Requirements

### Requirement: Доступ к карточке корректировки
Система SHALL открывать карточку корректировки по человекочитаемому ID только
пользователю, имеющему право её видеть: автору-филиалу, любому ЦФО, связанному с
корректировкой через направление, и любому пользователю роли ДТОиР (аудит всех
корректировок).

#### Scenario: Филиал открывает свою корректировку
- **WHEN** пользователь роли «Филиал» открывает `/corrections/COR-000001`, и корректировка создана его филиалом
- **THEN** система отображает карточку корректировки

#### Scenario: ДТОиР открывает любую корректировку в рамках аудита
- **WHEN** пользователь роли «ДТОиР» открывает `/corrections/COR-000001` любого филиала
- **THEN** система отображает карточку корректировки

#### Scenario: Пользователь без доступа не может открыть чужую карточку
- **WHEN** пользователь роли «Филиал» открывает корректировку другого филиала
- **THEN** система отклоняет запрос с кодом 403 и не отображает содержимое карточки

#### Scenario: Запрос несуществующей корректировки
- **WHEN** пользователь открывает `/corrections/COR-999999`, и такой корректировки не существует
- **THEN** система отображает состояние «не найдено»

### Requirement: Блок «Шапка корректировки»
Система SHALL отображать в шапке карточки филиал-автора, ID, тип корректировки,
текущий статус в виде цветного бейджа, текстовую расшифровку статуса (этап), автора и
даты создания/последнего изменения.

#### Scenario: Шапка отображается всем ролям одинаково
- **WHEN** любой пользователь с доступом к карточке открывает её
- **THEN** система отображает филиал, ID, тип, статус, этап, автора и даты создано/изменено

### Requirement: Комплектность пакета и загрузка версии файла
Система SHALL отображать для каждого обязательного и опционального слота типа
корректировки: название элемента, признак обязательности, проверяющее подразделение
(конкретный ЦФО или «все ЦФО маршрута») и текущую версию файла с номером, ссылкой на
скачивание, автором и временем загрузки.

Система SHALL позволять пользователю роли «Филиал» — автору корректировки — загрузить
новую версию файла в конкретный слот, пока корректировка не находится в статусе
`APPROVED_BY_DTOE`; каждая загрузка создаёт новую версию с номером на единицу больше
предыдущей и не изменяет и не удаляет предыдущие версии.

Система SHALL, если в момент загрузки по слоту есть открытое замечание, связывать
новую версию с этим замечанием и предлагать пользователю сразу отметить замечание
исправленным.

#### Scenario: Филиал загружает первую версию файла в пустой слот
- **WHEN** филиал-автор выбирает файл для слота без загруженных версий
- **THEN** система создаёт версию номер 1 и отображает её как текущую

#### Scenario: Филиал загружает исправленную версию по открытому замечанию
- **GIVEN** слот содержит версию 1, и по слоту есть открытое замечание
- **WHEN** филиал-автор загружает новый файл в этот слот
- **THEN** система создаёт версию номер 2, связывает её с замечанием и предлагает отметить замечание исправленным

#### Scenario: Загрузка недоступна после финального согласования
- **WHEN** корректировка находится в статусе `APPROVED_BY_DTOE`
- **THEN** система не позволяет загрузить новую версию ни в один слот

#### Scenario: ЦФО и ДТОиР не могут загружать файлы
- **WHEN** пользователь роли «ЦФО» или «ДТОиР» открывает карточку корректировки
- **THEN** система не отображает кнопку загрузки версии файла ни в одном слоте

### Requirement: Направление корректировки на проверку
Система SHALL позволять филиалу-автору направить корректировку в статусе `DRAFT`
выбранным ЦФО из числа связанных с его филиалом, только когда все обязательные слоты
содержат хотя бы одну версию файла.

#### Scenario: Направление недоступно при незаполненных обязательных слотах
- **GIVEN** корректировка в статусе `DRAFT`, и хотя бы один обязательный слот не содержит ни одной версии файла
- **WHEN** филиал-автор открывает карточку
- **THEN** кнопка «Направить» неактивна

#### Scenario: Успешное направление выбранным ЦФО
- **GIVEN** корректировка в статусе `DRAFT`, и все обязательные слоты заполнены
- **WHEN** филиал-автор выбирает один или несколько ЦФО из списка связанных с филиалом и направляет корректировку
- **THEN** корректировка переходит в статус `UNDER_CFO_REVIEW`
- **AND** каждый выбранный ЦФО получает независимый статус `PENDING`

### Requirement: Отображение статусов ЦФО
Система SHALL отображать для каждого направленного ЦФО его независимый статус
(«Ожидает» / «Согласовано» / «Возвращено»), а если решение принято — кто и когда его
принял. Блок SHALL быть доступен только для чтения независимо от роли просматривающего
пользователя.

#### Scenario: Филиал видит статусы ЦФО без возможности их менять
- **WHEN** филиал-автор открывает карточку корректировки с несколькими направленными ЦФО
- **THEN** система отображает статус каждого ЦФО
- **AND** не отображает ни одного элемента управления в этом блоке

### Requirement: Согласование корректировки ЦФО
Система SHALL позволять пользователю проверяющего ЦФО согласовать корректировку, только
если статус этого ЦФО по корректировке равен `PENDING`.

#### Scenario: ЦФО согласовывает корректировку
- **GIVEN** статус пользователя-ЦФО по корректировке — `PENDING`
- **WHEN** пользователь согласовывает корректировку
- **THEN** статус этого ЦФО переходит в `APPROVED`
- **AND** статусы остальных направленных ЦФО не изменяются

#### Scenario: Повторное согласование недоступно
- **GIVEN** статус пользователя-ЦФО по корректировке уже `APPROVED` или `RETURNED`
- **WHEN** пользователь открывает карточку корректировки
- **THEN** кнопка «Согласовать» неактивна для этого ЦФО

### Requirement: Возврат корректировки с замечанием
Система SHALL позволять пользователю проверяющего ЦФО или ДТОиР вернуть корректировку
на доработку вместе с созданием замечания к конкретному элементу пакета, только когда
корректировка находится у него на рассмотрении (для ЦФО — его статус `PENDING`; для
ДТОиР — статус корректировки `UNDER_DTOE_REVIEW`).

#### Scenario: ЦФО возвращает корректировку с замечанием к элементу
- **GIVEN** статус пользователя-ЦФО по корректировке — `PENDING`
- **WHEN** пользователь оставляет замечание к элементу пакета и указывает описание и требуемое действие
- **THEN** создаётся новое замечание в статусе `OPEN`, привязанное к этому элементу и к этому ЦФО
- **AND** статус корректировки переходит в `RETURNED_FOR_REVISION`
- **AND** статус этого ЦФО переходит в `RETURNED`

#### Scenario: ДТОиР возвращает корректировку с замечанием
- **GIVEN** корректировка в статусе `UNDER_DTOE_REVIEW`
- **WHEN** пользователь ДТОиР оставляет замечание к элементу пакета
- **THEN** создаётся новое замечание в статусе `OPEN`, привязанное к этому элементу, с автором ДТОиР
- **AND** статус корректировки переходит в `RETURNED_BY_DTOE`

#### Scenario: Второй проверяющий не может отправить решение поверх уже принятого
- **GIVEN** два ЦФО одновременно открыли карточку корректировки в статусе `PENDING`, и один уже согласовал или вернул её
- **WHEN** второй ЦФО пытается согласовать или вернуть эту же корректировку
- **THEN** система отклоняет действие, так как статус этого ЦФО уже не `PENDING`

### Requirement: Отметка замечания исправленным
Система SHALL позволять филиалу-автору отметить собственное замечание исправленным;
это действие переводит замечание в статус `FIXED_BY_FILIAL` и не закрывает его
окончательно — окончательное закрытие выполняет проверяющий при повторном
согласовании.

#### Scenario: Филиал отмечает замечание исправленным
- **GIVEN** замечание к корректировке филиала в статусе `OPEN`
- **WHEN** филиал-автор нажимает «Отметить исправленным»
- **THEN** статус замечания переходит в `FIXED_BY_FILIAL`

#### Scenario: Замечание в финальном статусе нельзя отметить повторно
- **GIVEN** замечание в статусе `CLOSED`
- **WHEN** филиал-автор открывает карточку корректировки
- **THEN** кнопка «Отметить исправленным» для этого замечания недоступна

### Requirement: Удаление замечания
Система SHALL позволять удалить замечание только его автору и только пока замечание
находится в статусе `OPEN`, независимо от роли автора.

#### Scenario: Автор удаляет собственное открытое замечание
- **GIVEN** замечание в статусе `OPEN`, оставленное текущим пользователем
- **WHEN** пользователь удаляет это замечание
- **THEN** замечание удаляется из карточки корректировки

#### Scenario: Нельзя удалить чужое замечание
- **GIVEN** замечание в статусе `OPEN`, оставленное другим пользователем
- **WHEN** текущий пользователь открывает карточку корректировки
- **THEN** кнопка удаления для этого замечания не отображается

#### Scenario: Нельзя удалить замечание не в статусе OPEN
- **GIVEN** замечание в статусе `FIXED_BY_FILIAL` или `CLOSED`, оставленное текущим пользователем
- **WHEN** пользователь открывает карточку корректировки
- **THEN** кнопка удаления для этого замечания не отображается

### Requirement: Повторное направление вернувшим ЦФО
Система SHALL отображать блок повторного направления только когда есть хотя бы один
ЦФО в статусе `RETURNED`, и SHALL предлагать в списке выбора только такие ЦФО.

Система SHALL разрешать повторное направление, только когда отмечен хотя бы один ЦФО
из списка и все замечания от каждого выбранного ЦФО находятся в статусе
`FIXED_BY_FILIAL`.

Система SHALL NOT сбрасывать статус ЦФО, ранее согласовавших корректировку, при
повторном направлении другим ЦФО.

#### Scenario: Блок скрыт, если ни один ЦФО не возвращал пакет
- **GIVEN** ни один ЦФО не находится в статусе `RETURNED`
- **WHEN** филиал-автор открывает карточку корректировки
- **THEN** блок «Повторное направление» не отображается

#### Scenario: Кнопка неактивна, пока остались открытые замечания
- **GIVEN** есть ЦФО в статусе `RETURNED`, и хотя бы одно его замечание в статусе `OPEN`
- **WHEN** филиал-автор отмечает этого ЦФО в списке повторного направления
- **THEN** кнопка «Перенаправить» неактивна

#### Scenario: Кнопка неактивна, если не выбран ни один ЦФО
- **GIVEN** есть ЦФО в статусе `RETURNED`, и все его замечания в статусе `FIXED_BY_FILIAL`
- **WHEN** филиал-автор не отмечает ни один чекбокс
- **THEN** кнопка «Перенаправить» неактивна

#### Scenario: Успешное повторное направление
- **GIVEN** один ЦФО в статусе `RETURNED` со всеми замечаниями в статусе `FIXED_BY_FILIAL`, и второй ЦФО уже в статусе `APPROVED`
- **WHEN** филиал-автор отмечает вернувшего ЦФО и нажимает «Перенаправить»
- **THEN** статус корректировки переходит в `RESUBMITTED`
- **AND** статус отмеченного ЦФО переходит в `PENDING`
- **AND** статус ранее согласовавшего ЦФО остаётся `APPROVED`

### Requirement: Направление в ДТОиР
Система SHALL позволять направить корректировку в ДТОиР любому согласовавшему её ЦФО,
только когда все обязательные ЦФО находятся в статусе `APPROVED`. Кнопка направления
SHALL становиться доступной сразу всем согласовавшим ЦФО, как только последний
обязательный ЦФО согласовал.

#### Scenario: Кнопка появляется у всех согласовавших ЦФО после последнего согласования
- **GIVEN** два обязательных ЦФО, оба в статусе `APPROVED`
- **WHEN** любой из этих ЦФО открывает карточку корректировки
- **THEN** кнопка «Направить в ДТОиР» активна

#### Scenario: Кнопка недоступна, пока не все обязательные ЦФО согласовали
- **GIVEN** один из двух обязательных ЦФО в статусе `PENDING`
- **WHEN** согласовавший ЦФО открывает карточку корректировки
- **THEN** кнопка «Направить в ДТОиР» неактивна

#### Scenario: Направление в ДТОиР закрывает связанные замечания
- **WHEN** согласовавший ЦФО направляет корректировку в ДТОиР
- **THEN** статус корректировки переходит в `UNDER_DTOE_REVIEW`
- **AND** замечания, связанные с этой корректировкой, переходят в статус `CLOSED`

### Requirement: Финальное согласование ДТОиР
Система SHALL позволять пользователю ДТОиР финально согласовать корректировку, только
когда она находится в статусе `UNDER_DTOE_REVIEW`.

#### Scenario: ДТОиР финально согласовывает корректировку
- **GIVEN** корректировка в статусе `UNDER_DTOE_REVIEW`
- **WHEN** пользователь ДТОиР согласовывает корректировку
- **THEN** статус корректировки переходит в `APPROVED_BY_DTOE`
- **AND** дата решения фиксируется

### Requirement: Повторное направление в ДТОиР
Система SHALL позволять филиалу-автору повторно направить в ДТОиР корректировку в
статусе `RETURNED_BY_DTOE`, только когда все замечания от ДТОиР находятся в статусе
`FIXED_BY_FILIAL`.

#### Scenario: Кнопка неактивна, пока остались открытые замечания ДТОиР
- **GIVEN** корректировка в статусе `RETURNED_BY_DTOE`, и хотя бы одно замечание ДТОиР в статусе `OPEN`
- **WHEN** филиал-автор открывает карточку корректировки
- **THEN** кнопка повторного направления в ДТОиР неактивна

#### Scenario: Успешное повторное направление в ДТОиР
- **GIVEN** корректировка в статусе `RETURNED_BY_DTOE`, и все замечания ДТОиР в статусе `FIXED_BY_FILIAL`
- **WHEN** филиал-автор повторно направляет корректировку в ДТОиР
- **THEN** статус корректировки переходит в `UNDER_DTOE_REVIEW`

### Requirement: Блок «История действий»
Система SHALL отображать в истории действий каждую значимую операцию по корректировке
с датой и временем с точностью до минуты, пользователем (ФИО, роль, подразделение) и
текстовым описанием действия, в хронологическом порядке.

Система SHALL NOT предоставлять ни одной роли, включая автора записи, возможность
редактировать или удалять запись истории.

#### Scenario: История доступна только для чтения всем ролям
- **WHEN** любой пользователь с доступом к карточке открывает блок «История действий»
- **THEN** система отображает список записей без элементов редактирования или удаления
