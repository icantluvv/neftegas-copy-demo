## ADDED Requirements

### Requirement: Создание корректировки ролью ЦФО

Система SHALL разрешать пользователю с ролью `CFO` создавать корректировку
(`POST /corrections`) наравне с ролью `FILIAL`. Созданная ЦФО корректировка
SHALL получать `initiatorKind = CFO`, `initiatorCfoId` равным `cfoId` автора,
и `filialId = null`. Система SHALL NOT позволять пользователю без `cfoId`
создавать корректировку от роли `CFO`.

#### Scenario: ЦФО создаёт корректировку

GIVEN пользователь с ролью `CFO` и заполненным `cfoId`
WHEN он отправляет `POST /corrections` с корректным `correctionTypeId`
THEN создаётся корректировка в статусе `DRAFT`
AND `initiatorKind` корректировки равен `CFO`
AND `initiatorCfoId` равен `cfoId` этого пользователя
AND `filialId` равен `null`

#### Scenario: Роль без организационной привязки не может создать корректировку

GIVEN пользователь с ролью `CFO`, у которого `cfoId` не заполнен
WHEN он отправляет `POST /corrections`
THEN сервер отвечает `403`
AND корректировка не создаётся

### Requirement: Направление корректировки филиалу(ам) или в ДТОиР ролью ЦФО

Система SHALL предоставлять эндпоинт `POST
/corrections/{humanId}/send-as-cfo`, доступный только автору
ЦФО-инициированной корректировки (`initiatorCfoId` равен `cfoId` вызывающего).
Система SHALL NOT разрешать направление, пока пакет документов не
укомплектован всеми обязательными слотами. При `target = FILIAL` система
SHALL создать по одной строке `CorrectionFilialStatus` со статусом `PENDING`
для каждого `filialId` из `filialIds` и перевести корректировку в статус
`UNDER_FILIAL_REVIEW`. При `target = DTOE` система SHALL перевести
корректировку в статус `UNDER_DTOE_REVIEW` напрямую, без предварительного
цикла согласования филиалами.

#### Scenario: ЦФО направляет корректировку нескольким филиалам

GIVEN корректировка с `initiatorKind = CFO`, `initiatorCfoId` равным `cfoId`
пользователя, в статусе `DRAFT`, со всеми обязательными слотами заполненными
WHEN автор отправляет `POST .../send-as-cfo` с `{ target: FILIAL, filialIds:
[F1, F2] }`
THEN для F1 и F2 создаются строки `CorrectionFilialStatus` со статусом
`PENDING`
AND статус корректировки становится `UNDER_FILIAL_REVIEW`
AND пользователи роли `FILIAL` филиалов F1 и F2 получают уведомление

#### Scenario: ЦФО направляет корректировку напрямую в ДТОиР

GIVEN корректировка с `initiatorKind = CFO`, `initiatorCfoId` равным `cfoId`
пользователя, в статусе `DRAFT`, со всеми обязательными слотами заполненными
WHEN автор отправляет `POST .../send-as-cfo` с `{ target: DTOE }`
THEN статус корректировки становится `UNDER_DTOE_REVIEW`
AND `targetKind` становится `DTOE`
AND пользователи роли `DTOE` получают уведомление
AND дальнейшее решение принимается существующими действиями «Согласовать
(ДТОиР)» / «Оставить замечание» (ДТОиР), без изменений их поведения

#### Scenario: Направление заблокировано при неукомплектованном пакете

GIVEN ЦФО-инициированная корректировка в статусе `DRAFT` без хотя бы одной
версии файла в обязательном слоте
WHEN автор отправляет `POST .../send-as-cfo`
THEN сервер отвечает `400` с перечнем недостающих элементов
AND статус корректировки не меняется

#### Scenario: Не-автор не может направить корректировку

GIVEN ЦФО-инициированная корректировка, где `initiatorCfoId` НЕ равен `cfoId`
вызывающего пользователя
WHEN этот пользователь отправляет `POST .../send-as-cfo`
THEN сервер отвечает `403`

### Requirement: Согласование корректировки филиалом-проверяющим

Система SHALL разрешать пользователю с ролью `FILIAL`, назначенному
проверяющим по ЦФО-инициированной корректировке (существует строка
`CorrectionFilialStatus` с его `filialId`), согласовывать
(`POST .../filial-approve`) её независимо от решений других назначенных
филиалов. Система SHALL NOT разрешать повторное согласование, если статус
этого филиала уже не `PENDING`.

#### Scenario: Филиал согласовывает корректировку

GIVEN корректировка в статусе `UNDER_FILIAL_REVIEW`
AND строка `CorrectionFilialStatus` для этого филиала в статусе `PENDING`
WHEN пользователь этого филиала отправляет `POST .../filial-approve`
THEN статус этой строки становится `APPROVED`
AND если все обязательные филиалы согласовали — статус корректировки
становится `ALL_FILIALS_APPROVED`
AND если согласовали не все — статус становится
`PARTIALLY_APPROVED_BY_FILIALS`

#### Scenario: Второй раз согласовать нельзя

GIVEN строка `CorrectionFilialStatus` для этого филиала уже в статусе
`APPROVED` или `RETURNED`
WHEN пользователь этого филиала повторно отправляет `POST .../filial-approve`
THEN сервер отвечает `400`
AND статус строки не меняется

### Requirement: Возврат корректировки филиалом-проверяющим с замечанием

Система SHALL разрешать пользователю с ролью `FILIAL`, назначенному
проверяющим по ЦФО-инициированной корректировке, оставлять замечания к
элементам пакета (`POST /corrections/{humanId}/remarks`, `remark.filialId`
равен `filialId` автора) без изменения статуса, и финализировать возврат
(`POST .../filial-return`) отдельным действием. Система SHALL NOT разрешать
финализировать возврат без хотя бы одного открытого замечания от этого
филиала.

#### Scenario: Филиал оставляет замечание и возвращает на доработку

GIVEN корректировка в статусе `UNDER_FILIAL_REVIEW`
AND строка `CorrectionFilialStatus` для этого филиала в статусе `PENDING`
WHEN пользователь этого филиала оставляет замечание к элементу пакета
AND затем отправляет `POST .../filial-return`
THEN статус строки `CorrectionFilialStatus` этого филиала становится
`RETURNED`
AND статус корректировки становится `RETURNED_FOR_REVISION_BY_FILIAL`
AND автор корректировки (ЦФО) получает уведомление со списком замечаний

#### Scenario: Нельзя вернуть без замечаний

GIVEN строка `CorrectionFilialStatus` для этого филиала в статусе `PENDING`
AND от этого филиала по этой корректировке нет ни одного замечания в статусе
`OPEN`
WHEN пользователь этого филиала отправляет `POST .../filial-return`
THEN сервер отвечает `400`
AND статус строки не меняется

### Requirement: Отмена решения филиала-проверяющего

Система SHALL разрешать пользователю с ролью `FILIAL`, назначенному
проверяющим, отменить собственное ранее принятое решение
(`POST .../cancel-filial-decision`), вернув статус его строки
`CorrectionFilialStatus` в `PENDING`, при условии что корректировка ещё не
передана в ДТОиР. Система SHALL NOT разрешать отмену решения, которое ещё не
принято, и отмену после передачи корректировки в ДТОиР.

#### Scenario: Филиал отменяет собственное решение

GIVEN строка `CorrectionFilialStatus` для этого филиала в статусе `APPROVED`
или `RETURNED`
AND корректировка ещё не в статусе `UNDER_DTOE_REVIEW`/`RETURNED_BY_DTOE`/
`APPROVED_BY_DTOE`
WHEN пользователь этого филиала отправляет `POST .../cancel-filial-decision`
THEN статус строки становится `PENDING`
AND статус корректировки пересчитывается по правилам согласования филиалов

#### Scenario: Нельзя отменить после передачи в ДТОиР

GIVEN корректировка в статусе `UNDER_DTOE_REVIEW`
WHEN филиал-проверяющий отправляет `POST .../cancel-filial-decision`
THEN сервер отвечает `400`

### Requirement: Повторное направление филиалам после доработки

Система SHALL разрешать автору ЦФО-инициированной корректировки повторно
направить её ранее вернувшим филиалам (`POST .../resubmit-to-filials`) —
только после того, как филиал отметил свои замечания исправленными. Успешное
повторное направление SHALL перевести статус вернувших филиалов обратно в
`PENDING` и статус корректировки — в `RESUBMITTED_TO_FILIALS`, не сбрасывая
решения филиалов, которые уже согласовали и не участвуют в повторном
направлении.

#### Scenario: ЦФО повторно направляет после исправления

GIVEN корректировка в статусе `RETURNED_FOR_REVISION_BY_FILIAL`
AND все замечания от вернувшего филиала в статусе `FIXED_BY_FILIAL`
WHEN автор-ЦФО отправляет `POST .../resubmit-to-filials` с `filialIds`,
включающим этот филиал
THEN статус строки `CorrectionFilialStatus` этого филиала становится
`PENDING`
AND статус корректировки становится `RESUBMITTED_TO_FILIALS`
AND статусы ранее согласовавших филиалов не изменяются

### Requirement: Видимость ЦФО-инициированных корректировок

Система SHALL включать в список корректировок пользователя с ролью `CFO`
(`GET /corrections`) как корректировки, где он проверяющий (существующее
поведение), так и корректировки, которые он создал сам
(`initiatorCfoId` равен его `cfoId`). Система SHALL включать в список
корректировок пользователя с ролью `FILIAL` как корректировки, которые
создал его филиал (существующее поведение), так и ЦФО-инициированные
корректировки, где его филиал назначен проверяющим.

#### Scenario: ЦФО видит созданные им корректировки в общем списке

GIVEN пользователь роли `CFO` создал корректировку с `initiatorKind = CFO`
WHEN он запрашивает `GET /corrections`
THEN эта корректировка присутствует в результате, даже если по ней ещё нет
ни одной строки `CorrectionCfoStatus`/`CorrectionFilialStatus` (черновик)

#### Scenario: Филиал видит ЦФО-инициированные корректировки, где он проверяющий

GIVEN ЦФО направил корректировку филиалу F (существует
`CorrectionFilialStatus` с `filialId = F`)
WHEN пользователь филиала F запрашивает `GET /corrections`
THEN эта корректировка присутствует в результате наравне с собственными
корректировками филиала F

### Requirement: ДТОиР как строка справочника ЦФО без изменения финального решения

Система SHALL хранить «ДТОиР» отдельной активной строкой в справочнике
`cfos`, доступной для отображения в интерфейсах, работающих со списком ЦФО.
Система SHALL NOT включать эту строку в связи `FilialCfoLink` и SHALL NOT
создавать по ней строки `CorrectionCfoStatus` в обычном цикле
филиал→ЦФО. Финальное решение по корректировке, направленной в ДТОиР (через
`send-as-cfo` с `target = DTOE`, либо через существующий `sendToDtoe` после
согласования всех ЦФО), SHALL приниматься исключительно ролью `DTOE` через
существующие `dtoeApprove`/`dtoeReturn`.

#### Scenario: ДТОиР не участвует в обычном списке ЦФО филиала

GIVEN справочник `cfos` содержит строку «ДТОиР»
WHEN филиал получает список ЦФО, доступных при направлении
(`CorrectionDetail.availableCfos`)
THEN строка «ДТОиР» в этом списке отсутствует

#### Scenario: Финальное решение ДТОиР не меняется

GIVEN корректировка в статусе `UNDER_DTOE_REVIEW` (независимо от того, как в
него попала — через филиал-инициированный цикл или напрямую от ЦФО)
WHEN пользователь роли `DTOE` отправляет `POST .../dtoe-approve`
THEN статус корректировки становится `APPROVED_BY_DTOE`
AND поведение эндпоинта не отличается от поведения для филиал-инициированных
корректировок

### Requirement: Доступ к созданию корректировки в интерфейсе

Система SHALL отображать пункт меню «Создать корректировку» пользователям с
ролью `CFO` наравне с ролью `FILIAL`. Система SHALL NOT полагаться только на
скрытие пункта меню как единственную защиту — соответствующий backend-эндпоинт
проверяет роль независимо (см. Requirement «Создание корректировки ролью
ЦФО»).

#### Scenario: Пункт меню виден ЦФО

GIVEN пользователь с ролью `CFO` авторизован
WHEN отображается боковое меню
THEN пункт «Создать корректировку» присутствует и ведёт на
`/corrections/create`
