# Proposal: planning-2027-package-review

## Проблема

Модуль «План на 2027» сейчас — визуальная заглушка (`SectionPlaceholder` на
`/planning`). Филиалы не имеют способа сформировать пообъектный план ДТОиР на
планируемый год (капитальный ремонт, техническое обслуживание и текущий
ремонт, диагностическое обследование) и провести его через формальное
согласование ЦФО и ДТОиР, аналогично тому, как это устроено для
«Корректировки» (домен `corrections`). Без этого экрана планирование не
документируется и не проходит согласование.

## Цель

Реализовать полноценный жизненный цикл «плана» — сущности, повторяющей
документооборот «Корректировки» **буквально по кнопкам и действиям**
(создание, загрузка версий файлов в слоты пакета, направление выбранным ЦФО,
замечания, согласование по каждому ЦФО независимо, направление в ДТОиР после
согласования всех обязательных ЦФО, финальное решение ДТОиР, цикл доработки/
повторной отправки), но как **полностью независимый, новый домен**: свои
таблицы/entities, свой API-неймспейс (`/plans`), свои frontend-роуты
(`/planning`) — без внешних ключей на таблицы `corrections` и без общего кода
с ними (дублирование архитектурного паттерна, не переиспользование данных).

Состав пакета документов плана — не фиксированный список, а конфигурируемый
через собственный аналог `CorrectionType`/`PackageRequirement`
(`PlanType`/`PlanPackageRequirement`): администратор задаёт типы плана и
обязательный состав слотов под каждый тип, как сейчас для корректировок.

Человекочитаемый ID плана — `PLN-000001` (отдельная Postgres-последовательность,
не связанная с `COR-`), замечаний к плану — `PLR-000001` (отдельная от `REM-`).

## Объём работ

### API (`api/src/`)

Новые схемы (`PlanStatus`, `PlanType`, `Plan`, `PlanDetail`, `PlanCfoStatus`,
`PlanHistoryEntry`, `PlanStats`) и пути (`/plans`, `/plans/{humanId}`,
`/plans/{humanId}/change-type`, `/plans/{humanId}/slots/{slotId}/files`,
`/plans/{humanId}/send`, `/plans/{humanId}/resubmit`,
`/plans/{humanId}/cfo-approve`, `/plans/{humanId}/cfo-return`,
`/plans/{humanId}/cfo-cancel`, `/plans/{humanId}/remarks`,
`/plans/{humanId}/remarks/{remarkId}`, `/plans/{humanId}/remarks/{remarkId}/fix`,
`/plans/{humanId}/remarks/{remarkId}/reopen`, `/plans/{humanId}/send-to-dtoe`,
`/plans/{humanId}/resubmit-to-dtoe`, `/plans/{humanId}/dtoe-approve`,
`/plans/{humanId}/dtoe-return`, `/plans-stats*`, `/org/plan-types*`,
`/plan-files/{id}/download`). Подробности — `design.md` (`## API Shape`).

### Backend (`apps/backend/src/planning/`)

Новый домен, параллельный `corrections`, по тому же архитектурному образцу
(entities, dto, mapper, service, controller, module) и той же статусной
модели (`Plan`/`PlanCfoStatus`/`PlanRemark`/`PlanHistoryEntry`/
`PlanDocumentSlot`/`PlanFileVersion`). Переиспользует только справочные
сущности `FilialCfoLink`/`Cfo`/`Filial`/`User`/`RolesGuard` — не таблицы
`corrections`. `Notification` получает третье nullable поле `planId` (рядом с
уже существующими `correctionId`/`factPackageId`) по уже заложенному в код
паттерну «ровно одно из полей заполнено».

### Frontend (`apps/frontend/app/(private)/planning/`)

Полноценные экраны вместо `SectionPlaceholder`: создание плана (выбор типа),
карточка плана (слоты пакета с загрузкой версий, панель отправки с выбором
ЦФО, статусы по ЦФО, замечания, финальное решение ДТОиР, история), рабочий
стол с дашборд-карточками по ролям (Филиал/ЦФО/ДТОиР) — 1:1 по составу
действий с соответствующими экранами `corrections`/`dashboard`. Kubb-клиент
генерируется из обновлённого контракта.

## Роли

Роли не меняются — переиспользуются существующие `FILIAL`, `CFO`, `DTOE` (и
`ADMIN` для аудита наравне с `DTOE`, как в `corrections`). Новых ролей не
заводится.

## Capabilities

### New Capabilities

- `planning-2027-package-review`: Филиал создаёт план (выбрав тип плана),
  загружает версии файлов в обязательные слоты пакета согласно типу,
  направляет план на проверку выбранным связанным через `FilialCfoLink` ЦФО;
  каждый ЦФО независимо согласовывает либо возвращает план с замечанием;
  после согласования всех обязательных ЦФО любой из них направляет план в
  ДТОиР; ДТОиР выносит финальное решение (согласовать — план становится
  неизменяемым, либо вернуть с обязательным замечанием); Филиал дорабатывает
  план и направляет его повторно (ЦФО или ДТОиР) без сброса статусов ранее
  согласовавших ЦФО. ДТОиР видит планы всех филиалов (аудит).

### Modified Capabilities

_(нет — существующие capabilities `corrections`/`fact-package-review` не
затрагиваются; план — полностью независимый домен, не изменяющий их
таблицы, API или поведение.)_

## Исключено из объёма работ

- Любая связь/перенос данных между `Correction` и `Plan` (например,
  автосоздание плана из корректировки) — сущности независимы полностью.
- Периодизация плана внутри года (помесячная/поквартальная разбивка одного
  плана) — план целиком на год, без под-периодов; при необходимости другой
  периодизации — отдельная будущая задача.
- Изменение статусной модели или поведения существующих доменов
  `corrections`/`fact-packages`.
- Уведомления через внешние каналы (email/push) — только внутрисистемные
  `Notification`, как у `corrections`/`fact-packages`.
- Финальный состав экрана `/planning/files` (список vs. переход сразу в
  карточку) — решается отдельно перед фронтовой веткой дашборда, не
  блокирует API/backend/create-detail работу.

## Связанные тикеты

Нет явного тикета `KT-*` — задача поставлена напрямую пользователем в этой
сессии (см. `design.md`, раздел «Источники»).
