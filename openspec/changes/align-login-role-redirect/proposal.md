## Why

Текущий экран входа (`apps/frontend/app/(public)/page.tsx`) расходится с продуктовой
спекой экрана входа (раздел «6.1 Экран входа»): поле логина называется и
валидируется как `username` вместо `email` (без проверки формата ни на фронте, ни
на бэке), а после успешного входа пользователь всегда попадает на общий
`/dashboard` — ролевого редиректа (FILIAL → `/filial`, CFO → `/cfo`, DTOE → `/dtoe`)
и защиты «чужого» ролевого раздела (403 на бэке, экран «Доступ запрещён» на
фронте) в коде нет вообще, хотя это часть контракта экрана входа и часть матрицы
доступа в корневом `AGENTS.md`. Расхождение подтверждено сверкой кода со спекой.

## What Changes

- Поле логина в API-контракте, backend DTO и frontend-форме переименовывается из
  `username` в `email`; добавляется проверка формата email на фронте (regex,
  ошибка под полем без отправки запроса) и на бэке (`class-validator`,
  `@IsEmail()`). **BREAKING**: тело запроса `POST /auth/login` меняет поле
  `username` на `email`.
- После успешного входа фронтенд читает роль пользователя из ответа `POST
  /auth/login` (`AuthUser.role`, поле уже есть в контракте) и перенаправляет:
  `FILIAL` → `/filial`, `CFO` → `/cfo`, `DTOE` → `/dtoe`. Роль `ADMIN` вне
  области этого change (см. Impact) — сохраняет текущий редирект на `/dashboard`.
- Создаются минимальные ролевые разделы приватного контура — `apps/frontend/app/
  (private)/filial/`, `(private)/cfo/`, `(private)/dtoe/` — по одной
  заглушечной странице на раздел (по аналогии с существующей заглушкой
  `/dashboard`), закрытые guard'ом по роли.
- На бэкенде разделы защищаются существующей ролевой инфраструктурой
  (`@Roles()` + `RolesGuard`) — по одному минимальному защищённому эндпоинту на
  раздел, чтобы `RolesGuard` реально применялся и возвращал 403 при чужой роли.
- На фронте прямой заход пользователя на чужой ролевой раздел (получение 403 от
  бэкенда) отображает экран «Доступ запрещён» вместо редиректа на логин.
- Существующее поведение `(private)/layout.tsx` (редирект на несуществующий
  `/login` при 401/403/413) не меняется в рамках этого change — страница логина
  остаётся на `/`, отдельный маршрут `/login` не создаётся (подтверждено
  пользователем как осознанное решение).

## Capabilities

### New Capabilities

- `login`: экран входа — поле email с валидацией формата, поле пароля, кнопка
  «Войти» с состоянием загрузки, единое сообщение об ошибке, редирект после
  успешного входа по роли пользователя.
- `role-scoped-sections`: защищённые ролевые разделы приватного контура
  (`/filial`, `/cfo`, `/dtoe`) — доступ только пользователю соответствующей
  роли, 403 на бэкенде и экран «Доступ запрещён» на фронте при чужой роли.

## Impact

- **API**: `api/src/components/schemas/auth.yaml` (`LoginRequest.username` →
  `email`, формат `format: email`), `api/src/paths/auth-login.yaml` (описание
  поля). Новых path-файлов для ролевых разделов не требуется, если минимальные
  защищённые эндпоинты используют уже существующие пути доменов; при
  необходимости добавляются точечные `GET`-заглушки — решается в design.md.
- **Backend**: `apps/backend/src/auth/dto/login.dto.ts` (`username` → `email`,
  `@IsEmail()`), `apps/backend/src/auth/strategies/local.strategy.ts` (поле
  стратегии), `apps/backend/src/auth/auth.service.ts` /
  `apps/backend/src/users/*` (поиск пользователя по email вместо username).
  Используется существующая ролевая инфраструктура: `apps/backend/src/common/
  decorators/roles.decorator.ts`, `apps/backend/src/common/guards/
  roles.guard.ts` — новых guard'ов не создаётся.
- **Frontend**: `apps/frontend/app/(public)/components/login-form.tsx` (поле
  email, редирект по роли), Kubb-кодоген
  (`apps/frontend/packages/api/base/codegen/**` — регенерируется из
  обновлённого контракта, вручную не редактируется), новые страницы
  `apps/frontend/app/(private)/filial/page.tsx`,
  `apps/frontend/app/(private)/cfo/page.tsx`,
  `apps/frontend/app/(private)/dtoe/page.tsx`, экран «Доступ запрещён»
  (компонент/страница ошибки для 403).
- **Вне области**: создание маршрута `/login` (страница логина остаётся на `/`);
  наполнение ролевых разделов реальным функционалом (дашборды, корректировки) —
  только заглушки, достаточные для проверки редиректа и guard'а; поведение роли
  `ADMIN` (не описана в спеке экрана входа, редирект не меняется); иконка
  показать/скрыть пароль (в спеке помечена как рекомендация, не обязательное
  требование); существующий редирект `(private)/layout.tsx` на `/login` при
  401/403/413 — не переименовывается в рамках этого change.
- Внешних зависимостей не затронуто.
