## Изучено перед проектированием

- `apps/backend/src/database/seed.ts` — массив `CFOS` (17 записей,
  `{ code, slug }`), используется и для `cfoRepo.save` (создание строки
  `cfos`), и для построения демо-логина ЦФО-пользователя
  (`username: \`cfo.${CFOS[i].slug}@demo.local\``). Сид выполняет ранний
  выход, если в базе уже есть хотя бы один пользователь — переименование
  кодом не применяется повторно к уже засеянной базе.
- `apps/backend/src/org/entities/cfo.entity.ts` — `Cfo.code` (`@Index({
  unique: true })`), `Cfo.name` — обычные строковые колонки, без enum/CHECK
  constraint на конкретные значения.
- `grep -rn "СОРиСОФ"` по всему репозиторию — 2 совпадения (`seed.ts`,
  `apps/backend/AGENTS.md`); во frontend, API-контракте (`api/src/**`) и
  тестах совпадений нет.
- `apps/backend/AGENTS.md` — таблица `Filial / CFO / FilialCFO`, справочник
  из 17 значений `CFO.code`.

## Backend

Единственная логическая правка — значение в сиде:

```ts
// apps/backend/src/database/seed.ts, строка 90
{ code: 'СОВОФ', slug: 'sovof' },
```

Никаких изменений в `Cfo`-сущности, сервисах или guard'ах не требуется —
`code`/`name` не участвуют ни в одном сравнении с литералом «СОРиСОФ» нигде в
`apps/backend/src/**` (проверено grep'ом).

### Уже засеянные базы

Локальный dev-стек этой сессии (`infra-db-1`, поднят и заполнен `bun run
seed` ранее) уже содержит строку `cfos` со значением `code = 'СОРиСОФ'`.
Правка `seed.ts` не применяется к уже существующим данным (см. Why). Для
приведения такой базы в соответствие — ручной SQL, выполняемый один раз:

```sql
UPDATE cfos SET code = 'СОВОФ', name = 'СОВОФ' WHERE code = 'СОРиСОФ';
```

Обновление по `code`, а не по `id` — безопаснее и не требует знания
конкретного `id` в разных средах. Запрос идемпотентен: повторный вызов на уже
обновлённой базе не находит строк и ничего не делает.

`username` уже существующего демо-пользователя (`cfo.sorisof@demo.local`)
**не переименовывается** этим SQL — он не выводится из `code` во время
выполнения, а зафиксирован в БД при первом сидировании. Обновлять его или нет
— открытый вопрос (см. «Открыто» ниже); в этом change не делается
автоматически, чтобы не менять логин уже выданной демо-учётной записи без
явного подтверждения пользователя.

## Frontend

Изменений нет. `CorrectionDetail.availableCfos`, `CorrectionCfoStatus.cfo`,
списки/фильтры в кабинетах ЦФО и ДТОиР (`cfo-corrections-overview.tsx`,
`dtoe-corrections-overview.tsx` при его появлении) отображают `cfo.code`/
`cfo.name`, приходящие из API — значение подставится автоматически после
обновления данных в БД, без пересборки frontend.

## Дизайн (UI)

Изменений визуального оформления не требуется — переименование не меняет
макет, только текстовое значение, подставляемое туда же, где раньше
отображалось «СОРиСОФ» (те же бейджи/строки таблиц/пункты фильтра). Раздел
оставлен как точка фиксации на случай, если пользователь позже попросит
что-то visual-специфичное для этого change (например, отдельный алиас/
сокращение для отображения в узких колонках таблиц) — на момент создания
change таких пожеланий не поступало.

## API Shape

Без изменений — ни один путь/схема `api/src/**` не содержит значения
«СОРиСОФ» и не требует правки.

## Тестовая стратегия

P3 — ручная верификация вместо автотестов (нет новой логики, см.
`proposal.md` → «Влияние на качество»). Порядок: (1) убедиться, что чистая БД
после `bun run seed` содержит «СОВОФ», не «СОРиСОФ»; (2) на уже существующей
БД выполнить SQL-обновление и убедиться, что `GET /corrections/{humanId}`
(или любой другой ответ, включающий `availableCfos`) возвращает «СОВОФ»; (3)
визуально проверить фильтр по ЦФО в кабинете ЦФО/ДТОиР и карточку
корректировки. Подробности — `test-plan.md`.
