## Why

Пользователь запросил переименовать ЦФО «СОРиСОФ» в «СОВОФ» в справочнике
подразделений Администрации Общества. Причина переименования (организационное
изменение названия подразделения) продуктовая, но сама правка — техническая:
меняется значение справочных данных (`Cfo.code`/`Cfo.name`), а не бизнес-
правило, API-контракт или новая функциональность.

Разведка (`grep -rn СОРиСОФ`) показала ровно два места в кодовой базе:
`apps/backend/src/database/seed.ts:90` (демо-данные) и
`apps/backend/AGENTS.md:59` (справочная таблица в документации). Отдельного
`GET /org/cfos`-эндпоинта нет (см. `openspec/changes/cfo-cabinet/proposal.md`,
раздел «Вне области») — значение `code`/`name` ЦФО передаётся клиенту всегда
динамически из БД (`CorrectionDetail.availableCfos`,
`CorrectionCfoStatus.cfo`, `Remark.cfo`), поэтому во frontend нет ни одного
захардкоженного упоминания «СОРиСОФ» — переименование не требует правок React-
компонентов.

## What Changes

- `apps/backend/src/database/seed.ts`: строка справочника `CFOS` —
  `{ code: 'СОРиСОФ', slug: 'sorisof' }` → `{ code: 'СОВОФ', slug: 'sovof' }`.
  Демо-логин соответствующего ЦФО-пользователя меняется с
  `cfo.sorisof@demo.local` на `cfo.sovof@demo.local` (username строится из
  `slug` во время сидирования, `userRepo.save` с `username:
  \`cfo.${CFOS[i].slug}@demo.local\``).
- `apps/backend/AGENTS.md`: строка справочника `CFO.code` (17 значений) —
  замена `СОРиСОФ` на `СОВОФ` в перечислении.
- **Существующие базы данных** (уже засеянные — в частности локальный dev-
  стек, поднятый в этой сессии): правка `seed.ts` не переименовывает уже
  существующую строку `cfos` — сид идемпотентен и пропускается целиком, если
  в базе уже есть хотя бы один пользователь (`if (await userRepo.exist({
  where: {} }))`). Для таких сред нужен отдельный ручной шаг — SQL-обновление
  существующей строки (см. `tasks.md`, `design.md`).
- Никаких изменений API-контракта, backend-логики (сервисы/контроллеры/guard'ы)
  и frontend-кода — переименование затрагивает только значение, а не форму/
  схему данных.

## Capabilities

Краткое техническое изменение — без изменения продуктовой capability, API-
контракта и наблюдаемого поведения приложения *(в смысле бизнес-правил и
структуры ответов)*. Delta-спецификации (`ADDED`/`MODIFIED Requirements`) не
создаются: ни один существующий `openspec/specs/**/spec.md` не формулирует
требование, привязанное к конкретному значению `Cfo.code` — справочник
подразделений не описан как отдельная capability с нормативными сценариями,
это статические демо-данные для локальной разработки, значение которых не
фиксировано ни одной спекой.

Наблюдаемое поведение всё же меняется в одном узком смысле — везде, где
раньше отображалось «СОРиСОФ» (карточка корректировки, фильтры по ЦФО в
кабинетах ЦФО/ДТОиР, история/уведомления), теперь будет отображаться «СОВОФ»;
это прямое и единственное следствие смены значения справочных данных, не
изменение логики отображения.

## Impact

- **Backend**: `apps/backend/src/database/seed.ts` (1 строка), локальные
  dev/staging базы, уже засеянные значением «СОРиСОФ» — требуют ручного
  SQL-обновления (см. `tasks.md`, задача 2.2).
- **Документация**: `apps/backend/AGENTS.md` (1 строка).
- **Frontend**: изменений нет — значение приходит из БД динамически.
- **API-контракт**: изменений нет.
- **Вне области**: полная миграционная система (в проекте её нет —
  `synchronize: true` вне production, см. `apps/backend/AGENTS.md`); история
  уже созданных корректировок (`CorrectionHistoryEntry.text`), где текст типа
  «СОРиСОФ согласовал» уже зафиксирован строкой на момент действия, — такие
  записи не переписываются задним числом (это неизменяемый лог, см. корневой
  `AGENTS.md`, правило 10 и глоссарий), новые записи после переименования
  будут содержать «СОВОФ».

## Влияние на качество

- **Уровень риска**: P3 — статическая правка справочных данных без
  изменения кода бизнес-логики, контракта или UI-компонентов.
- **Затронутые маршруты**: нет (значение подставляется динамически везде, где
  уже отображался ЦФО).
- **Затронутые frontend-компоненты**: нет.
- **Затронутые backend-модули**: `database` (сид).
- **Затронутые API**: нет.
- **TDD-порядок**: не применим — нет новой логики для failing-теста; проверка
  выполняется чтением сида и ручной верификацией (см. `test-plan.md`).
- **Обязательные уровни проверки**: Static — нет (правка не .ts-логики, а
  строкового литерала и Markdown); ручная проверка сидирования на чистой БД
  (см. `test-plan.md`).
- **Ручные проверки**: см. `test-plan.md` — пересидирование чистой БД,
  SQL-обновление уже существующей dev-базы, визуальная проверка отображения
  «СОВОФ» в интерфейсе.
- **План отката**: revert коммита; для уже обновлённых через SQL баз —
  обратный `UPDATE ... SET code = 'СОРиСОФ' WHERE code = 'СОВОФ'`.

## Процессное примечание

По стандартному правилу этого проекта для всех активных change (см. также
`openspec/changes/cfo-initiated-corrections/proposal.md`, раздел «Открытый
процессный вопрос»): все уточнения и решения пользователя, которые появятся
по ходу работы над этим change — включая дизайн/визуальные пожелания, если
такие появятся, — фиксируются в артефактах `rename-cfo-sorisof-to-sovof`
немедленно, в первую очередь в `design.md` → «Дизайн (UI)» и в «Журнал
уточнений» `test-plan.md`.
