## Why

На карточке корректировки (`correction-detail-page`) проверяющие (ЦФО и ДТОиР)
видели название загруженного филиалом файла и номер версии в блоке
«Комплектность пакета», но не могли открыть или скачать сам файл прямо со
страницы — при том что backend-эндпоинт `GET /files/{id}/download` уже
существовал и был реализован (`FilesController`), просто не был подключён ни к
одному элементу интерфейса. Проверяющий был вынужден принимать решение о
согласовании/возврате, не имея возможности посмотреть содержимое документа.
Пользователь явно запросил дать ЦФО и ДТОиР возможность открывать и скачивать
эти файлы прямо со страницы (роль Филиала, загрузившего файл, — исключена по
явному указанию пользователя: см. `design.md`, Decisions).

Отдельно пользователь столкнулся с отсутствием способа отменить случайное
нажатие кнопки «Согласовать»/«Вернуть на доработку» — после клика решение ЦФО
фиксировалось необратимо (кроме случая, когда ЦФО ещё раз пересматривает
решение после исправлений филиала через штатный флоу возврата/повторной
отправки). Запрошена кнопка-предохранитель «Отменить решение», доступная
самому ЦФО сразу после клика.

Ещё пользователь запросил возможность удалить у себя на дашборде («Мои
корректировки») корректировку, которую он создал по ошибке или больше не
собирается направлять. Уточнение в диалоге сузило запрос до одного точного
случая: крестик удаления доступен только для корректировок в статусе
«Черновик» — у любого другого статуса (уже направленного проверяющим)
крестика нет вовсе, полное удаление недоступно ни при каком статусе, кроме
`DRAFT`.

## What Changes

- Backend: `CorrectionsService.downloadFileVersion` дополнительно проверяет
  роль пользователя — доступ к скачиванию файла версии сужен до `CFO` и
  `DTOE` (были: филиал-владелец, ЦФО с доступом к корректировке, ДТОиР,
  админ). Филиал, загрузивший файл, теперь получает `403` при прямом вызове
  эндпоинта, даже если у него есть доступ к самой корректировке.
- Frontend: в блоке «Комплектность пакета» (`package-completeness.tsx`)
  название элемента пакета и текущая версия файла стали кликабельными
  ссылками на `GET /files/{id}/download`, открывающими файл в новой вкладке.
  Ссылки видны только пользователям с `isCfoReviewer`/`isDtoe` — Филиал их не
  видит.
- Backend: новый эндпоинт `POST /corrections/{humanId}/cfo-cancel`
  (`cancelCfoDecision`, роль CFO) — откатывает статус ТОЛЬКО этого ЦФО
  (`APPROVED`/`RETURNED` → `PENDING`) с пересчётом общего статуса
  корректировки. Оставленные этим ЦФО замечания не меняются и не удаляются —
  они часть истории согласования (`apps/backend/AGENTS.md`). Недоступно, если
  корректировка уже передана в ДТОиР, или если решение ещё не принято
  (`PENDING`) — `400` в обоих случаях.
- Frontend: новая кнопка «Отменить решение» в общей панели действий карточки
  корректировки (`remarks-list.tsx`, `RemarksActionBar`), видна только ЦФО и
  только когда есть что отменять.
- Также исправлен предсуществующий пробел, обнаруженный при разведке этой
  задачи: `cfoApprove` не проверял `myStatus.status === PENDING` (в отличие
  от уже исправленного в `cfo-cabinet` `cfoReturn`) — второй подряд вызов
  «Согласовать» проходил успешно вместо `400`. Guard добавлен по аналогии с
  `cfoReturn`.
- Backend: новый эндпоинт `DELETE /corrections/{humanId}` (`deleteCorrection`,
  роль FILIAL, только автор/владелец) — полностью удаляет корректировку
  (слоты, версии файлов на диске, замечания, статусы ЦФО, историю,
  уведомления — каскадом на уровне БД + физическая очистка файлов), но
  только пока статус — `DRAFT`. Для любого другого статуса — `400`.
  `DRAFT`-корректировка не может иметь ни одного статуса ЦФО (они создаются
  только `send()`), поэтому удаление черновика никого не уведомляет — уведомлять
  некого.
- Frontend: крестик «Удалить» в таблице «Мои корректировки»
  (`filial-corrections-overview.tsx`) — виден только в строке со статусом
  «Черновик», вызывает `deleteCorrection` без диалога подтверждения (тот же
  UX-паттерн, что уже принят для «Удалить» у собственного открытого
  замечания в `remarks-list.tsx`).

## Capabilities

### New Capabilities

- `correction-review-safeguards`: открытие/скачивание файлов версий со
  страницы корректировки (только ЦФО/ДТОиР), кнопка отмены собственного
  решения ЦФО и удаление собственной корректировки филиалом, пока она в
  статусе «Черновик».

### Modified Capabilities

_(нет — исправление guard'а `cfoApprove` относится к уже открытому change
`correction-detail-page` по тому же прецеденту, что и аналогичное исправление
`cfoReturn` в `cfo-cabinet`; baseline `openspec/specs/correction-detail-page/`
всё ещё не существует, `correction-detail-page` не заархивирован — отдельная
`MODIFIED Requirements`-секция не создаётся, задача зафиксирована в
`tasks.md` этого change для прослеживаемости.)_

## Impact

- **Backend**: `apps/backend/src/corrections/corrections.service.ts`
  (`downloadFileVersion` — guard роли; новый `cancelCfoDecision`; `cfoApprove`
  — guard `PENDING`; новый `deleteCorrection`), `corrections.controller.ts`
  (новые маршруты `POST :humanId/cfo-cancel`, `DELETE :humanId`),
  `corrections.service.spec.ts` (+13 тестов).
- **Frontend**: `apps/frontend/app/(private)/corrections/[humanId]/components/package-completeness.tsx`
  (ссылки на скачивание), `remarks-list.tsx` (кнопка «Отменить решение»),
  `lib/permissions.ts` (`canCancelCfoDecision`),
  `apps/frontend/app/(private)/dashboard/components/filial-corrections-overview.tsx`
  (крестик удаления для статуса «Черновик»), Kubb-кодоген
  `packages/api/base/codegen/**` (новые `useCancelCfoDecision`/`cancelCfoDecision`,
  `useDeleteCorrection`/`deleteCorrection`).
- **API-контракт**: новый путь `POST /corrections/{humanId}/cfo-cancel`
  (`api/src/paths/corrections-human-id-cfo-cancel.yaml`, зарегистрирован в
  `api/src/openapi.yaml`). Описание `GET /files/{id}/download`
  (`api/src/paths/files-id-download.yaml`) дополнено — сужение доступа до
  CFO/DTOE, схема запроса/ответа не менялась. `DELETE /corrections/{humanId}`
  добавлен в уже существующий `api/src/paths/corrections-human-id.yaml`
  (тот же path, что и `GET`).
- **Вне области**: полноценный «просмотрщик» файлов внутри страницы (превью
  PDF/Excel без скачивания) — реализовано только открытие/скачивание;
  массовая отмена решений нескольких ЦФО сразу (администратором/ДТОиР) — не
  запрошено; удаление уже направленной корректировки (любой статус, кроме
  `DRAFT`) — явно отклонено пользователем, кнопки для этого случая нет
  вообще (не задизейблена — отсутствует).

## Влияние на качество

- **Уровень риска**: P1 — сужение прав доступа к существующему эндпоинту
  (проверка регрессии для оставшихся разрешённых ролей обязательна), новое
  действие, мутирующее статус корректировки/ЦФО с пересчётом по уже
  существующей функции `recomputeStatusAfterCfoAction`, и необратимое
  удаление записи (единственное из трёх, где ошибка guard'а по статусу
  привела бы к потере данных, а не только к неверному статусу — сужено до
  `DRAFT`, где потерять нечего, кроме уже загруженных филиалом черновых
  версий файлов, которые он и так может перезалить).
- **Затронутые маршруты**: `/corrections/[humanId]` (карточка корректировки),
  `/dashboard` (таблица «Мои корректировки» для роли FILIAL).
- **Затронутые frontend-компоненты**: `PackageCompleteness`, `RemarksList`
  (`RemarksActionBar`), `FilialCorrectionsOverview`.
- **Затронутые backend-модули**: `corrections`
  (`CorrectionsService.downloadFileVersion`/`cancelCfoDecision`/`cfoApprove`/`deleteCorrection`,
  `CorrectionsController`).
- **Затронутые API**: `GET /files/{id}/download` (сузилось поведение — было:
  200 для филиала-владельца, стало: 403), новый `POST /corrections/{humanId}/cfo-cancel`,
  `POST /corrections/{humanId}/cfo-approve` (сузилось поведение при повторном
  вызове — было: 200, стало: 400), новый `DELETE /corrections/{humanId}`.
- **TDD-порядок**: соблюдён для backend — тесты (`corrections.service.spec.ts`)
  написаны вместе с каждым guard'ом и запущены сразу после (see `tasks.md`).
  Не соблюдён для frontend — реализация опережала тесты в рамках этой сессии
  (см. Gaps в `test-plan.md`, тот же класс пробела, что задокументирован в
  `cfo-cabinet/test-plan.md`).
- **Обязательные уровни проверки**: Static (`tsc --noEmit`, `redocly lint`) —
  выполнены, 0 ошибок/новых warning'ов. Backend Unit — `corrections.service.spec.ts`,
  13 новых тестов green (3 `downloadFileVersion`, 6 `cancelCfoDecision`, 4
  `deleteCorrection`; полный файл — 21/21, весь backend — 36/36). Frontend
  Component — не запущены (см. Gaps).
- **Ручные проверки**: под демо-аккаунтами `filial.donbassgaz@demo.local` /
  `filial.luganskgaz@demo.local` / `cfo.angnks@demo.local` через `curl` против
  поднятого dev-стека — скачивание файла (ЦФО с доступом → 200, ДТОиР → 200,
  ЦФО без доступа к этой корректировке → 403, Филиал-владелец → 403); отмена
  решения ЦФО (`ALL_CFO_APPROVED`/`APPROVED` → `cfo-cancel` →
  `UNDER_CFO_REVIEW`/`PENDING`, повторный вызов → `400`, Филиал → `403`);
  удаление корректировки (свой `DRAFT` → `204`, повторный `GET` того же
  `humanId` → `404`; чужой `DRAFT` другого филиала → `403`; `DRAFT` под ЦФО
  → `403`; направленная корректировка (`ALL_CFO_APPROVED`) под её
  владельцем → `400`). Демо-данные восстановлены повторным согласованием
  после проверки `cfo-cancel`; тестовые `DRAFT`-корректировки, созданные
  для проверки удаления, удалены тем же эндпоинтом (самоочистка). Визуальная
  проверка в браузере (клик по ссылке/кнопке) не выполнена — окружение не
  позволяет запустить Playwright Chromium (Alpine/musl dev-образ фронтенда,
  см. `test-plan.md`, Gaps).
- **План отката**: изменения аддитивны и локальны (новая кнопка/ссылки,
  новый эндпоинт, сужение guard'ов двух существующих эндпоинтов) — откат
  равносилен revert соответствующих коммитов без обратных миграций БД и без
  breaking-изменений остальной части API-контракта.
