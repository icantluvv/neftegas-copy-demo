## Context

`apps/backend/src/corrections/files.controller.ts` (`GET /files/:id/download`)
и `CorrectionsService.downloadFileVersion` уже существовали и были полностью
рабочими — читали файл с диска (`UPLOADS_DIR`) и отдавали его как
`attachment` через `Content-Disposition`. Единственной проверкой был
`checkAccess(user, correction)` — общий guard «видит ли пользователь эту
корректировку вообще» (Филиал-владелец / ЦФО с назначенным статусом / ДТОиР /
ADMIN). Frontend не вызывал этот эндпоинт нигде — `package-completeness.tsx`
(`CurrentVersionCell`) показывал только номер версии и дату загрузки, без
ссылки.

`apps/backend/AGENTS.md`, раздел «Роли и матрица доступа», явно перечисляет,
кто может «Оставить замечание к элементу» и «Согласовать» (ЦФО/ДТОиР), но не
описывает отдельно право на скачивание файла — этот change формализует его
как отдельное правило, продиктованное явным запросом пользователя (см.
`proposal.md`, Why).

`CorrectionsService.cfoReturn`/`dtoeReturn` уже получили guard `PENDING`/
`UNDER_DTOE_REVIEW` в рамках `cfo-cabinet` (см. `openspec/changes/cfo-cabinet/design.md`,
раздел «Backend guard»). При разведке этого change обнаружено, что
`cfoApprove` осталась без аналогичной проверки `myStatus.status === PENDING`
— тот же класс пробела, исправлен по тому же паттерну (`BadRequestException`
до входа в транзакцию).

`recomputeStatusAfterCfoAction` (уже существующая приватная функция
`CorrectionsService`) пересчитывает `Correction.status` по совокупности
`CorrectionCfoStatus` всех обязательных ЦФО (`RETURNED` → приоритет,
`APPROVED` у всех → `ALL_CFO_APPROVED`, частично → `PARTIALLY_APPROVED`,
иначе → `UNDER_CFO_REVIEW`). Она уже вызывается из `cfoApprove` и `resubmit`
— переиспользована для отмены решения без нового кода пересчёта статуса.

## Goals / Non-Goals

**Goals:**
- Дать ЦФО и ДТОиР возможность открыть/скачать файл версии прямо со страницы
  корректировки, не покидая карточку.
- Явно сузить это право до ЦФО/ДТОиР на backend — по прямому запросу
  пользователя, а не как продолжение общего `checkAccess`.
- Дать ЦФО кнопку-предохранитель, откатывающую собственное случайно нажатое
  решение (`APPROVED`/`RETURNED` → `PENDING`), без затрагивания истории
  замечаний.
- Закрыть обнаруженный при разведке пробел `cfoApprove` (guard `PENDING`) —
  та же категория race condition, что уже устранена для `cfoReturn` в
  `cfo-cabinet`.
- Дать Филиалу возможность удалить собственную корректировку, пока она в
  статусе «Черновик» — до того, как её увидел хоть один проверяющий.

**Non-Goals:**
- Не строится встроенный просмотрщик содержимого файла (PDF/Excel preview) —
  только открытие/скачивание браузером по прямой ссылке.
- Не вводится отмена решения ДТОиР (`dtoe-cancel`) — не запрошено; ДТОиР —
  финальная инстанция, откат её решения требует отдельного продуктового
  решения (например, кто уполномочен отменить финальное согласование) и
  сознательно вынесен за пределы этого change.
- Не вводится массовая/административная отмена чужих решений — кнопка видна
  и доступна только самому ЦФО, принявшему решение.
- Не меняется поведение `cfoReturn`/`dtoeReturn`/`leaveRemark` — эти guard'ы
  уже приняты в `cfo-cabinet`.
- Не вводится удаление направленной (не `DRAFT`) корректировки ни в каком
  виде — ни hard, ни soft/«отозвать». Пользователь явно сузил запрос до
  `DRAFT`: кнопка удаления для остальных статусов не показывается и не
  дизейблится — она просто не существует в этом сценарии.
- Не вводится отдельный эндпоинт «отозвать корректировку» (soft withdraw с
  сохранением записи) — рассматривался как более безопасная альтернатива
  hard delete, отклонён пользователем в пользу полного удаления, но только
  для `DRAFT`, где это не создаёт риска для истории/аудита (см. Decisions).

## Decisions

### Скачивание файла — доступно только ЦФО и ДТОиР, не Филиалу-владельцу

Рассмотрено: оставить действующий `checkAccess` без изменений (Филиал,
загрузивший файл, тоже мог бы его переоткрыть — он и так технически владеет
исходником на своём компьютере). Пользователь явно уточнил в диалоге (см.
историю разработки этой сессии), что кнопка нужна «только ЦФО и ДТОиР» —
формализовано как отдельная проверка роли поверх `checkAccess`, а не замена
её: `checkAccess` по-прежнему определяет «видит ли пользователь эту
корректировку», новая проверка — «может ли эта роль скачивать файлы в её
рамках». ADMIN, ранее проходивший через `checkAccess` (`user.role === Role.ADMIN`),
теперь тоже не может скачивать файлы через этот эндпоинт — в глоссарии
`AGENTS.md` роль ADMIN не входит в три бизнес-роли (Филиал/ЦФО/ДТОиР), это
технический аккаунт для администрирования; явного запроса на скачивание
файлов для него не поступало, оставлено вне доступа для консистентности с
буквальным «только ЦФО и ДТОиР».

### Ссылка на скачивание — прямой `<a href>` на `/files/{id}/download`, не программный fetch+blob

Рассмотрено: скачивать файл через `fetch`/`useDownloadFileVersion`-хук (уже
сгенерирован Kubb) и создавать `Blob`/`ObjectURL` на клиенте. Отклонено —
эндпоинт уже отдаёт `Content-Disposition: attachment`, браузер сам покажет
диалог сохранения/откроет файл по прямой ссылке; `fetch`+`blob` не даёт
дополнительных гарантий (авторизация — through same-origin httpOnly cookie,
`next.config.ts` уже проксирует `/api/*` на backend) и добавляет сложность
(отслеживание `isPending`, ручное освобождение `ObjectURL`) без пользы для
этого сценария («открыть в новой вкладке или скачать»).

### Название элемента в «Комплектность пакета» — тоже ссылка, не только версия

Изначальная реализация ссылки — только под номером версии («Открыть /
скачать»). Пользователь прислал скриншот, где кликал именно по названию
элемента пакета (столбец «Элемент»), ожидая, что оно откроет файл —
запрошено сделать оба места кликабельными. Оба варианта ведут на один и тот
же URL текущей версии слота; сохранены оба, а не заменено одно другим, чтобы
не ломать уже привычное расположение «Открыть / скачать» под версией.

### Отмена решения — не удаляет и не переоткрывает замечания

Рассмотрено (см. историю уточняющих вопросов пользователю): (а) откатывать
весь пакет статусов и замечаний по всем ЦФО этой корректировки, (б) удалять
собственные замечания ЦФО при отмене решения. Оба варианта отклонены
пользователем явно. Выбрано: откатывается только `CorrectionCfoStatus` этого
конкретного ЦФО; любые замечания (в том числе уже `CLOSED` в результате
`cfoApprove`, закрывающего открытые замечания при согласовании) остаются как
есть — согласуется с `apps/backend/AGENTS.md`, «Версии файлов не удаляются
никогда» / «Замечание в статусе... `CLOSED` неизменяемо — эти записи являются
частью истории согласования» (тот же принцип неизменности истории,
распространённый на действие «отмена»). Следствие: после отмены согласования
замечания, закрытые этим согласованием, остаются `CLOSED`, даже когда статус
ЦФО снова `PENDING` — сознательно принятый побочный эффект, задокументирован
в `proposal.md`, не считается багом.

### Удаление корректировки — только для `DRAFT`, hard delete, без уведомлений

Рассмотрено в диалоге с пользователем: (а) hard delete vs soft
(«отозвать» — статус, данные остаются) — выбран hard delete, но **только**
для `DRAFT`; (б) для каких статусов доступен крестик — только «На проверке
ЦФО» / любой ненаправленный статус кроме финального / произвольный —
пользователь сузил до буквально одного статуса: `DRAFT`. Для любого другого
статуса кнопки нет вообще (не задизейблена — отсутствует), backend
дополнительно отклоняет `400` при прямом вызове API в обход UI. Обоснование
именно этого сужения: `DRAFT` — единственный статус, гарантированно не
имеющий ни одной строки `CorrectionCfoStatus` (создаются только в `send()`)
и ни одного замечания (замечания оставляют только ЦФО/ДТОиР, которым
`DRAFT` недоступен для проверки) — то есть удаление `DRAFT` физически не
может задеть ничью историю согласования, в отличие от любого другого
статуса, где `apps/backend/AGENTS.md` («Версии файлов не удаляются никогда»)
и уже принятые Decisions этого же change (отмена решения ЦФО не трогает
замечания) прямо требуют сохранности данных. Третий вопрос пользователю —
нужны ли уведомления ЦФО/ДТОиР при удалении — получил ответ «да,
уведомлять» как общий принцип, но в сочетании с сужением до `DRAFT` он
оказывается неприменим на практике: уведомлять физически некого (ни у кого
нет статуса по `DRAFT`-корректировке). Уведомление НЕ реализовано —
добавление такого кода было бы мёртвым, никогда не исполняемым путём при
текущем ограничении; если сценарий удаления расширится на направленные
статусы в будущем change, уведомление нужно будет добавить тогда, вместе с
самим этим расширением, а не заранее.

Помимо каскадного удаления записей в БД (`onDelete: 'CASCADE'` уже
проставлен во всех связанных entity — `DocumentSlot`, `FileVersion`,
`CorrectionCfoStatus`, `Remark`, `CorrectionHistoryEntry`, `Notification`),
`deleteCorrection` дополнительно удаляет физические файлы версий с диска
(`fs.unlink`, best-effort — ошибка чтения/отсутствия файла не блокирует
удаление записи, поскольку запись к этому моменту уже удалена).

### Guard'ы отмены: `PENDING` запрещена, статусы после ДТОиР запрещены

Отмена решения, когда статус ЦФО уже `PENDING` (нечего отменять), и отмена
после того, как корректировка уже в `UNDER_DTOE_REVIEW`/`RETURNED_BY_DTOE`/
`APPROVED_BY_DTOE` (решение ЦФО уже использовано вышестоящим шагом процесса
— откат задним числом сломал бы согласованность с уже принятым в ДТОиР
пакетом), — оба возвращают `400` до входа в транзакцию, тот же стиль, что
уже принят для `cfoReturn`/`leaveRemark` в `cfo-cabinet`.

## API Shape

- **Изменено**: `GET /files/{id}/download` (`api/src/paths/files-id-download.yaml`)
  — описание дополнено: доступ ограничен ролями CFO и DTOE с доступом к
  соответствующей корректировке; Филиал (в том числе владелец) — `403`.
  Схема запроса/ответа не менялась (`200` — `application/octet-stream`,
  `403` — уже был описан).
- **Новое**: `POST /corrections/{humanId}/cfo-cancel` (`cancelCfoDecision`,
  `api/src/paths/corrections-human-id-cfo-cancel.yaml`). Роль CFO. Без тела
  запроса. Ответ `200` — `CorrectionDetail` (статус этого ЦФО — `PENDING`,
  `decidedById`/`decidedAt` — `null`, `Correction.status` пересчитан).
  `400` — если статус этого ЦФО уже `PENDING` («отменять нечего») или
  корректировка уже в `UNDER_DTOE_REVIEW`/`RETURNED_BY_DTOE`/`APPROVED_BY_DTOE`.
  `403` — не роль CFO или у пользователя нет строки статуса по этой
  корректировке.
- **Новое**: `DELETE /corrections/{humanId}` (`deleteCorrection`, добавлен в
  уже существующий `api/src/paths/corrections-human-id.yaml`, тот же path,
  что и `GET`). Роль FILIAL, только автор/владелец. Без тела запроса. Ответ
  `204`, без содержимого. `400` — статус корректировки не `DRAFT`. `403` —
  не роль FILIAL или не владелец. `404` — корректировка не найдена.

### Backend guard: `downloadFileVersion` — проверка роли

- **Файл**: `apps/backend/src/corrections/corrections.service.ts`.
- **Было**: единственная проверка — `checkAccess(user, correction)`.
- **Стало**: дополнительно `if (!(user.role === Role.CFO || user.role ===
  Role.DTOE)) throw new ForbiddenException(...)` — после `checkAccess`, до
  чтения файла с диска.
- **Обратная совместимость**: сужение — Филиал-владелец и ADMIN, ранее
  получавшие файл, теперь получают `403`. Ни один сценарий ЦФО/ДТОиР не
  меняется.

### Backend guard: `cfoApprove` — проверка `PENDING`

- **Файл**: тот же.
- **Было**: `if (!(user.role === Role.CFO && myStatus)) throw new
  ForbiddenException()`.
- **Стало**: дополнительно `if (myStatus.status !== CfoStatusValue.PENDING)
  throw new BadRequestException(...)` — до входа в транзакцию, идентично уже
  принятому паттерну `cfoReturn` (`cfo-cabinet`).
- **Обратная совместимость**: сужение — повторный вызов после решения
  (`APPROVED`/`RETURNED`) теперь `400` вместо повторного успешного
  выполнения (ранее приводило к перезаписи `decidedAt`/повторному закрытию
  уже закрытых замечаний без видимого эффекта, но без ошибки).

### Backend: `cancelCfoDecision` — новый метод

- **Файл**: тот же, размещён сразу после `cfoReturn`.
- Проверяет роль/наличие статуса (`403`), `status !== PENDING` (`400`,
  «нечего отменять»), `correction.status` не в списке `[UNDER_DTOE_REVIEW,
  RETURNED_BY_DTOE, APPROVED_BY_DTOE]` (`400`, «уже передана в ДТОиР»).
  В транзакции: `CorrectionCfoStatus.update(myStatus.id, { status: PENDING,
  decidedById: null, decidedAt: null })`, запись в историю, вызов уже
  существующего `recomputeStatusAfterCfoAction`.

### Backend: `deleteCorrection` — новый метод

- **Файл**: тот же, размещён сразу после `create`.
- Проверяет роль/владение филиалом (`403`), `status !== DRAFT` (`400`).
  В транзакции — `manager.getRepository(Correction).delete(correction.id)`
  (каскад на уровне БД удаляет `DocumentSlot`/`FileVersion`/
  `CorrectionCfoStatus`/`Remark`/`CorrectionHistoryEntry`/`Notification`).
  После транзакции — `fs.unlink` для каждого `storagePath` уже загруженных
  версий (best-effort, ошибки игнорируются). Возвращает `void` — контроллер
  отвечает `204 No Content` (тот же паттерн, что уже у `deleteRemark`).
