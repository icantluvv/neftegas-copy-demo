## Context

См. `proposal.md` — Why и раздел «Контекст решения». Текущее состояние до
изменения: навигация распределена между `TopTabs` (шапка) и `SidebarNav`
(боковая панель), состав сайдбара вычисляется от `pathname` через
`findActiveModule` → `getSidebarItems`. Изменение целиком в контуре
`apps/frontend`, без API и backend.

## Goals / Non-Goals

**Goals:**
- Один источник навигации по разделам — `SidebarNav`.
- Состав и ссылки пунктов не зависят от маршрута; от маршрута зависит только
  подсветка активного пункта.
- Конфигурация меню — декларативный статический массив в одном месте.

**Non-Goals:**
- Изменение маршрутов страниц (`/planning`, `/execution`, `/fact` остаются).
- Изменение мобильного поведения сайдбара, блока профиля, выхода, брендинга.
- Ролевая модель прав (меняется только видимость пунктов меню, не доступ к
  маршрутам).

## Decisions

- **Статический `sidebarItems: NavSection[]` в `app/(private)/constants.ts`
  вместо вычисления от `pathname`.** Альтернатива — оставить `getSidebarItems`,
  но вернуть ему стабильный набор. Отклонено: сама функция провоцирует
  page-dependent логику; декларативный массив однозначнее и тестируется без
  моков роутера.
- **Подсветка через чистую функцию `isNavItemActive(item, pathname)` с
  `matchPrefixes`.** Точное совпадение `pathname === href` плюс
  `pathname.startsWith(prefix)`. Позволяет подсвечивать «Рабочий стол» на
  `/corrections/*`, не подмешивая эти пункты в состав меню. Альтернатива —
  `usePathname` + сравнение только по `href`: не покрывает вложенные маршруты.
- **Полное удаление `TopTabs`, `get-sidebar-items.ts`, `find-active-module.ts`,
  `ModuleTab`, `FALLBACK_HOME_HREF`.** Оставлять «на всякий случай» нельзя —
  мёртвый код снова затянет page-dependent навигацию (см. `proposal.md` →
  «Контекст решения»).
- **Фильтрация по роли остаётся на клиенте (`item.roles`)** — это UX-подсказка;
  защита доступа к самим маршрутам — отдельный слой и вне объёма change.

## Risks / Trade-offs

- [Пересечение с незавершённым change `sidebar-nav-icons` — те же файлы] →
  сохранить поле `icon` у каждого пункта и рендер иконки; согласовать порядок
  вливания.
- [«План на 2027», «Выполнение», «Факт» — страницы-заглушки, пункты ведут на
  полупустые экраны] → допустимо: маршруты уже существуют, поведение страниц
  вне объёма change.
- [Потеря пункта «Создать корректировку» для модуля планирования
  (`/planning/create`)] → осознанно: остаётся один маршрут `/corrections/create`
  (см. `proposal.md`).

## Test strategy

- **Static:** `bun run lint`, `bun run build` — отсутствие ссылок на удалённые
  модули, типы `NavSection`/`isNavItemActive`.
- **Frontend Component** (`sidebar-nav.component.test.tsx`, Vitest Browser Mode):
  наличие всех пунктов и корректность ссылок; идентичность состава при разных
  `usePathname`; подсветка активного пункта по точному совпадению и по префиксу
  `/corrections/*`; видимость «Создать корректировку» для `FILIAL` и скрытие для
  `CFO`.
- **Manual:** проход по всем разделам, визуальная проверка подсветки и шапки без
  вкладок.
- Backend Unit/Feature, E2E, Integration — не применимы (нет API и критического
  пользовательского маршрута с сессией/кукой в объёме change).
