# corrections-mtr-list-slot

## Why

В демо-данных (`apps/backend/src/database/seed.ts`) «Перечень комплекта МТР
(ХС)» существует только как `groupLabel` — подпись над группой из двух
взаимоисключающих документов («Локальный сметный расчёт (ПД)» и «ХЗ-х ТКП»,
выбор одного варианта). Пользователь, глядя на карточку «Комплектность
пакета», ожидает увидеть «Перечень комплекта МТР (ХС)» как отдельную строку
своего собственного элемента пакета — с отдельным файлом, а не только как
заголовок над чужими двумя документами.

Это краткое техническое изменение: продуктовая capability не меняется —
`PackageRequirement`/`DocumentSlot` уже поддерживают произвольные документные
требования типа корректировки, механизм не меняется. Меняется только
демо-состав требований для типа «Стандартная корректировка» — добавляется
ещё один обязательный документ. API-контракт и модель данных не меняются
(используется существующая структура `PackageRequirement`). Delta specs не
создаются (`skip_specs: true`) — наблюдаемое поведение ограничено составом
демо-строк в уже существующей таблице «Комплектность пакета», не новой
capability.

При добавлении нового слота обнаружена смежная проблема: `PackageRequirement.
order` — поле, чьё единственное назначение по `apps/backend/AGENTS.md`
(«Порядок отображения в карточке») — фактически нигде не применялось при
формировании ответа `GET /corrections/:humanId`. Слоты возвращались в том
порядке, в котором их отдаёт TypeORM/Postgres без явного `ORDER BY` —
случайно совпадающем с порядком создания (а значит и с `order`) только пока
слоты создаются в seed строго последовательно. Явного контракта на этот
порядок не было: любое будущее изменение порядка создания слотов (другой тип
корректировки, миграция данных, ручная правка через API) могло незаметно
разъехаться с `order` без единой ошибки — потому что ничего не проверяет это
сегодня. Добавлена явная сортировка по `requirement.order` при сборке ответа.

## What Changes

- В `apps/backend/src/database/seed.ts` добавлено новое требование
  `PackageRequirement` — «Перечень комплекта МТР (ХС)», обычный обязательный
  документ (без `choiceGroupKey`), отдельная строка со своим слотом и файлом
  в демо-корректировках. Существующая группа выбора одного варианта
  («Локальный сметный расчёт (ПД)» / «ХЗ-х ТКП» под тем же `groupLabel`)
  сохранена без изменений — это два разных элемента пакета.
- Порядок (`order`) остальных требований типа «Стандартная корректировка»
  сдвинут, чтобы новый документ шёл перед группой выбора.
- Демо-корректировки в статусе `DRAFT` получают файл для нового слота — как и
  для остальных обязательных документов.
- В `package-completeness.tsx` убрана подпись группы («Перечень комплекта МТР
  (ХС) — выберите один вариант»), которая рендерилась над первым элементом
  группы выбора: после того как «Перечень комплекта МТР (ХС)» появился
  отдельной строкой, повторение того же названия как заголовка группы над
  «Локальный сметный расчёт (ПД)» стало избыточным и вводит в заблуждение.
  Таблица теперь показывает все элементы пакета плоским списком без
  группового заголовка (`choiceGroupKey`/`groupLabel` в данных и backend
  validation-логике не меняются — убрано только визуальное обособление).
- В `corrections.service.ts` (`toCorrectionDetailDto`) добавлена явная
  сортировка `correction.slots` по `requirement.order` перед маппингом в DTO
  (слот без требования — `Excel корректировка`, `requirementId = null` —
  сортируется первым, `order ?? -1`). Порядок строк в ответе API теперь
  гарантированно соответствует `PackageRequirement.order`, а не порядку
  вставки строк в БД.

## Impact

- `apps/backend/src/database/seed.ts` — состав `PackageRequirement`, слоты и
  файлы демо-корректировок.
- `apps/frontend/app/(private)/corrections/[humanId]/components/
  package-completeness.tsx` — убран рендеринг группового заголовка
  (`SlotLabelCell` больше не принимает `groupHeader`, `isFirstInGroup`
  удалена как неиспользуемая).
- `apps/backend/src/corrections/corrections.service.ts`
  (`toCorrectionDetailDto`) — явная сортировка `slots` по `requirement.order`.
- Backend-модель (`PackageRequirement`, `DocumentSlot`) и API-контракт не
  меняются — меняется только гарантия порядка элементов существующего поля
  `slots` в ответе.

## Влияние на качество

- Уровень риска: P3
- Затронутые маршруты: карточка корректировки `/corrections/[humanId]`
  (таблица «Комплектность пакета») — состав строк, без изменения кода
- Затронутые frontend-компоненты: `PackageCompleteness`/`SlotLabelCell`
  (`package-completeness.tsx`) — убран групповой заголовок
- Затронутые backend-модули: `database` (seed), `corrections`
  (`toCorrectionDetailDto` — явная сортировка `slots`)
- Затронутые API: нет (контракт `GET /corrections/:humanId` не меняется,
  меняется только гарантия порядка элементов `slots`)
- TDD-порядок: для сортировки — failing unit-тест на порядок `slots`
  (в т. ч. при перемешанном порядке вставки) -> реализация -> green; для
  seed-данных не применим
- Обязательные уровни проверки: backend unit-тест на сортировку слотов,
  пересидинг локальной БД (`bun run seed`), ручная проверка карточки
  корректировки
- Ручные проверки: после пересидинга открыть демо-корректировку в статусе
  «Черновик» — «Перечень комплекта МТР (ХС)» отображается отдельной строкой
  со своим файлом; таблица «Комплектность пакета» не показывает подпись
  «— выберите один вариант» ни над одной строкой
- План отката: `git revert` коммита правки + повторный `bun run seed`
