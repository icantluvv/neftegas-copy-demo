## Context

`apps/frontend/app/(private)/layout.tsx` — серверный компонент: проверяет сессию через `getMe()`, при 401/403/413 редиректит на `/login`, иначе рендерит `<>{children}</>` без какой-либо обвязки макета. Единственный существующий приватный маршрут — `apps/frontend/app/(private)/dashboard/page.tsx`.

Для клиентской логики выхода уже сгенерирован Kubb-хук `useLogout` (`apps/frontend/packages/api/base/codegen/hooks/authController/useLogout.ts`, дергает `POST /auth/logout`), аналогично `useLogin`, используемому в `apps/frontend/app/(public)/components/login-form.tsx`. Новый API не требуется — см. proposal.md.

В `apps/frontend/app/globals.css` уже определены, но нигде не используются shadcn-токены `--sidebar` / `--sidebar-foreground` (и `--sidebar-*` accent/border/ring), а также their `@theme inline` алиасы `--color-sidebar` / `--color-sidebar-foreground`, доступные в Tailwind как `bg-sidebar` / `text-sidebar-foreground`.

## Goals / Non-Goals

**Goals:**
- Добавить в `PrivateLayout` персистентную боковую панель шириной 1/5 экрана слева на десктопе, с тёмно-синим фоном и белым текстом, и кнопкой выхода внизу.
- На мобильных экранах скрыть сайдбар по умолчанию и дать доступ к нему через кнопку-бургер в левом верхнем углу, открывающую сайдбар на всю ширину экрана.
- Дать место для будущих пунктов навигации приватного контура, не проектируя лишнего.

**Non-Goals:**
- Полноценный adaptive-паттерн с промежуточными breakpoint'ами (планшет и т.п.) — только два состояния: десктоп (фиксированная колонка 1/5) и мобильный (скрыто/оверлей на всю ширину).
- Динамическое построение меню из конфигурации ролей/прав — сейчас один маршрут (`/dashboard`), поэтому список пунктов — статический массив в компоненте.
- Изменение backend/API — эндпоинт `/auth/logout` уже существует и не меняется.

## Decisions

- **Раскладка через flex, не CSS grid/`fixed`.** `PrivateLayout` оборачивает сайдбар и `children` в `<div className="flex min-h-svh">`, сайдбар — `<aside className="w-1/5 ...">`, контент — `<div className="w-4/5 ...">{children}</div>`. Просто и соответствует тому, что `layout.tsx` — единственная точка, где нужно сохранить структуру страницы; `fixed`-позиционирование не нужно, так как отдельного скролла контента поверх сайдбара не требуется.
- **Цвета — через существующие shadcn-токены `--sidebar`/`--sidebar-foreground`**, а не через хардкод `bg-[#...]` в компоненте. В `apps/frontend/app/globals.css` меняются значения `--sidebar` (тёмно-синий, единое значение и в `:root`, и в `.dark`, чтобы сайдбар не зависел от системной темы) и `--sidebar-foreground` (белый). Компонент использует Tailwind-классы `bg-sidebar text-sidebar-foreground`. Альтернатива — задать цвета инлайн в компоненте — отклонена: токены уже введены дизайн-системой (shadcn) именно для этого назначения и не используются нигде, вводить параллельный источник цвета избыточно.
- **Логика выхода — клиентский компонент `SidebarNav`**, а не действие в самом `layout.tsx` (который остаётся server component). Файл: `apps/frontend/app/(private)/components/sidebar-nav.tsx`, по аналогии с `apps/frontend/app/(public)/components/login-form.tsx`. `PrivateLayout` остаётся async server component и просто рендерит `<SidebarNav />`, сохраняя проверку сессии на сервере.
- **Выход — `useLogout` + `router.replace("/login")` в `onSuccess`, `toast.error` в `onError`.** Повторяет паттерн `LoginForm` (`useLogin` + `router.replace` + `sonner`), уже принятый в проекте, без изобретения нового способа уведомлений/навигации.
- **Активный пункт меню — через `usePathname()`** (без сторонней навигационной библиотеки): текущий пункт получает визуальное выделение (класс), явный сценарий поведения в spec не заявляется (не наблюдаемое требование, а деталь реализации), поэтому это решение design-уровня, не отдельное requirement.
- **Список пунктов меню — статический массив** `{ href, label }[]` внутри `SidebarNav` (сейчас один пункт — «Дашборд» → `/dashboard`). Вынесение в отдельный конфиг-файл не требуется при одном пункте; при добавлении новых разделов массив расширяется на месте.
- **Мобильный breakpoint — Tailwind `md` (768px)**, стандартный для проекта порог между мобильной и десктопной раскладкой. Ниже `md`: сайдбар скрыт по умолчанию, видна кнопка-бургер в левом верхнем углу; на `md` и шире: сайдбар — статичная колонка `w-1/5`, кнопка-бургер не отображается (`md:hidden` на кнопке). Переключение раскладки — на Tailwind-классах (`hidden md:flex` и т.п.), без `matchMedia`/`useEffect`, чтобы избежать гидратационных расхождений (SSR не знает реальную ширину экрана).
- **Открытое/закрытое состояние сайдбара на мобильном — локальный `useState<boolean>` в `SidebarNav`.** Простейший вариант для одного элемента UI без внешнего состояния; синхронизация между вкладками/компонентами не требуется. При открытии сайдбар рендерится как оверлей `fixed inset-0 z-50` шириной на весь экран (`w-full`), поверх контента; закрывается либо повторным нажатием кнопки-бургера, либо нажатием на пункт навигации.
- **Закрытие по пункту меню — общий обработчик `onClick` на каждом `Link` пункта навигации, вызывающий `setIsOpen(false)`.** Next.js `Link` сам выполняет переход; синхронный вызов `setIsOpen(false)` в том же обработчике закрывает оверлей без ожидания завершения навигации. На десктопе (`md` и шире) этот обработчик не имеет видимого эффекта, так как сайдбар там не оверлей, а постоянная колонка — состояние `isOpen` там не участвует в раскладке.

## Risks / Trade-offs

- [Фиксированная ширина `1/5` на очень узких десктопных/планшетных экранах, близких к breakpoint `md`, может сжать текст навигации] → Осознанный trade-off: ниже `md` сайдбар полностью скрывается за бургер-меню (см. Decisions), поэтому крайний случай — только узкий диапазон около самого breakpoint'а; при появлении жалоб — отдельный change.
- [Правка глобальных токенов `--sidebar`/`--sidebar-foreground` в `globals.css` теоретически затронет другие места, использующие эти классы] → Проверено: на момент написания design токены нигде в коде не используются (`grep` по `bg-sidebar`/`text-sidebar` пуст), риска регрессии нет.
- [Дублирование логики выхода, если в будущем появится второй способ выйти (например, из настроек)] → Не актуально сейчас (один вход в UI); при появлении второго места — выделить общий хук-обёртку `useLogoutAction`.
- [Мобильный оверлей на всю ширину экрана без крестика/`Escape`-закрытия может быть неочевиден пользователю] → Смягчено: закрытие доступно повторным нажатием кнопки-бургера и автоматически при выборе пункта навигации (см. specs/private-navigation); отдельная кнопка «Закрыть»/`Escape`-обработчик не заявлены и не проектируются в этом change.

## Тестовая стратегия

Риск: P2 (внутренняя навигационная UI-функциональность приватного контура без критичных прав/данных; кнопка выхода — единственный элемент с сайд-эффектом, но использует уже протестированный на backend эндпоинт).

TDD-порядок:
1. Failing component-тест `sidebar-nav.component.test.tsx`: рендер `SidebarNav`, проверка, что видна кнопка «Выйти» и пункт «Дашборд».
2. Реализация `SidebarNav` и подключение в `layout.tsx` → тест зелёный.
3. Failing component-тест на сценарий «Успешный выход»: клик по «Выйти» вызывает мутацию `useLogout` и после успеха — переход на `/login` (мокается `next/navigation` и Kubb-клиент/MSW-аналог по конвенции проекта, `useLogout` мокается на уровне мутации так же, как в существующих тестах `login-form`).
4. Реализация обработчика → тест зелёный.
5. Failing component-тест на сценарий «Ошибка при выходе»: мутация завершается ошибкой → показывается `toast.error`, редиректа нет.
6. Реализация обработчика ошибки → тест зелёный.
7. Failing component-тесты на мобильное поведение: сайдбар скрыт и видна кнопка-бургер по умолчанию на мобильной ширине viewport; клик по бургеру открывает сайдбар на всю ширину; повторный клик закрывает.
8. Реализация мобильной раскладки и `useState`-переключателя в `SidebarNav` → тесты зелёные.
9. Failing component-тест: на мобильном viewport при открытом сайдбаре клик по пункту навигации закрывает сайдбар.
10. Реализация `onClick`-обработчика на пунктах меню → тест зелёный.
11. Refactor при необходимости, без изменения покрытых сценариев.

Frontend Unit: не требуется — вся логика тривиальна и покрывается на component-уровне вместе с рендером.
Frontend Component (`*.component.test.tsx`, Vitest Browser Mode + Playwright): 7 сценариев выше (desktop-рендер, успешный выход, ошибка выхода, скрытие/бургер по умолчанию, открытие, закрытие по бургеру, закрытие по пункту меню) — основной способ проверки для P2. Component-тесты на мобильное поведение эмулируют мобильный viewport через Playwright `page.setViewportSize` (Vitest Browser Mode), не через JS-детекцию ширины.
Frontend E2E: не требуется отдельно — сквозной путь «логин → дашборд → выход» не выделяется в этом change как отдельный критический маршрут (P0/P1 не назначен); может быть добавлен позже вместе с E2E-покрытием логина, если появится.

Моки/фикстуры: мутация `useLogout` мокается через `vi.mock` на модуле `@/packages/api/base/codegen` (или эквивалентный паттерн, уже используемый в существующих тестах `error-boundary`/`login-form` — см. `apps/frontend/AGENTS.md` перед написанием тестов). Typed fixtures не требуются — нет доменных сущностей, только пользовательское действие.

Verification gates: `bun run typecheck`, `bun run lint`, `bun run test` (unit+component), `bun run build` (проверка, что `(private)` layout собирается) — все обязательны, так как меняется общий layout приватного контура.
