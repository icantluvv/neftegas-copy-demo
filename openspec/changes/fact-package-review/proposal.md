# Proposal: fact-package-review

## Проблема

Модуль «Факт» → экран «Файлы» (`/fact/files`) сейчас — заглушка
(`SectionPlaceholder`). Филиалы не имеют способа загрузить пакет документов
по направлениям работ (ДО, ТОиР, КР ПД, КР ХС) и провести его через
согласование ЦФО и ДТОиР, аналогично тому, как это устроено для
«Корректировки» (домен `corrections`). Без этого экрана факт выполнения работ
по направлениям не документируется и не проходит формальное согласование.

## Цель

Реализовать полноценный жизненный цикл «факт-пакета» — сущности,
аналогичной «Корректировке», но без периода (месяца/квартала): один
долгоживущий пакет на пару «Филиал × Направление», проходящий через циклы
доработка → повторная отправка сколько угодно раз, с собственным
человекочитаемым ID `FCT-000001` (отдельная последовательность от `COR-`).

Экран `/fact/files` в модуле «Факт»:

- 4 вкладки-направления: ДО (Диагностическое обследование), ТОиР
  (Техническое обслуживание и ремонт), КР ПД (Капремонт, подрядный способ),
  КР ХС (Капремонт, хозяйственный способ).
- Каталог из 7 форм документов (Акт выполнения работ, Акт выполнения услуги,
  КС-2, КС-3, Акт вовлечённости материалов, Счёт на оплату, Заявка на
  платёж). Направления ДО, ТОиР, КР ПД показывают все 7 форм; КР ХС —
  только формы 1, 5, 6, 7 (без форм приёмки у подрядчика — 2, 3, 4), так как
  при хозспособе подрядчика нет.
- Все формы направления для конкретного филиала образуют один факт-пакет.
  Каждая форма — «элемент пакета»/слот, копящий историю версий файла (версии
  никогда не удаляются).
- Направление на проверку выбранным ЦФО (из `FilialCFO`), согласование по
  каждому ЦФО независимо, замечания к форме, отметка «исправлено»,
  направление в ДТОиР после согласования всех выбранных ЦФО, финальное
  решение ДТОиР (согласовать/вернуть).

## Допущение: без периода — подтверждено пользователем

Черновик ЧТЗ поднимал открытый вопрос: привязан ли факт-пакет к отчётному
периоду (месяц/квартал), то есть может ли быть несколько последовательных
пакетов на одну пару «филиал + направление», или один долгоживущий пакет,
проходящий через циклы доработки бессрочно.

**Это решение уже принято и подтверждено пользователем (постановщиком
задачи), а не открытый вопрос для этого change**: факт-пакет — **один
долгоживущий пакет на пару «Филиал × Направление», без периода**, полностью
аналогичный «Корректировке» по механике многократной доработки/повторной
отправки. Реализация ниже полностью исходит из этого допущения; поле
`period` не вводится нигде — ни в модели данных, ни в API, ни в UI.

Остальные три допущения черновика ЧТЗ также зафиксированы как решённые:

- ХС/ПД — «ХС» = хозяйственный способ (без подрядчика), «ПД» = подрядный
  способ. Формы «Акт выполнения услуги», «КС-2», «КС-3» — только для ПД.
- Каталог форм для ДО и ТОиР — полный (все 7 форм), как для КР ПД.
- Согласование факт-пакета — та же двухступенчатая проверка (ЦФО → ДТОиР),
  что и у «Корректировки».

## Объём работ

### API (`api/src/`)

Новые схемы (`Direction`, `FactFormCode`, `FactPackage`, `FactPackageDetail`,
`FactPackageStatus`, `FactPackageCfoStatus`, `FactPackageForm`,
`FactFormVersion`, `FactPackageRemark`) и пути (`/fact-packages`,
`/fact-packages/{humanId}`, `/fact-packages/{humanId}/forms/{formCode}/versions`,
`/fact-packages/{humanId}/submit`, `/fact-packages/{humanId}/cfo/{cfoId}/approve`,
`/fact-packages/{humanId}/remarks`, `/fact-packages/{humanId}/remarks/{remarkId}/fix`,
`/fact-packages/{humanId}/remarks/{remarkId}`,
`/fact-packages/{humanId}/send-to-dtoe`,
`/fact-packages/{humanId}/final-decision`). Подробности — `design.md`
(`## API Shape`).

### Backend (`apps/backend/src/fact-packages/`)

Новый домен, параллельный `corrections`, по тому же архитектурному образцу
(entities, dto, mapper, service, controller, module). Переиспользует
`FilialCfoLink`, `RolesGuard`, паттерн файлового хранилища из `corrections`
(отдельная директория `uploads/fact-packages/...`). Домен `corrections` и его
таблицы не изменяются.

### Frontend (`apps/frontend/app/(private)/fact/files/`)

Полноценный экран вместо `SectionPlaceholder`: вкладки направлений, таблица
форм с фильтрацией по каталогу направления, загрузка версии (модалка),
отправка на проверку (выбор ЦФО), замечания и «исправлено» (Филиал), карточка
для ЦФО (замечание/согласование), карточка для ДТОиР (финальное решение +
аудит всех филиалов). Kubb-клиент генерируется из обновлённого контракта.

## Роли

Роли не меняются — переиспользуются существующие `FILIAL`, `CFO`, `DTOE`
(и `ADMIN` для аудита наравне с `DTOE`, как в `corrections`). Новых ролей не
заводится.

## Исключено из объёма работ

- Помесячная/поквартальная периодизация факт-пакетов (см. допущение выше).
- Изменение статусной модели или поведения существующего домена `corrections`.
- Смена типа факт-пакета (аналог `updateCorrectionType`) — направление
  факт-пакета не меняется после создания; при необходимости сменить
  направление филиал использует другой факт-пакет (Филиал × другое
  Направление).
- Уведомления через внешние каналы (email/push) — только внутрисистемные
  `Notification`, как у `corrections`.

## Связанные тикеты

Нет явного тикета `KT-*` — задача поставлена напрямую текстом ЧТЗ,
опубликованным как Artifact (см. `design.md`).
