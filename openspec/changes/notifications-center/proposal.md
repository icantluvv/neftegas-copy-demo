## Why

Бэкенд уже создаёт уведомления синхронно при каждом значимом событии жизненного цикла
корректировки (`NotificationsService`, `GET /notifications`, `POST /notifications/:id/open`),
но во фронтенде нет ни одного места, где пользователь мог бы их увидеть: колокольчика
в шапке нет, выпадающей панели нет, а пункт меню сайдбара «Уведомления» ведёт на
несуществующий маршрут `/notifications`. Пользователь не узнаёт о возврате
корректировки с замечанием иначе, чем случайно открыв карточку сам — при пятилетнем
горизонте документооборота и десятках корректировок в работе это означает пропущенные
дедлайны на доработку.

## What Changes

- Добавляется колокольчик уведомлений в правом верхнем углу шапки приватного контура:
  бейдж с числом непрочитанных (скрыт при нуле, «9+» при числе больше 9), фоновое
  обновление раз в 60 секунд.
- Добавляется выпадающая панель (popover, не модальное окно) по клику на колокольчик:
  заголовок «Уведомления» с текущим числом непрочитанных, последние 7 записей
  (дата/время, текст, визуальное выделение непрочитанных), пустое состояние «Новых
  уведомлений нет», ссылка «Все уведомления» на `/notifications`. Массовая пометка
  прочитанным в панели не дублируется — только со страницы `/notifications`. Клик по записи
  помечает её прочитанной и переходит на карточку соответствующей корректировки; клик
  вне панели или `Escape` закрывает её без побочных эффектов.
- Реализуется SSR-страница `/notifications` (полный архив, без ограничения в 7 записей):
  таблица «Дата» / «Сообщение» с выделением непрочитанных, кнопка «Открыть» в строке
  (помечает прочитанной и переходит на карточку), фильтр «Только непрочитанные»,
  кнопка «Отметить все прочитанными», пустое состояние «Уведомлений нет».
- Добавляется API-эндпоинт `POST /notifications/read-all` (массовая пометка прочитанным
  для текущего пользователя) — используется и панелью, и страницей.
- Добавляется маршрут-заглушка `/corrections/[humanId]`, на который ведут переходы из
  уведомлений — реализация самой карточки корректировки не входит в область этого
  change (см. «Вне области»).
- Уведомления о промежуточном согласовании отдельным ЦФО намеренно не создаются (уже
  так в текущей backend-логике — `recomputeStatusAfterCfoAction` не шлёт уведомление
  при переходе в `PARTIALLY_APPROVED`) — это подтверждающее ограничение, а не новое
  поведение.
- Автопометка уведомлений прочитанными при открытии карточки корректировки напрямую
  (минуя список уведомлений) НЕ реализуется — соответствует открытому вопросу
  исходного макета, по умолчанию принят вариант без автопометки.

## Capabilities

### New Capabilities

- `notifications`: колокольчик с бейджем непрочитанных, выпадающая панель последних 7
  уведомлений, полная страница `/notifications` (список, фильтр непрочитанных, массовая
  и точечная пометка прочитанным), переход по уведомлению на карточку корректировки.

### Modified Capabilities

_(нет — `private-navigation` уже описывает пункт меню «Уведомления» со ссылкой на
`/notifications`; сама страница по этому пункту становится рабочей, но требование
`private-navigation` не меняется)_

## Impact

- **Frontend**: новый общий header-компонент с колокольчиком и панелью (интегрируется
  в `apps/frontend/app/(private)/layout.tsx` рядом с `SidebarNav`), новый роут
  `apps/frontend/app/(private)/notifications/page.tsx` (SSR) с клиентским компонентом
  таблицы, новый роут-заглушка `apps/frontend/app/(private)/corrections/[humanId]/page.tsx`.
  Используются уже сгенерированные Kubb-хуки `useGetNotifications`/`useOpenNotification`
  из `apps/frontend/packages/api/base/codegen/**`; добавляется хук `useMarkAllNotificationsRead`
  после обновления OpenAPI-контракта и перегенерации кодогена.
- **Backend**: `apps/backend/src/notifications/` — новый метод `NotificationsService.markAllRead`
  и `NotificationsController.readAll` (`POST /notifications/:id/open` уже существует и не
  меняется). Изменений схемы БД не требуется — `Notification.isRead` уже есть.
- **API-контракт**: новый путь `api/src/paths/notifications-read-all.yaml`
  (`POST /notifications/read-all`), регистрация в `api/src/openapi.yaml`.
- **Внешние зависимости**: не вводятся. Создание уведомлений остаётся синхронным —
  выполняется в той же БД-транзакции, что и смена статуса корректировки/замечания
  (см. `design.md`, раздел о рассмотренной и отклонённой очереди сообщений).
- **Вне области**: полноценная карточка корректировки (`/corrections/[humanId]`
  реализуется как маршрут-заглушка, замещается отдельным будущим change), пагинация
  списка `GET /notifications` (риск роста списка отмечен как открытый вопрос в
  `design.md`, не блокирует эту фичу при текущем масштабе данных), push/email-каналы
  доставки уведомлений (только внутрисистемные).

## Влияние на качество

- **Уровень риска**: P1 — новый пользовательский маршрут и общий для всех ролей
  UI-элемент (колокольчик), но без изменения статусной модели корректировок и без
  затрагивания прав доступа к существующим данным.
- **Затронутые маршруты**: `/notifications` (новый), приватный layout `(private)/*`
  (добавление колокольчика в шапку), `/corrections/[humanId]` (новый, заглушка).
- **Затронутые frontend-компоненты**: новый `NotificationBell` (колокольчик + панель),
  новый `NotificationsPage`/`NotificationsTable`, `PrivateLayout`.
- **Затронутые backend-модули**: `notifications` (`NotificationsService`,
  `NotificationsController`).
- **Затронутые API**: `GET /notifications` (без изменений контракта, переиспользуется),
  `POST /notifications/:id/open` (без изменений), `POST /notifications/read-all` (новый).
- **TDD-порядок**: failing backend unit/e2e-тест на `markAllRead` → минимальная
  реализация → green; failing frontend component-тест на панель/таблицу →
  минимальная реализация → green → refactor.
- **Обязательные уровни проверки**: Backend Unit (`NotificationsService.markAllRead` —
  только свои уведомления, идемпотентность), Backend Feature/E2E
  (`POST /notifications/read-all` через HTTP), Frontend Component (колокольчик:
  бейдж/панель/пустое состояние; таблица `/notifications`: фильтр, выделение,
  пустое состояние), Frontend E2E (клик по колокольчику → открытие панели → переход
  по записи; страница `/notifications` → «Отметить все прочитанными» → бейдж
  обнуляется).
- **Ручные проверки или waiver**: ручная проверка фонового опроса раз в 60 секунд
  (обоснованный waiver — таймер не покрывается E2E, дергается напрямую unit-тестом
  на конфигурацию `refetchInterval`).
- **План отката**: изменения аддитивны (новый эндпоинт, новые маршруты, новый
  UI-компонент), схема БД не меняется — откат равносилен revert соответствующих
  коммитов/PR без миграций назад.
