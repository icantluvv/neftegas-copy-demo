## Context

`apps/frontend/app/(private)/dashboard/page.tsx` уже реализует `role-scoped-sections`:
единый маршрут `/dashboard`, серверный switch по роли на
`FilialDashboard`/`CfoDashboard`/`DtoeDashboard`. До этого change `CfoDashboard`
(`apps/frontend/app/(private)/dashboard/components/cfo-dashboard.tsx`) запрашивал
`getCorrectionStatsCfo()` только ради 4 плиток статистики и guard-логики (403 →
`AccessDeniedScreen`, 401 → `null`) — без графика, фильтров и таблицы, хотя
аналогичный экран для роли FILIAL (`FilialCorrectionsOverview`,
`filial-corrections-overview`) уже реализован ранее.

`apps/backend/src/corrections/corrections.service.ts` `findAll` (`GET
/corrections`) уже скоупит список для роли CFO через `innerJoin('c.cfoStatuses',
'myStatus', 'myStatus.cfoId = :myCfoId')` и поддерживает `query.filialId` — то есть
backend был полностью готов отдавать всё необходимое для фильтруемой таблицы, не
хватало только frontend-компонента, потребляющего этот эндпоинт с нужной
группировкой.

`apps/frontend/packages/api/base/codegen/types/CorrectionListItem.ts` уже включает
`myCfoStatus?: CfoStatusValue2 | null` — статус конкретно этого ЦФО по каждой
корректировке в списке, заполняется backend'ом только для роли CFO
(`corrections.service.ts`, `findAll`, L132-143). Это ключевое отличие от
`FilialCorrectionsOverview`, где группировка ведётся по общему `CorrectionStatus2`
корректировки — для ЦФО ЧТЗ (раздел 2.4) явно требует различать «статус пакета» и
«статус нашего ЦФО» как две независимые оси.

При разведке для этого change обнаружено, что кнопка «Оставить замечание к
элементу» (`ReturnRemarkDialog`, вызывается из `RemarksActionBar` в
`remarks-list.tsx`) никогда не передавала `relatedSlotId`, хотя тип
`RemarkCreateInput` его поддерживает, а `RemarkCreateDto` на бэкенде принимает —
Kubb-кодогену и контракту ничего не требовалось менять, отсутствовало только
использование поля во frontend-компоненте. Аналогично обнаружено, что
`cfoApprove`/`cfoReturn` не проверяли `myStatus.status === PENDING` — guard
существовал только на фронте (`permissions.ts`, `canApproveAsCfo`/`canReturnAsCfo`).

## Goals / Non-Goals

**Goals:**
- Дать роли CFO рабочий `/dashboard`: обзор направленных корректировок,
  визуальную сводку по статусу СВОЕГО ЦФО, фильтр по филиалу.
- Исправить `relatedSlotId` в форме замечания и переместить кнопку в строку
  элемента пакета — без этого форма создаёт «сиротские» замечания, не
  привязанные ни к одному элементу, что делает бессмысленной саму идею «замечание
  к элементу», описанную и в ЧТЗ Филиала, и в ЧТЗ ЦФО.
- Закрыть пробел backend-guard'а `PENDING`, обнаруженный при разведке —
  устранить реальную возможность гонки состояний, а не только полагаться на
  frontend-дизейбл кнопки.
- Переиспользовать существующие backend-эндпоинты (`GET /corrections`,
  `GET /corrections/stats/cfo`) без изменений контракта.

**Non-Goals:**
- Не вводится маршрут `/cfo` (см. Decision ниже, тот же выбор, что и для
  Филиала).
- Не вводятся `/org/filials`/`/org/cfos` backend-эндпоинты — справочник
  филиалов для фильтра строится клиентски.
- Не переделывается механика модального окна формы замечания в
  разворачивающийся инлайн-блок под строкой — см. Decision.
- Не меняется поведение ДТОиР-кабинета (вне scope этого change).

## Decisions

### `/dashboard` с рендерингом по роли остаётся, `/cfo` не вводится

Тот же выбор и то же обоснование, что уже принято и заархивировано для Филиала
(`filial-corrections-overview/design.md`, раздел «`/dashboard` с рендерингом по
роли остаётся, `/filial` не вводится») — `role-scoped-sections` уже даёт
содержательное различие кабинетов без физического разделения маршрута.
Согласованность между «сёстринскими» кабинетами (Филиал/ЦФО/ДТОиР) важнее
буквального следования ЧТЗ по частям.

### Группировка доната — по `item.myCfoStatus`, не по общему `CorrectionStatus2`

Рассмотрено: скопировать `STAGE_GROUPS` из `FilialCorrectionsOverview` (5→4
укрупнённые группы общего статуса пакета). Отклонено — ЧТЗ раздел 2.4 прямо и
неоднократно подчёркивает, что «статус пакета» и «статус нашего ЦФО» — разные
величины, которые могут расходиться (пакет в статусе «На проверке ЦФО» в целом,
но конкретно для этого ЦФО уже «Согласовано»), и именно вторая величина отвечает
на вопрос «мне лично нужно что-то делать по этой строке прямо сейчас» — главная
цель донат-графика и плиток статистики этого экрана. Выбрана группировка по
`CfoStatusValue2` (`PENDING`/`RETURNED`/`APPROVED`, 3 группы) — она совпадает по
смыслу и по цветам с уже принятой семантикой плиток `CfoDashboard`
(«На проверке у нас»/«Мы вернули»/«Мы согласовали»).

### Фильтр по филиалу и фильтр по статусу ЦФО — независимые, не единое поле

`FilialCorrectionsOverview` использует единый `filterValue: string` с префиксами
(`"group:<key>"`/`"all"`), потому что там только одна ось фильтрации. У ЦФО ЧТЗ
(раздел 2.3) явно описывает два независимых фильтра, применяемых одновременно
(«У ЦФО может быть привязано сразу несколько филиалов... фильтр нужен, чтобы
разбирать пакеты одного филиала подряд»). Реализованы два раздельных `useState`
(`statusFilter`, `filialFilter`), таблица фильтруется пересечением обоих условий
— единое поле здесь дало бы неверное поведение (выбор филиала сбрасывал бы ранее
выбранный статус, и наоборот).

### Список филиалов для фильтра — выводится клиентски из уже загруженного списка корректировок

ЧТЗ (раздел 2.3) требует ограничить список фильтра только филиалами, реально
привязанными к этому ЦФО. Список корректировок (`GET /corrections`) уже
естественным образом содержит только корректировки, направленные этому ЦФО —
множество различных `item.filial` в этом списке автоматически совпадает с
множеством привязанных филиалов (при условии, что каждый привязанный филиал хотя
бы раз направил корректировку этому ЦФО; филиал без единой направленной
корректировки этому ЦФО не появится в фильтре — признанный, задокументированный
компромисс, не блокирует change при текущем демо-масштабе данных, где у каждого
ЦФО есть направленные корректировки от всех привязанных филиалов). Альтернатива —
новый `GET /org/filials?cfoId=` — вынесена за пределы `cfo-cabinet` вместе с
остальным `org`-CRUD (см. `filial-corrections-overview`, тот же прецедент).

### Кнопка «Оставить замечание к элементу» — модальное окно в строке, не разворачивающийся блок

ЧТЗ (раздел 3.3) описывает раскрывающийся блок прямо под строкой элемента, без
модального окна. В `apps/frontend/src/components/ui` есть только `Dialog` —
нет `Collapsible`/`Popover`/`Accordion`. Рассмотрено: реализовать инлайн-раскрытие
вручную (локальный `useState<boolean>` на строку + условный рендер формы как
второй `<tr>` под строкой в `DataTable`). Отклонено ради этого change — `DataTable`
(`apps/frontend/src/components/ui/data-table`) обёрнут над `@tanstack/react-table`
без встроенной поддержки expandable rows, добавление этой возможности — отдельная
по объёму работа над переиспользуемым UI-примитивом, непропорциональная данному
изменению. Оставлен уже существующий `Dialog`, кнопка перенесена в строку и
получила `slotId`/`slotLabel` — пользовательский результат эквивалентен (форма
жёстко привязана к конкретному элементу, открывается и закрывается без перехода
на другой экран), отличается только визуальное представление (модальное окно
вместо инлайн-блока). Задокументировано как явное отклонение в `proposal.md`.

### «Оставить замечание к элементу» разделено на создание замечания и финализацию возврата

Первая версия этого change (см. историю коммитов) реализовала кнопку «Оставить
замечание к элементу» как атомарное действие: сохранение формы сразу переводило
корректировку в `RETURNED_FOR_REVISION`, а статус ЦФО — в `RETURNED`. Пользователь
протестировал прототип вручную (см. скриншоты в диалоге) и explicitly указал, что
после одного замечания кнопки «Оставить замечание»/«Согласовать» пропадали во
всех строках сразу — ЦФО не мог просмотреть весь пакет и отметить проблемы в
нескольких файлах за один заход. Запрошено явно: разрешить несколько замечаний
за один заход (альтернатива — оставить как есть — отклонена пользователем).

Решение — развести на два независимых бэкенд-действия:
- `leaveRemark` (`POST /corrections/{humanId}/remarks`) — создаёт `Remark(OPEN)`,
  не трогает `Correction.status`/`CorrectionCfoStatus.status`. Guard идентичен
  прежнему guard'у «можно оставить замечание» (CFO: `myStatus.status ===
  PENDING`; DTOE: `correction.status === UNDER_DTOE_REVIEW`) — семантика «когда
  можно оставить замечание» не изменилась, изменился только побочный эффект.
- `cfoReturn`/`dtoeReturn` (те же маршруты `POST .../cfo-return`/`.../dtoe-return`,
  но без тела запроса) — финализируют возврат: требуют, чтобы у текущего
  проверяющего уже было ≥1 замечание в статусе `OPEN` на этой корректировке
  (иначе `400`), и только тогда меняют статусы + уведомляют филиал со списком
  всех оставленных замечаний одним сообщением (было — одно замечание на одно
  уведомление).

Frontend: `canLeaveRemarkAsCfo`/`canLeaveRemarkAsDtoe` (переименованы из
`canReturnAsCfo`/`canReturnAsDtoe`, логика не изменилась) продолжают гейтить
кнопку в строке пакета (`PackageCompleteness`/`LeaveRemarkCell`, вызывает
`useLeaveRemark`). Новые `canFinalizeReturnAsCfo`/`canFinalizeReturnAsDtoe`
(требуют ≥1 `OPEN`-замечания этого проверяющего в `detail.remarks`) гейтят
новую кнопку «Вернуть на доработку» — она возвращена в общую `RemarksActionBar`
(`remarks-list.tsx`), рядом с «Согласовать»/«Направить в ДТОиР», поскольку это
теперь действие уровня всей корректировки, а не конкретного элемента пакета.

Явно не введено: возможность отредактировать/удалить уже оставленное открытое
замечание перед финализацией (кроме уже существующего «Удалить» для автора) —
не запрашивалось, вне scope. Кнопка «Согласовать» осталась доступна даже после
того, как ЦФО уже оставил замечания (не только когда их 0) — `cfoApprove` и
раньше автоматически закрывал все открытые замечания этого ЦФО при согласовании
(строки 438-450 сервиса), так что «оставил замечания, но передумал и согласовал»
уже корректно поддерживалось без дополнительных правок guard'а.

### Заголовок кабинета — без имени ЦФО

ЧТЗ показывает в заголовке имя подразделения («Кабинет ЦФО «АНГНКС»»).
`AuthUser`/`GetMe` (`api/src/openapi.yaml`) возвращает только `cfoId: number | null`,
не объект `Cfo` с `name`. Получить имя можно было бы из `detail.cfoStatuses` любой
уже загруженной корректировки, но на пустом кабинете (ни одной направленной
корректировки) это ничего не даст. Расширение контракта `GetMe` ради одной
подписи заголовка — непропорционально этому change; оставлен нейтральный
заголовок «Кабинет ЦФО».

## API Shape

- `GET /corrections?pageSize=100` — уже возвращает `myCfoStatus` для роли CFO
  и поддерживает клиентский `filial`/`correctionType` через `items[].filial`,
  `items[].correctionType`. Контракт не менялся.
- `GET /corrections/stats/cfo` — без изменений, только переименованы подписи
  плиток на фронте.
- `POST /corrections/{humanId}/cfo-approve` — поведение сужено (см. Backend
  guard ниже), схема запроса/ответа не менялась.
- **Новое**: `POST /corrections/{humanId}/remarks` (`leaveRemark`) — роли CFO
  и DTOE. Тело — `RemarkCreateInput` (без изменений схемы, поле уже
  существовало). Ответ — `CorrectionDetail`, без изменения статусов
  корректировки/проверяющего. Guard: CFO — `myCfoStatus.status === PENDING`
  (`403` без строки статуса, `400` если не `PENDING`); DTOE —
  `correction.status === UNDER_DTOE_REVIEW` (`400` иначе).
- **Изменено**: `POST /corrections/{humanId}/cfo-return`,
  `POST /corrections/{humanId}/dtoe-return` — `requestBody` убран (эндпоинты
  больше не принимают `RemarkCreateInput`). Финализируют возврат: требуют ≥1
  замечания в статусе `OPEN` от текущего проверяющего (`400` иначе), помимо
  прежнего guard'а «на рассмотрении у этого проверяющего».

### Backend guard: `cfoApprove`/`cfoReturn` — проверка `PENDING`

- **Файл**: `apps/backend/src/corrections/corrections.service.ts`.
- **Было**: `if (!(user.role === Role.CFO && myStatus)) throw new ForbiddenException()`.
- **Стало**: дополнительно `if (myStatus.status !== CfoStatusValue.PENDING) throw
  new BadRequestException(...)` — до входа в `this.dataSource.transaction(...)`,
  стиль ошибки согласован с уже существующим `sendToDtoe` (тоже
  `BadRequestException` для нарушенного guard-условия статуса, не
  `ConflictException` — в проекте нет прецедента использования 409).
- **Обратная совместимость**: сужение принимаемых состояний — ранее ошибочно
  успешные повторные вызовы теперь отклоняются `400`; ни один корректный путь
  (единственный вызов при `PENDING`) не меняется.

## Open Questions

- Список филиалов для фильтра строится из уже загрученного списка корректировок
  (см. Decision) — если появится ЦФО с привязанным, но ни разу не
  воспользовавшимся филиалом, тот не попадёт в фильтр. Нужен ли отдельный
  справочный эндпоинт `GET /org/filials?cfoId=` — не блокирует текущий scope,
  открытый вопрос для будущего `org`-CRUD change.
- Открытые вопросы самого ЧТЗ (`docs/tz/cfo-cabinet.md`, раздел 7) —
  редактирование/отзыв замечания, пересмотр решения ЦФО после возврата другим
  ЦФО, экспорт в Excel, объединение дублирующих замечаний от разных ЦФО — не
  решены и не входят в этот change.
