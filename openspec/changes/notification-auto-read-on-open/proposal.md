## Why

`docs/tz/filial-cabinet.md` (раздел 6.6) держал вопрос «помечать ли
уведомления прочитанными автоматически при открытии карточки
соответствующей корректировки?» открытым и фиксировал вариант по умолчанию
«без автопометки». Это решение уже было формализовано текстом требования
«Пометка прочитанным только по явному действию пользователя» в
`openspec/specs/notifications/spec.md` и реализовано в коде (корректировка,
открытая напрямую, не через клик по уведомлению, не помечала связанные
уведомления прочитанными).

Ответ заказчика получен и меняет решение на противоположное: автопометка —
да. Первая реализация ставила пометку на монтирование карточки
(`useEffect`) и одинаково работала независимо от способа попадания на неё,
включая прямой заход по ссылке. Ревью выявило, что это шлёт запрос на
пометку при каждом заходе на уже прочитанную карточку (обновление страницы,
переход назад/вперёд, повторный визит) — по решению после ревью пометка
теперь привязана не к отображению карточки, а к клику по элементу
интерфейса, ведущему на неё; прямой заход в обход интерфейса приложения
уведомления не помечает (см. `design.md`, «Decisions» и «Risks»).

## What Changes

- При переходе на карточку корректировки (`/corrections/{humanId}`) по
  клику на элементе интерфейса — записи уведомления (в панели колокольчика
  или на странице `/notifications`) либо кнопке «Открыть» в обзорной
  таблице дашборда — все уведомления текущего пользователя, связанные с
  этой корректировкой, автоматически помечаются прочитанными.
- Правило «открытие панели без клика по записи не меняет прочитанность»
  (первая часть прежнего требования) сохраняется без изменений.
- Прямой заход на карточку в обход перечисленных элементов интерфейса
  (ручной ввод URL, внешняя ссылка, навигация назад/вперёд, обновление уже
  открытой страницы) уведомления не помечает — сознательное сужение
  сценария после ревью, см. `design.md`.
- Новый backend-эндпоинт `POST /notifications/by-correction/{correctionId}/read`
  — массовая идемпотентная пометка прочитанным уведомлений текущего
  пользователя по одной корректировке.
- Фронтенд вызывает этот эндпоинт из общего хука
  `useMarkCorrectionNotificationsRead`, подключённого в обработчиках клика
  в трёх местах (панель уведомлений, страница `/notifications`, кнопка
  «Открыть» в дашборде), и инвалидирует кэш списка уведомлений только когда
  запрос реально что-то изменил (`updatedCount > 0`), чтобы бейдж
  колокольчика обновился без ожидания фонового опроса (раз в 60 секунд) и
  без лишнего рефетча, когда нечего было помечать.

## Capabilities

### Modified Capabilities

- `notifications`: требование «Пометка прочитанным только по явному
  действию пользователя» переименовано и переформулировано — клик по
  элементу интерфейса, ведущему на карточку корректировки, теперь помечает
  связанные уведомления прочитанными (было: только клик по самой записи
  уведомления); заход на карточку в обход интерфейса приложения по-прежнему
  не помечает; сценарий «открытие панели без клика» не изменился.

## Impact

- **Frontend**:
  `apps/frontend/src/hooks/use-mark-correction-notifications-read.ts`
  (новый хук), `apps/frontend/src/components/notification-bell/notification-bell.tsx`,
  `apps/frontend/app/(private)/notifications/components/notifications-content.tsx`,
  `apps/frontend/app/(private)/dashboard/components/open-correction-link.tsx`
  (новый компонент), `apps/frontend/app/(private)/dashboard/components/{filial-corrections-overview.tsx,cfo-corrections-overview.tsx}`.
- **Backend**: `apps/backend/src/notifications/notifications.service.ts`
  (`markReadByCorrection`), `notifications.controller.ts`
  (`POST by-correction/:correctionId/read`).
- **API-контракт**: новый путь
  `POST /notifications/by-correction/{correctionId}/read`
  (`api/src/paths/notifications-by-correction-correction-id-read.yaml`),
  зарегистрирован в `api/src/openapi.yaml`. Kubb-клиент перегенерирован
  (`useMarkNotificationsReadByCorrection`).
- **Обратная совместимость**: аддитивное изменение контракта; поведение
  существующих эндпоинтов (`POST /notifications/{id}/open`,
  `POST /notifications/read-all`) не менялось.

## Влияние на качество

- Уровень риска: **P1** — меняет уже опубликованное и реализованное
  поведение (реверс требования спецификации), затрагивает счётчик
  непрочитанных на колокольчике, видимый на каждой приватной странице всем
  трём ролям.
- Затронутые маршруты: `/corrections/{humanId}` (побочный эффект открытия).
- Затронутые frontend-компоненты: `CorrectionDetailView`, косвенно
  `NotificationBell` (обновление бейджа через инвалидацию кэша).
- Затронутые backend-модули: `notifications` (новый метод и роут).
- Затронутые API: `POST /notifications/by-correction/{correctionId}/read`
  (новый).
- TDD-порядок: не соблюдён — реализация велась напрямую по коду; тестов на
  момент фиксации change нет.
- Обязательные уровни проверки: Backend Unit (идемпотентность, изоляция по
  пользователю и по корректировке), Frontend Component
  (`useMarkCorrectionNotificationsRead` инвалидирует кэш только при
  `updatedCount > 0`), Frontend E2E (сквозной сценарий: непрочитанное
  уведомление → клик по нему → бейдж уменьшился; обновление уже открытой
  карточки не отправляет повторный запрос).
- Ручные проверки: подтверждено `curl` под демо-аккаунтом
  `filial.donbassgaz@demo.local` — `POST /notifications/by-correction/1/read`
  вернул `{"updatedCount":5}` для корректировки с пятью непрочитанными
  уведомлениями пользователя. Проверка фактического обновления бейджа в
  браузере не выполнена — waiver, см. `test-plan.md` (то же
  инфраструктурное ограничение окружения, что и в `filial-corrections-overview`:
  нет Chromium в dev-контейнере для Playwright/Vitest Browser Mode).
- План отката: изменения аддитивны на уровне контракта (новый путь) и
  локальны на фронте (общий хук и его подключение в трёх точках клика) — откат
  равносилен revert соответствующих коммитов; спецификацию потребуется
  откатить синхронно, чтобы не разойтись с кодом повторно.
