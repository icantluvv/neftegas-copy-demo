# dtoir-nav-sections

## Why

По референсному макету (скриншоты интерфейса) и Регламенту-СОВОФ-ХХХХХ-2026
(планирование и организация ДТОиР) верхний уровень интерфейса — 4
переключаемые вкладки рабочей области: «План на 2027», «Выполнение»,
«Корректировка», «Факт». Вкладки расположены в шапке над рабочей областью (не
в боковом меню) и переключают контент под собой на дашборд своего раздела,
как отдельные листы одного экрана. Боковое меню при этом сохраняет только
разделы, не являющиеся переключением рабочей области: «Рабочий стол»,
«Создать корректировку», «Уведомления».

Backend и API-контракт поддерживают сегодня только домен согласования
корректировок (`corrections`) — сущностей годового плана, мониторинга
выполнения и план/факт-отчётности в системе нет (см. `apps/backend/src` и
`api/src/paths`). Полноценная реализация разделов «План на 2027»,
«Выполнение», «Факт» требует отдельных доменов, миграций БД и правок
OpenAPI-контракта — самостоятельных change'ей вне текущего скоупа.

Это изменение — навигационный каркас с новой структурой: верхняя панель
вкладок вместо пунктов бокового меню. Три вкладки («План на 2027»,
«Выполнение», «Факт») ведут на страницы-заглушки с честным статусом «в
разработке» и перечнем форм документов Регламента, которые будут привязаны к
разделу в будущих change'ах. Вкладка «Корректировка» переиспользует
существующую страницу `/dashboard` (дашборд корректировок по роли) без
изменения её поведения.

Модули полностью изолированы: у каждого — своя «домашняя» страница (то, что
открывается по клику на вкладку) и свои пункты бокового меню; ничего общего
между модулями не подразумевается по умолчанию. В частности, «Рабочий стол» в
боковом меню — это не отдельная страница, а переход на домашнюю страницу
*текущего* активного модуля (а не всегда на `/dashboard`), а «Уведомления»
показаны только внутри модуля «Корректировка», потому что сегодня уведомления
генерируются исключительно по событиям корректировок — у остальных модулей
собственных уведомлений в системе пока нет.

Модуль «План на 2027» дополнительно получил собственную кнопку «Создать
корректировку» — визуально идентичную кнопке модуля «Корректировка» (та же
форма, те же названия элементов пакета документов: «Excel корректировка»,
«Пакет документов», «Счета на оплату» — см. глоссарий), но полностью
независимую: без вызова API, без сохранения — раздел планирования ещё не
имеет своего домена на бэкенде, поэтому кнопка визуальный макет-заглушка, а
не рабочая функциональность, разделяющая данные с «Корректировкой».

## What Changes

- В `apps/frontend/app/(private)/constants.ts` состав интерфейса построен
  вокруг понятия «модуль» (`ModuleTab`, элемент `topTabs`): у каждого модуля
  («План на 2027» `/planning`, «Выполнение» `/execution`, «Корректировка»
  `/dashboard` + `/corrections/*`, «Факт» `/fact`) — свой набор пунктов
  бокового меню (`sidebarItems`), видимых только пока пользователь находится
  внутри этого модуля. «Рабочий стол» — единственный пункт, общий для всех
  модулей по смыслу, но не по назначению: его `href` вычисляется динамически
  как `href` активного модуля (`getSidebarItems`), поэтому клик по «Рабочий
  стол» из «Плана на 2027» остаётся на `/planning`, а не уводит на
  `/dashboard` («Корректировку»).
- Модуль «Корректировка» — единственный с непустым `sidebarItems` пока:
  «Создать корректировку» (`/corrections/create`, роль FILIAL) и
  «Уведомления» (`/notifications`) — уведомления сегодня генерируются только
  по событиям корректировок, поэтому пункт принадлежит именно этому модулю, а
  не общий. У «План на 2027», «Выполнение», «Факт» сейчас `sidebarItems: []`
  — при живой работе с разделом эти модули получат свои собственные пункты
  (включая, возможно, собственные уведомления) в последующих change'ах.
- Модуль «План на 2027» получил в `sidebarItems` пункт «Создать
  корректировку» (`/planning/create`, роль FILIAL). Страница использует новый
  компонент `CreateCorrectionStub` (`apps/frontend/src/components/
  create-correction-stub`) — визуальная копия реальной формы
  `CreateCorrectionForm` (`apps/frontend/app/(private)/corrections/create/
  components/create-correction-form.tsx`): тот же выбор типа корректировки и
  тот же список элементов пакета документов, но без запросов к API
  (`useCreateCorrection`/`useGetCorrectionTypes` не используются) — кнопка
  «Создать» задизейблена с пояснением «раздел в разработке», список типов и
  элементов пакета статический. Компонент переиспользуемый — рассчитан на
  такое же подключение к «Выполнению» и «Факту» в будущем.
- Функция `findActiveModule(pathname)` определяет, какому модулю принадлежит
  текущий маршрут (по `href` или `matchPrefixes`, например `/corrections`
  для модуля «Корректировка») — используется и в `TopTabs` (подсветка
  активной вкладки), и в `SidebarNav` (состав бокового меню). Так переход на
  «внутреннюю» страницу модуля (например, «Создать корректировку» из
  «Корректировки») не переключает активный модуль — вкладка сверху остаётся
  подсвеченной, а боковое меню — тем же, что и в модуле.
- Добавлен компонент `TopTabs` (`apps/frontend/src/components/top-tabs`) —
  горизонтальная панель вкладок в шапке `app/(private)/layout.tsx`, рядом с
  колокольчиком уведомлений.
- `SidebarNav` больше не рендерит статический список — состав меню зависит от
  активного модуля через `getSidebarItems(pathname)`.
- Компонент `SectionPlaceholder` (`apps/frontend/src/components/
  section-placeholder`), рендерящий заголовок, описание раздела и список форм
  документов Регламента со ссылкой на соответствующее приложение/пункт
  (например, «Приложение Б.4») — без изменений с предыдущей версии этого
  change.
- Страницы App Router `app/(private)/planning/page.tsx`,
  `app/(private)/execution/page.tsx`, `app/(private)/fact/page.tsx` — без
  изменений с предыдущей версии этого change.
- Backend, API-контракт, страница `/dashboard` и её данные не изменяются.

## Capabilities

Навигационный каркас без новой бизнес-логики и без данных с бэкенда —
наблюдаемое поведение ограничено расположением переключателей (верхние
вкладки вместо пунктов бокового меню) и статическим текстом
страниц-заглушек. Delta specs не создаются (`skip_specs: true`).

## Влияние на качество

- Уровень риска: P3
- Затронутые маршруты: `/planning`, `/execution`, `/fact` (страницы без
  изменений, доступ теперь через верхнюю вкладку), `/dashboard` (доступен и
  через «Рабочий стол» в боковом меню, и через вкладку «Корректировка»)
- Затронутые frontend-компоненты: `SidebarNav` (меню зависит от активного
  модуля), новый `TopTabs`, `topTabs`/`findActiveModule`/`getSidebarItems` в
  `constants.ts`
- Затронутые backend-модули: нет
- Затронутые API: нет
- TDD-порядок: не применим — статический контент без бизнес-логики
- Обязательные уровни проверки: Static (lint, typecheck), Component-тесты на
  `SidebarNav` и `TopTabs`
- Ручные проверки: переход по всем 4 верхним вкладкам под ролью FILIAL —
  каждая открывает свою рабочую область, активная вкладка подсвечивается;
  «Рабочий стол» ведёт на домашнюю страницу текущего модуля (не переключает
  модуль); «Создать корректировку» и «Уведомления» модуля «Корректировка»
  видны только внутри него; «Создать корректировку» модуля «План на 2027»
  ведёт на `/planning/create` и не вызывает API создания корректировок
- План отката: `git revert` коммита правки

## Открытые вопросы (для последующих change'ей)

- **[К]** Критерии статуса объекта в разделе «Выполнение» («Выполняется» /
  «Приостановлено» / «Отменено») не определены Регламентом — требуют решения
  владельца процесса перед реализацией данных.
- Домены `planning`, `execution`, `fact` (объекты плана, МТР, план/факт по
  стоимости и срокам) — предмет отдельных OpenSpec change'ей с правкой
  `api/src/openapi.yaml` и новых backend-сущностей.
