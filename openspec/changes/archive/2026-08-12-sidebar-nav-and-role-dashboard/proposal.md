## Why

Боковая навигация приватного контура (`SidebarNav`) сейчас — пустой каркас: список пунктов меню (`navItems`) пуст, нет ни брендинга компании, ни блока профиля пользователя. Одновременно ролевые разделы приватного контура (`/filial`, `/cfo`, `/dtoe`) реализованы как три параллельных маршрута-заглушки с раздельными layout'ами и защитой по роли — при росте функциональности каждого раздела это дублирует общий каркас страницы и не даёт единой точки входа «Рабочий стол», на которую должен вести пункт меню сайдбара. Нужно одновременно наполнить сайдбар (брендинг, рабочая навигация, блок профиля с данными из SSR-сессии, выход) и заменить три отдельных ролевых маршрута на единую страницу `/dashboard`, которая рендерит нужный ролевой дашборд по роли текущего пользователя.

## What Changes

- В `SidebarNav` добавляется верхний блок брендинга: круглый логотип-плейсхолдер без изображения и название компании «Черноморнефтегаз».
- Пункты меню наполняются реальными ссылками (`next/link`): «Рабочий стол» → `/dashboard`, «Уведомления» → `/notifications` (создание самой страницы уведомлений — вне области этого change, пункт меню — рабочая ссылка на предполагаемый маршрут).
- В нижней части сайдбара добавляется блок профиля: круглая иконка-плейсхолдер с инициалами ФИО, полное ФИО пользователя, кнопка «Выйти» (уже реализованная логика выхода переиспользуется без изменений).
- Данные пользователя для блока профиля (ФИО и далее) `SidebarNav` больше не запрашивает сам — они приходят пропом из серверного `PrivateLayout`, который уже вызывает `getMe()` на SSR.
- **BREAKING**: маршруты `/filial`, `/cfo`, `/dtoe` (страницы-заглушки и их layout'ы с ролевой защитой) удаляются и заменяются единым маршрутом `/dashboard`, который на сервере определяет роль текущего пользователя (из той же SSR-сессии) и условно рендерит один из компонентов ролевого дашборда: `FilialDashboard`, `CfoDashboard` или `DtoeDashboard`. Каждый компонент дашборда самостоятельно выполняет свои запросы к бэкенду.
- Редирект после успешного входа (`login-form.tsx`) перестаёт вести на ролевые маршруты (`/filial`, `/cfo`, `/dtoe`) и всегда ведёт на `/dashboard` для ролей `FILIAL`, `CFO`, `DTOE`.
- Ролевая защита данных остаётся на бэкенде: каждый ролевой дашборд по-прежнему обращается к своим (уже существующим) ролевым эндпоинтам статистики, которые проверяют роль на сервере — это не даёт пользователю получить чужие данные, даже если он локально подменит рендер.

## Capabilities

### New Capabilities

_(нет — обе затронутые capability уже описаны в незаархивированных changes `add-private-sidebar-nav` и `align-login-role-redirect`; см. Modified Capabilities)_

### Modified Capabilities

- `private-navigation`: добавляется брендинг сайдбара (логотип, название компании), реальные ссылки пунктов меню, блок профиля пользователя (аватар-инициалы, ФИО) с данными из SSR-сессии, переданными пропом.
- `role-scoped-sections`: три отдельных ролевых маршрута (`/filial`, `/cfo`, `/dtoe`) с раздельной защитой заменяются единой страницей `/dashboard`, которая на сервере определяет роль пользователя и рендерит соответствующий ролевой дашборд; ролевая защита переносится с уровня маршрута на уровень условного рендеринга + ролевые бэкенд-эндпоинты внутри дашборда.

## Impact

- **Frontend**: `apps/frontend/app/(private)/components/sidebar-nav.tsx` (брендинг, пункты меню, блок профиля, проп с данными сессии), `apps/frontend/app/(private)/layout.tsx` (передача результата `getMe()` пропом в `SidebarNav`), `apps/frontend/app/(public)/components/login-form.tsx` (редирект на `/dashboard` вместо ролевых маршрутов). Удаляются `apps/frontend/app/(private)/filial/`, `(private)/cfo/`, `(private)/dtoe/`; добавляется `apps/frontend/app/(private)/dashboard/` с серверной страницей и тремя клиентскими компонентами дашбордов (`FilialDashboard`, `CfoDashboard`, `DtoeDashboard`).
- **Backend**: не затрагивается — переиспользуются уже существующие ролевые эндпоинты статистики (`getCorrectionStatsCfo` и аналогичные для филиала/ДТОиР) и существующий `GET /auth/me`.
- **API-контракт**: не затрагивается — новых эндпоинтов не требуется.
- **Вне области**: наполнение `/notifications` (страница не создаётся, только ссылка в меню), функциональность роли `ADMIN` (её домашний маршрут не входит в область этого change, как и в `align-login-role-redirect`), загрузка реальной картинки логотипа (пока только форма-плейсхолдер).
- Внешних зависимостей не затронуто.

## Влияние на качество

- **Уровень риска**: P1 — затронута навигация и точка входа приватного контура для всех трёх бизнес-ролей, но без изменения бизнес-правил согласования корректировок.
- **Затронутые маршруты**: `/dashboard` (новый, заменяет `/filial`, `/cfo`, `/dtoe`), приватный layout (`/(private)/*`), экран входа (`/`).
- **Затронутые frontend-компоненты**: `SidebarNav`, `PrivateLayout`, `LoginForm`, новые `FilialDashboard`/`CfoDashboard`/`DtoeDashboard`.
- **Затронутые backend-модули**: нет изменений — используются существующие ролевые эндпоинты и `auth/me`.
- **Затронутые API**: нет новых; используются существующие `GET /auth/me`, `POST /auth/logout`, ролевые эндпоинты статистики.
- **TDD-порядок**: failing component/E2E-тест на новое поведение сайдбара и `/dashboard` → минимальная реализация → green → refactor.
- **Обязательные уровни проверки**: Frontend Unit (маппинг роли → компонент дашборда, вычисление инициалов ФИО), Frontend Component (`SidebarNav` с брендингом и профилем, ролевые дашборд-компоненты), Frontend E2E (вход → редирект на `/dashboard` → корректный ролевой дашборд; выход из сайдбара).
- **Ручные проверки или waiver**: ручная проверка адаптивной раскладки сайдбара на мобильном экране (бургер-меню уже покрыт существующими тестами `add-private-sidebar-nav`, повторно не переснимается).
- **План отката**: изменения локализованы в frontend-роутинге приватного контура и не меняют схему БД/API-контракт — откат равносилен revert соответствующих коммитов/PR.
