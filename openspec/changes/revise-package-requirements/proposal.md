## Why

Текущий состав обязательного пакета документов для типа корректировки
«Стандартная корректировка» (`apps/backend/src/database/seed.ts`, справочник
`PackageRequirement`) — «Excel корректировка» (основной слот, вне
`PackageRequirement`), «D-листы» (`EXCEL_SHEET`), «ДОО» (`DOCUMENT`,
обязателен), «Дефектная ведомость» (`DOCUMENT`, не обязателен) — не
соответствует реальному перечню документов, который запросил пользователь по
результатам разведки блока «Комплектность пакета» на карточке корректировки.

Пользователь запросил новый состав, полной заменой старого:

1. Excel корректировка *(уже существует как основной слот — без изменений)*
2. Согласованная служебная записка
3. Пакет обосновывающих документов
4. Перечень комплекта МТР (ХС) — **выбор ровно одного** из двух вариантов:
   - 4.1 Локальный сметный расчёт (ПД)
   - 4.2 ХЗ-х ТКП

Пункт 4 — принципиально новый случай для модели данных: сейчас каждый элемент
`PackageRequirement` проверяется независимо («заполнен — обязателен, пуст —
пакет неполный»). Пункты 4.1/4.2 должны работать иначе — комплектность пакета
по этому пункту считается выполненной, если заполнен **любой один** из двух,
второй остаётся доступен, но не обязателен после того, как первый заполнен
(уточнено в диалоге с пользователем: «ровно один из трёх» — где пунктов
оказалось два, не три, но принцип выбора «ровно один, не оба сразу
обязательны» подтверждён).

## Побочная находка при реализации

При сквозной проверке через API обнаружен и исправлен пред­существующий баг,
не связанный напрямую с составом пакета, но блокировавший саму возможность
проверить эту фичу: `DETAIL_RELATIONS`
(`apps/backend/src/corrections/corrections.service.ts`) не подгружал
`correctionType.requirements` — из-за этого `checkPackageComplete()` в
реальном боевом пути (`send()`, `resubmit()`, `toDetailDto()`) всегда получал
`correction.correctionType.requirements === undefined` и молча проверял
только основной Excel-слот, ни одно типизированное требование пакета
(`PackageRequirement`) на практике не блокировало направление корректировки.
Юнит-тесты этого не ловили, т.к. тестовые фикстуры вручную передавали
`correctionType.requirements`. Исправлено добавлением
`'correctionType.requirements'` в `DETAIL_RELATIONS` — без этого исправления
новое правило «группа МТР» тоже не работало бы в реальности, несмотря на
корректный код. Подтверждено `curl`-проверкой на `infra-db-1` (см.
`test-plan.md`).

## What Changes

- **Backend, модель данных**: `PackageRequirement` получает два новых поля —
  `choiceGroupKey: string | null` (общий ключ для альтернативных требований;
  `null` — требование проверяется независимо, как сейчас) и `groupLabel:
  string` (текст заголовка группы для UI, например «Перечень комплекта МТР
  (ХС)»; пусто для независимых требований).
- **Backend, бизнес-правило комплектности**: `checkPackageComplete()`
  (`corrections.service.ts`) переработан — требования без `choiceGroupKey`
  проверяются как раньше (каждое обязательное требование должно иметь ≥1
  версию файла); требования с одинаковым `choiceGroupKey` считаются
  выполненными группой, если **хотя бы одно** из них имеет ≥1 версию файла;
  если ни одно не заполнено — в список недостающих элементов попадает
  `groupLabel` с перечислением вариантов через «/».
- **Backend, справочные данные**: `database/seed.ts` — состав требований типа
  «Стандартная корректировка» полностью заменён на список выше (см. Why).
  Старые требования («D-листы», «ДОО», «Дефектная ведомость») удаляются из
  сида; на уже засеянных средах — правятся вручную (см. `tasks.md`).
- **API-контракт**: `DocumentSlot`/`PackageRequirement`-связанные схемы
  дополняются полями `choiceGroupKey` (nullable), `groupLabel` (string).
- **Frontend**: `PackageCompleteness` (`.../corrections/[humanId]/components/package-completeness.tsx`)
  визуально группирует элементы с одинаковым `choiceGroupKey` под общим
  подзаголовком-группой с пометкой «выберите один из вариантов»; статус
  «Обязателен»/заполненность у сгруппированных строк отображается с учётом
  правила «группой, не по отдельности» (конкретное визуальное решение — см.
  `design.md` → «Дизайн (UI)», пока не подтверждено пользователем).

## Impact

- **Backend**: `apps/backend/src/org/entities/package-requirement.entity.ts`
  (`choiceGroupKey`, `groupLabel`), `apps/backend/src/corrections/corrections.service.ts`
  (`checkPackageComplete()`), `apps/backend/src/corrections/corrections.mapper.ts`
  (`toDocumentSlotDto` — прокинуть новые поля), `apps/backend/src/database/seed.ts`
  (состав требований + переработка демо-генератора `seedCorrection()`, который
  сейчас жёстко ссылается на `reqExcelSheet`/`reqDoo` и текст замечаний про
  «ДОО»).
- **API-контракт**: `api/src/components/schemas/document-slot.yaml` (или где
  фактически описан `DocumentSlot`) — новые поля.
- **Frontend**: `package-completeness.tsx`, Kubb-кодоген (перегенерация после
  правки контракта).
- **Уже засеянные среды**: состав `package_requirements` для типа
  «Стандартная корректировка» нужно обновить вручную (SQL) — см. `tasks.md`.
  Существующие `document_slots`, ссылающиеся на удалённые требования
  («D-листы»/«ДОО»/«Дефектная ведомость»), физически не удаляются
  (`onDelete: 'RESTRICT'` у `DocumentSlot.requirement` не позволит удалить
  строку `PackageRequirement`, пока есть ссылающиеся слоты) — см. `design.md`
  за стратегией миграции существующих данных.
- **Вне области**: изменение состава пакета для гипотетических будущих типов
  корректировки, кроме «Стандартная корректировка» (сейчас в системе только
  один тип); произвольная глубина вложенности групп (поддержана только
  плоская группа «выбери один из N», без под-групп внутри групп).

## Влияние на качество

- **Уровень риска**: P1 — изменение обязательного бизнес-правила
  комплектности пакета (что именно блокирует направление корректировки),
  затрагивает уже существующий и часто используемый путь (`send()`,
  `resubmit()`), но локализовано в одной функции с чёткими границами.
- **Затронутые маршруты**: `/corrections/create`, `/corrections/[humanId]`
  (блок «Комплектность пакета»).
- **Затронутые frontend-компоненты**: `PackageCompleteness`.
- **Затронутые backend-модули**: `org` (`PackageRequirement`), `corrections`
  (`checkPackageComplete`, mapper), `database` (сид).
- **Затронутые API**: `GET /corrections/{humanId}` (`DocumentSlot.choiceGroupKey`/
  `groupLabel` — новые поля, аддитивно), `POST /corrections/{humanId}/send`/
  `.../resubmit` (сообщение об ошибке `400` при неполном пакете меняет состав
  перечисляемых недостающих элементов для группы).
- **TDD-порядок**: failing unit-тест на `checkPackageComplete()` (группа не
  заполнена → элемент группы в `missing`; заполнен один из двух → группа не в
  `missing`; заполнены оба → тоже не в `missing`) → минимальная реализация →
  green → refactor.
- **Обязательные уровни проверки**: Backend Unit
  (`corrections.service.spec.ts`, новые кейсы для `checkPackageComplete`
  через `send()`/`create()`+`send()`); Static (`tsc --noEmit` backend/frontend);
  Frontend Component (`package-completeness.component.test.tsx` — рендер
  группы, если визуальное решение зафиксировано до реализации).
- **Ручные проверки**: пересидированная/обновлённая БД — создание
  корректировки, попытка направить с пустой группой → `400` с текстом
  недостающего элемента-группы; загрузка файла в один из двух вариантов →
  направление становится доступным без заполнения второго.
- **План отката**: revert коммита; на средах, где уже применён ручной SQL
  (переименование состава `package_requirements`), потребуется обратный SQL
  (см. `tasks.md`) — данные аддитивны (новые nullable-колонки), откат кода
  безопасен независимо от отката данных.
