# ЧТЗ — Модуль «План на 2027»

Частное техническое задание по модулю «План на 2027»: задачи всех трёх ролей,
экраны, назначение каждого элемента интерфейса. Описывает реализованное поведение —
код на момент написания живёт на ветках `chore/planning-2027-openspec`,
`feat/planning-2027-api-contract`, `feat/planning-2027-backend`,
`feat/planning-2027-frontend-create-detail`, `feat/planning-2027-frontend-dashboard`
(см. `openspec/changes/planning-2027-package-review/`), ещё не влитых в `dev` на
момент написания документа.

Версия 1.0 · Проект GasDashboard.

Модуль реализован как **полностью независимый второй экземпляр** механики
«Корректировки» — отдельные таблицы БД (`plans`, `plan_types`,
`plan_package_requirements`, ...), отдельный API-неймспейс `/plans`, отдельные
человекочитаемые ID (`PLN-000001`, замечания — `PLR-000001`), без единой FK-связи с
таблицами `corrections`. Единственная общая сущность — справочник `FilialCfoLink`
(привязка филиал↔ЦФО, общесистемный справочник, не бизнес-данные модуля).
Документ использует терминологию ЧТЗ «Корректировка»
(`docs/tz/filial-cabinet.md`, `docs/tz/cfo-cabinet.md`, `docs/tz/dtoe-cabinet.md`) —
общая механика уведомлений, Sidebar, правил прочитанности не повторяется, даётся
ссылка на соответствующий раздел.

## 0. Соответствие терминов «Корректировка» → «План на 2027»

| Корректировка | План на 2027 |
|---|---|
| `Correction`, `COR-000001` | `Plan`, `PLN-000001` |
| `CorrectionType` | `PlanType` |
| `PackageRequirement` | `PlanPackageRequirement` |
| `DocumentSlot` | `PlanDocumentSlot` |
| Слот «Excel корректировка» (`requirementId == null`) | Слот «Excel плана» (`requirementId == null`) |
| `Remark`, `REM-000001` | `PlanRemark`, `PLR-000001` |
| `/corrections`, `/dashboard`, `/notifications` | `/planning`, `/planning/files`, аналог `/notifications` — пометка через `markNotificationsReadByPlan` |

**Намеренные отличия от Корректировки** (не пробелы, а решения, принятые при
проектировании модуля):

1. Нет статуса `SENT_TO_DTOE` — у Корректировки это технический зарезервированный
   статус, ни разу не используемый в реальных переходах (см.
   `apps/backend/AGENTS.md`, «Статусная модель корректировки»); модуль плана не
   переносит неиспользуемый статус.
2. Есть дополнительное действие «Отменить решение» (`canCancelCfoDecision`) — ЦФО
   может откатить собственное решение (согласовал/вернул) обратно в «Ожидает» как
   страховку от случайного клика, пока план не ушёл в ДТОиР. У Корректировки такого
   действия нет.
3. Есть отдельный маршрут `/planning/[id]/edit` — смена типа плана, пока статус
   `DRAFT` (у Корректировки решение о таком же маршруте зафиксировано отдельно,
   см. ЧТЗ Филиала, раздел 0.3 — оба модуля пришли к одному и тому же решению).
4. Состав пакета демо-типа «Пообъектный план ДТОиР на 2027 год» **зеркалит**
   состав демо-типа Корректировки 1:1 (те же 6 строк, включая группу выбора «один
   из группы» — «Локальный сметный расчёт (ПД)» / «ХЗ-х ТКП») — совпадение
   намеренное, для демо-данных, не следствие переиспользования кода.

## 3. Экран «Создать план» (`/planning/create`)

Идентичен ЧТЗ Филиала, раздел 3: единственное поле «Тип плана» (выпадающий список),
кнопка «Создать» (неактивна, пока тип не выбран; блокируется на время запроса),
кнопка «Отмена» → `/planning`. Создание сразу открывает карточку `/planning/{id}`.

## 4. Экран «Файлы» (`/planning/files`)

**В отличие от Корректировки** (там отдельного экрана «Файлы» нет вообще — список и
есть дашборд) и **в отличие от Факта** (там «Файлы» — вход для создания новых
пакетов по направлению), у плана «Файлы» — это **плоский архив** уже существующих
планов, доступных роли, с собственным поиском и фильтром, не дублирующий детальную
карточку:

| Элемент | Что делает |
|---|---|
| Заголовок «Файлы — План на 2027» + пояснение | Статический текст. |
| Поле поиска «Поиск по ID (PLN-000001)» | Фильтрует список по вхождению подстроки в `humanId`, запрос на сервер (`q` в `GET /plans`). |
| Фильтр по статусу | Выпадающий список из всех 9 статусов плана (не укрупнённых групп, в отличие от донат-диаграммы дашборда) + «— все статусы —». |
| Таблица: ID, Филиал, Тип, Статус, Изменено, «Открыть» | Открывает ту же карточку `/planning/{id}`, что и рабочий стол — отдельного детального экрана под `/planning/files/{id}` нет (решение, а не недосмотр). |

Видимость записей ограничена так же, как и везде в модуле: Филиал видит свои, ЦФО —
направленные ему, ДТОиР/ADMIN — все.

## 5. Карточка плана (`/planning/[id]`)

Общий маршрут для всех ролей, порядок блоков сверху вниз: шапка → «Комплектность
пакета» → «Направить на проверку» → «Статусы ЦФО» → «Замечания» (таблица +
панель решений) → «Повторное направление» → «История действий».

### 5.1 Блок «Шапка плана»

Идентичен ЧТЗ Филиала, раздел 4.1 (Филиал, ID, Тип плана, Статус, Этап, Автор,
Создано/Изменено) плюс ссылка «Изменить тип» — видна автору (Филиалу), только
пока статус = `DRAFT`, ведёт на `/planning/[id]/edit`.

### 5.2 Блок «Комплектность пакета» — задачи 2 и 6

Идентичен ЧТЗ Филиала, раздел 4.2, с двумя дополнениями:

| Элемент | Отличие от Корректировки |
|---|---|
| Колонка «Обязателен» | Значение «Да (один из группы)» для слотов с `choiceGroupKey` (МТР-группа «Локальный сметный расчёт (ПД)» / «ХЗ-х ТКП») — у Корректировки колонка та же, механика групп выбора идентична. |
| Колонка «Проверено» (чекбокс) | Видна только проверяющим (ЦФО/ДТОиР), **отсутствует у Корректировки** — локальная, не сохраняется на сервере отметка «уже посмотрел» для текущего экрана; скрывает кнопку «Оставить замечание к элементу» для отмеченных строк на время сессии, снятие галочки возвращает кнопку. Чисто клиентское удобство, не бизнес-правило. |
| Кнопка «Загрузить версию» | Видна владельцу (Филиалу), пока статус ≠ `APPROVED_BY_DTOE` — идентично Корректировке. |
| Кнопка «Оставить замечание к элементу» | Видна ЦФО (`myCfoStatus.status === PENDING`) или ДТОиР (статус плана = `UNDER_DTOE_REVIEW`) — идентично Корректировке; можно оставить несколько замечаний за один заход, финализация возврата — отдельным действием (5.5). |

### 5.3 Блок «Направить на проверку» — задача 3

Идентичен ЧТЗ Филиала, раздел 4.2 (блок направления в разделе 4 ЧТЗ Филиала описан
как часть карточки, а не отдельный подраздел — здесь выделен явно): виден только
Филиалу-автору в статусе `DRAFT`. Чекбоксы `availableCfos` (только привязанные к
филиалу через `FilialCfoLink`), кнопка «Направить» неактивна, если не заполнены все
обязательные слоты (подсказка «Заполните все обязательные слоты») **или** не выбран
ни один ЦФО (подсказка «Выберите хотя бы один ЦФО») — см. также открытый вопрос 7.2.

### 5.4 Блок «Статусы ЦФО»

Идентичен ЧТЗ Филиала, раздел 4.3 — только чтение для Филиала. Для ЦФО и ДТОиР
блок дополнительно интерактивен через панель решений (5.5).

### 5.5 Блок «Замечания» + панель решений

Таблица замечаний — идентична ЧТЗ Филиала, раздел 4.4 (ID, Элемент пакета, От кого,
Описание, Что исправить, Лист/строка/ячейка, Статус) плюс колонка действий
(«Отметить исправленным» для Филиала, «Удалить» для автора замечания в статусе
`OPEN`). Панель решений над таблицей — шапка блока:

| Кнопка | Кто видит | Когда активна | Что делает |
|---|---|---|---|
| «Согласовать» | ЦФО, `myCfoStatus.status === PENDING` | Всегда при видимости | Статус этого ЦФО → `APPROVED`. Последний обязательный → статус плана `ALL_CFO_APPROVED`. |
| «Вернуть на доработку» | ЦФО, есть собственное открытое замечание (`myCfoStatus.cfoId`) | Активна, только если у этого ЦФО есть замечание в статусе `OPEN` | Статус этого ЦФО → `RETURNED`, статус плана → `RETURNED_FOR_REVISION`. |
| **«Отменить решение»** (отсутствует у Корректировки) | ЦФО, `myCfoStatus.status` ∈ {`APPROVED`, `RETURNED`}, статус плана не в {`UNDER_DTOE_REVIEW`, `RETURNED_BY_DTOE`, `APPROVED_BY_DTOE`} | Всегда при видимости | Откатывает статус этого ЦФО обратно в `PENDING`. Замечания не трогает (часть истории). Страховка от случайного клика по «Согласовать»/«Вернуть». |
| «Направить в ДТОиР» | ЦФО, статус плана = `ALL_CFO_APPROVED`, `myCfoStatus.status === APPROVED` | Всегда при видимости | Статус плана → `UNDER_DTOE_REVIEW`. Любой согласовавший ЦФО, не только последний. |
| «Согласовать (ДТОиР)» | ДТОиР, статус = `UNDER_DTOE_REVIEW` | Всегда при видимости | Статус → `APPROVED_BY_DTOE` (финальный). |
| «Вернуть на доработку (ДТОиР)» | ДТОиР, статус = `UNDER_DTOE_REVIEW`, есть собственное открытое замечание (`cfoId === null`) | Активна, только если есть открытое замечание ДТОиР | Статус → `RETURNED_BY_DTOE`. |

### 5.6 Блок «Повторное направление» — задача 8

Идентичен ЧТЗ Филиала, раздел 4.5: виден Филиалу, только в статусе
`RETURNED_FOR_REVISION`, когда есть хотя бы один вернувший ЦФО (`returnedCfos`).
Список чекбоксов только среди вернувших, кнопка «Перенаправить» неактивна, пока
остались открытые замечания выбранного ЦФО. Дополнительно — второй, независимый
подблок «Повторно направить в ДТОиР»: виден при статусе `RETURNED_BY_DTOE`, кнопка
активна, только когда все замечания от ДТОиР (`cfoId === null`) в статусе
`FIXED_BY_FILIAL`.

### 5.7 Блок «История действий»

Идентичен ЧТЗ Филиала, раздел 4.6 — только чтение, те же три колонки.

## 6. Экран «Изменить тип плана» (`/planning/[id]/edit`)

| Элемент | Что делает |
|---|---|
| Заголовок «Изменить тип плана {ID}» + пояснительный текст | Явно предупреждает: смена типа переформирует комплектность пакета — уже загруженные версии в слотах, которых нет в новом типе, удаляются безвозвратно; общий слот «Excel плана» не затрагивается. |
| Поле «Тип плана» (выпадающий список) | Все активные типы из справочника. |
| Кнопка «Сохранить» | Неактивна, пока не выбран другой тип, отличный от текущего, или пока идёт запрос. |
| Кнопка «Отмена» | Возврат на `/planning/[id]` без изменений. |

Доступен только автору (Филиалу), только в статусе `DRAFT` — маршрут недоступен
даже при прямом вводе адреса вне этих условий (проверка на бэкенде).

## 7. Открытые вопросы

1. **Отсутствие обзорного списка у ДТОиР на дашборде** — тот же пробел, что в
   `docs/tz/dtoe-cabinet.md`, раздел 7.1. У плана он частично закрыт экраном
   `/planning/files` (раздел 4 этого документа) — ДТОиР там видит полный список без
   фильтра по владению, как и по «Факту».
2. **Запрос пользователя (не реализован на момент написания документа):** разрешить
   направление на проверку (кнопка «Направить», раздел 5.3) при неполном пакете —
   не требовать заполнения всех обязательных слотов, достаточно одного загруженного
   файла. Сейчас (и у Плана, и у Корректировки, и у Факта — кроме одного отличия, см.
   `docs/tz/fact-module.md`, открытый вопрос 4) кнопка блокируется, пока
   `missingRequirements` не пуст. Требует явного решения: точечно для модуля плана,
   или как согласованное изменение бизнес-правила №1 (`AGENTS.md`) сразу во всех
   трёх модулях — задача поднималась в разговоре с пользователем, но реализация не
   доведена до конца.
3. Ветки модуля ещё не влиты в `dev` (см. заголовок документа) — после мержа
   актуализировать шапку документа, убрав список веток.
