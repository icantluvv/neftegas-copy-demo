# Процесс разработки

## Структура репозитория

```
gas-dashboard/
├── api/
│   ├── redocly.yaml          ← линтер-правила и сборка спеки
│   └── src/
│       ├── openapi.yaml      ← корневой API-контракт (source of truth)
│       ├── paths/            ← эндпоинты (один файл = один path)
│       └── components/schemas/ ← переиспользуемые схемы
├── apps/
│   ├── backend/
│   │   └── AGENTS.md         ← технический контекст BE для AI
│   └── frontend/
│       └── CLAUDE.md         ← технический контекст FE для AI
├── docs/                     ← документация проекта
├── infra/                    ← Docker Compose, Docker
└── openspec/
    ├── config.yaml           ← продуктовый контекст + оба стека
    ├── specs/                ← живая документация поведения продукта
    └── changes/
        └── <feature>/        ← единый change для FE и BE
```

## Процесс разработки фичи

```text
1. ТРЕБОВАНИЯ
   Аналитик/PM фиксирует бизнес-правила и сценарии во входном тикете задачи —
   они становятся входом для change (proposal.md и specs), отдельный файл не создаётся.

2. ЕДИНЫЙ OPENSPEC CHANGE  (создаёт тот, кто первым приступил к задаче)
   /openspec-propose <feature>

   proposal.md   — полное изменение: общая цель, затронутые FE- и BE-модули
   specs/        — поведение системы в нейтральном продуктовом языке
   design.md     — решения для FE и BE + API Shape (эндпоинты, схемы, ошибки)
   tasks.md      — первая задача: API-контракт; далее отдельные разделы Backend и Frontend
   test-plan.md  — проверки сценариев для обеих сторон и общие verification gates

3. API-КОНТРАКТ  (первая задача, до начала реализации FE и BE)
   За контракт отвечает разработчик, который первым взял задачу и создал change.
   Он создаёт или обновляет контракт в api/ по API Shape из design.md и запускает линтинг.
   Обязательное согласование со второй стороной не требуется: после успешной проверки
   контракт фиксируется как source of truth, а задача отмечается выполненной.
   Когда вторая сторона приступает к своим задачам, она может внести в контракт
   необходимые изменения и повторно запустить его проверки.

4. РЕАЛИЗАЦИЯ  (параллельно в рамках одного change)
   FE: /openspec-apply-change <feature> — выполнять только задачи раздела Frontend.
   BE: /openspec-apply-change <feature> — выполнять только задачи раздела Backend.

   Каждая сторона отмечает выполненными только свои задачи и обновляет относящиеся
   к ним проверки в test-plan.md. Общие артефакты change изменяются согласованно.

5. ARCHIVE  (один раз для общего change)
   После перехода задачи в трек «Приемка»:
   /openspec-archive-change <feature>
```

## Правила OpenSpec

Детальные правила описания спецификаций, дизайна и задач — в `openspec/config.yaml` (раздел `rules`).

- На одну продуктовую задачу создаётся один OpenSpec change без префиксов `be-` и `fe-`.
- Change создаёт и заполняет тот, кто первым приступил к задаче — frontend- или backend-разработчик.
- `proposal.md`, `specs/`, `design.md` и `test-plan.md` описывают фичу целиком, а не только одну сторону.
- Первая исполняемая задача в `tasks.md` всегда — создание или обновление API-контракта.
- За API-контракт отвечает разработчик, который первым взял задачу и создал change; обязательное согласование со второй стороной не требуется.
- Вторая сторона может изменить контракт, когда приступит к выполнению своих задач.
- После API-контракта задачи группируются по владельцам: `Backend` и `Frontend`.
- При запуске `/openspec-apply-change` разработчик выполняет и закрывает только задачи своей стороны.
- Общий change архивируется только после завершения обеих сторон.

## Контекст для AI

| Где работает AI | Откуда берёт контекст |
|---|---|
| `/openspec-propose` | `openspec/config.yaml` |
| BE реализация | `apps/backend/AGENTS.md` |
| FE реализация | `apps/frontend/CLAUDE.md` |

## Definition of Done

| | Критерий |
|---|---|
| BE | `npm run test` + `npm run test:e2e` + `npm run lint` (из `apps/backend`) |
| FE | тесты + линтер (см. `apps/frontend/CLAUDE.md`) |
| API | `npm run lint` из `api/` без ошибок |
| Фича | API-, Backend- и Frontend-задачи общего change завершены; change заархивирован один раз |
