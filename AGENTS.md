# AGENTS.md

Инструкции для AI-агентов уровня монорепозитория Дэшборд Нефтегаз. Здесь — карта
проекта и кросс-контурные правила. Правила реализации конкретного контура — в его
собственном `AGENTS.md` (см. ниже).

## Что это

Дэшборд Нефтегаз — Система согласования корректировок.
Внутренний документооборот согласования корректировок между 4 филиалами
(газовыми компаниями), 17 подразделениями администрации (ЦФО) и департаментом ДТОиР,
который выполняет финальное согласование и полный аудит по системе.

## Глоссарий

| Термин                | Значение                                                                                                                                               |
|-----------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------|
| Корректировка         | Единица документооборота: пакет документов, который филиал направляет на согласование. Человекочитаемый ID: COR-000001.                                |
| Замечание             | Претензия проверяющего (ЦФО или ДТОиР) к конкретному элементу пакета. Человекочитаемый ID: REM-000001.                                                 |
| Слот / элемент пакета | Одна из позиций обязательного состава документов: «Excel корректировка», «Пакет документов», «Счета на оплату» (состав зависит от типа корректировки). |
| Версия файла          | Каждая загрузка файла в слот создаёт новую версию; предыдущие версии не удаляются.                                                                     |
| ЦФО                   | Центр финансовой ответственности — подразделение администрации, проверяющее корректировки привязанных к нему филиалов.                                 |
| ДТОиР                 | Финальный согласующий орган. Также выполняет функцию аудита по всей системе.                                                                           |

## Роли и матрица доступа

Три бизнес-роли. У каждого пользователя — ровно одна роль, назначается администратором при создании аккаунта (создание
аккаунтов — вне UI конечного пользователя, отдельная административная функция).

| Действие                             | Филиал                                 | ЦФО                                         | ДТОиР                                    |
|--------------------------------------|----------------------------------------|---------------------------------------------|------------------------------------------|
| Создать корректировку                | ✓ (только для своего филиала)          | —                                           | —                                        |
| Загрузить версию файла в слот        | ✓ (пока не финальный статус)           | —                                           | —                                        |
| Направить на проверку выбранным ЦФО  | ✓                                      | —                                           | —                                        |
| Оставить замечание к элементу пакета | —                                      | ✓ (если корректировка направлена этому ЦФО) | ✓ (если корректировка на проверке ДТОиР) |
| Согласовать (на уровне ЦФО)          | —                                      | ✓ (свой статус)                             | —                                        |
| Направить в ДТОиР                    | —                                      | ✓ (любой согласовавший ЦФО)                 | —                                        |
| Финальное согласование / возврат     | —                                      | —                                           | ✓                                        |
| Отметить замечание исправленным      | ✓ (свои корректировки)                 | —                                           | —                                        |
| Удалить замечание                    | автор замечания, пока статус «открыто» | автор замечания, пока статус «открыто»      | автор замечания, пока статус «открыто»   |
| Видеть чужие корректировки (аудит)   | —                                      | —                                           | ✓ (все, всех филиалов и ЦФО)             |

Право «удалить замечание» технически не зависит от роли — зависит только от авторства и статуса конкретной записи.
Проверка обязана выполняться на бэкенде (a не только скрытием кнопки в UI) — иначе прямой запрос к API в обход
интерфейса позволит удалить чужое замечание.

## Бизнес-правила и защита от некорректных состояний

Все правила ниже обязаны проверяться на бэкенде — фронт может дублировать их для UX
(дизейблить кнопки, скрывать действия), но никогда не быть единственной защитой:
прямой запрос к API в обход интерфейса не должен приводить к некорректному состоянию.

1. Направление возможно только если все обязательные слоты пакета содержат хотя бы
   одну версию файла.
2. Филиал может направить корректировку только тем ЦФО, которые связаны с ним через
   `FilialCFO` — проверка обязательна на бэкенде, а не только ограничением списка
   чекбоксов на фронте.
3. Замечание можно оставить только к корректировке, которая в данный момент
   находится «на проверке» у конкретного проверяющего (его `CorrectionCfoStatus` =
   `PENDING`, либо для ДТОиР — статус корректировки = `UNDER_DTOE_REVIEW`). Это
   защита от гонки состояний: если два проверяющих открыли карточку одновременно и
   один уже принял решение, второй не должен иметь возможность отправить своё поверх.
4. Повторное направление возможно только когда все замечания от ЦФО, вернувших
   корректировку, помечены филиалом как исправленные.
5. Направление в ДТОиР возможно только когда все обязательные ЦФО в статусе
   `APPROVED` — как только последний ЦФО согласовывает, кнопка появляется у всех
   согласовавших ЦФО, а не только у последнего.
6. Статус согласовавшего ранее ЦФО не сбрасывается при повторном направлении
   другому ЦФО — история согласования каждого ЦФО независима.
7. Удалить можно только собственное замечание и только в статусе `OPEN`. Замечание
   в статусе `FIXED_BY_FILIAL` или `CLOSED` неизменяемо — эти записи являются частью
   истории согласования.
8. Версии файлов не удаляются никогда — исправление документа всегда добавляет
   новую версию, а не заменяет старую.
9. Email уникален в рамках системы, используется как логин. Пароль хранится только
   в виде хэша (bcrypt/argon2), не логируется и не возвращается ни в одном
   API-ответе, включая ответы для роли ДТОиР при аудите.
10. Каждое действие, меняющее статус корректировки или замечания, обязано быть
    атомарным (транзакция БД) — например, «согласовать» одновременно меняет
    `CorrectionCfoStatus` и пересчитывает общий статус `Correction`; частичное
    применение недопустимо.

## Кросс-контурные правила

- **Contract-first.** `api/src/openapi.yaml` и связанные `api/src/**` — единственный
  источник истины HTTP API. Backend, Kubb-codegen фронта и интеграция следуют
  последней успешно проверенной версии контракта. Порядок единого FE/BE-изменения —
  в `docs/DEVELOPMENT_PROCESS.md`.
- **Единый change на фичу.** Одна продуктовая задача — один OpenSpec-change без
  префиксов `be-`/`fe-`; API, Backend и Frontend живут в одном change. Легаси
  `be-*`/`fe-*` changes не переименовывать.
- **Трейлеры коммита.** Когда правка относится к тикету, добавляй трейлер `Refs`
  (тикет); когда к OpenSpec-change — трейлер `Change` (имя change). Оба
  необязательны: мелкие правки бывают без тикета, многие правки — без change.
  Если добавляешь трейлеры — после заголовка пустая строка, затем трейлеры. Пример:

  ```
  Refs: KT-68007863
  Change: stage-dates-not-null
  ```
- **Язык.** Инструкции, документация, UI-тексты, тестовые описания и комментарии —
  русский. Код и идентификаторы — английский. Служебные маркеры OpenSpec, RFC 2119
  и Gherkin — английский (их парсит CLI).
- **Правила контура.** Границы модулей, генерируемый код (codegen, миграции) и
  прочая специфика реализации — по правилам соответствующего контура из его
  `AGENTS.md`; в корневом не дублируются.

## Источники истины

- `docs/DEVELOPMENT_PROCESS.md` — процесс единого FE/BE change и contract-first.
- `api/src/openapi.yaml`, `api/src/**` — публичный HTTP-контракт.
- `apps/backend/AGENTS.md` — backend.
- `apps/frontend/AGENTS.md`, `docs/adr/` — frontend.
- `openspec/config.yaml` — процессные правила OpenSpec-артефактов.

## Окружение

Backend-команды (npm — NestJS, TypeORM, Jest) выполняются из `apps/backend`.
Frontend-команды — из `apps/frontend` (Bun). API-команды (`npm run lint`,
`npm run bundle`) — из `api/`.
